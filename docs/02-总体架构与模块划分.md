本篇定义 `base/` → `media/` → `player/` → `platform/` 四层架构，目录结构与类名**一一对应 Chromium 的 `base/` 与 `media/`**。

## 1. 为什么镜像 Chromium

Chromium 的 `media/` 目录是工业界最成熟的开源媒体管线实现。它解决的是与我们完全相同的问题（解复用 → 解码 → 同步 → 输出），并且：

- `media/base/` 放**接口与核心值类型**，`media/filters/` 放**具体实现** —— 这个分离正是我们需要的"核心不依赖 FFmpeg"
- `media::DecoderBuffer` / `VideoFrame` / `AudioBus` 已经是 `scoped_refptr` 化的、带 `StorageType` 类型擦除的成熟设计
- `media::DemuxerStream::Read(count, ReadCB)` + `Status{kOk, kAborted, kConfigChanged, kError}` 是比"阻塞队列"更精确的背压表达
- `media::VideoDecoder::Decode(buffer, DecodeCB)` 异步回调式接口，天然适配硬件解码器（MediaCodec / VideoToolbox / VAAPI）
- `media::Pipeline` + `PipelineController` + `Renderer` + `VideoRendererImpl` / `AudioRendererImpl` + `VideoFrameCompositor` 的分层，正好对应 ijkplayer 里那坨 5400 行 `ff_ffplay.c` 应该被拆成的样子
- `media::AudioRendererSink::RenderCallback::Render(delay, delay_timestamp, glitch_info, AudioBus* dest)` —— 这正是我们想要的 pull 模型，且额外带了硬件延迟与 glitch 统计

采用它的命名与结构带来三个直接好处：**SDK 使用者上手成本低**（读过 Chromium 就能读懂）、**设计分歧有裁决依据**、**未来扩展路径清晰**（要接 Mojo/DRM/WebCodecs 语义时不用重构）。

代价：需要自研一个 `base/` 子集（见 §3），约 4000 行、2.5 周。

## 3. `base/` — 自研的 Chromium base 子集

### 3.1 为什么自研而不是 vendor

| 方案 | 评估 |
|---|---|
| A. 从 Chromium 抽取 `base/` 子树 | ❌ 依赖 absl + Chromium 构建系统（`//base` 的 BUILD.gn）+ 大量 `base::*` 内部交叉依赖，抽取成本远超收益；且会带入我们不需要的 30k 行 |
| B. 用 Abseil | ❌ Abseil 明确不提供 task runner / `BindOnce` / `WeakPtr` / `TimeTicks` / message pump，而这些正是我们最需要的部分。只能覆盖 `StatusOr`/`Mutex`/`Notification` |
| C. **自研同名同语义最小子集** | ✅ 约 28 个文件 / 4000 行（含测试）。每个文件头注明 `API mirrors Chromium's base/xxx.h (BSD-3-Clause)`。调用方形态与 Chromium 完全一致，未来若要换成 vendored Chromium base 只需替换实现 |

| `buffer_controller.cc` | 缓冲水位与起播判定 | `ffp_toggle_buffering` + `ffp_check_buffering_l` |
| `diagnostics.cc` | `DumpDiagnostics()` JSON 快照 | 无（原版只能加日志重编） |
| `public/c/avbase_c.h`（可选，M11） | C ABI 兼容层 | `ijkplayer.h` |

**`player/` 不包含任何媒体算法**，只做：状态管理、事件派发、配置解析、生命周期编排、诊断输出。

## 9. 关键设计决策（v2 更新）

### D2 · FFmpeg 类型不出现在 `media/base/`

`media::DecoderBuffer` / `VideoFrame` 用 `StorageType` 枚举 + type-erased 存储，对齐 Chromium：

```cpp
// media/base/video_frame.h
class VideoFrame : public base::RefCountedThreadSafe<VideoFrame> {
 public:
  enum class StorageType {
    kStorageOwned,        // CPU 内存，planes() 可读
    kStorageShmem,        // 共享内存（跨进程预留）
    kStorageDmaBufs,      // Linux dmabuf，零拷贝送 GL
    kStorageGpuMemoryBuffer,
    kStorageOpaque,       // 平台私有句柄（MediaCodec Surface / CVPixelBuffer）
    kStorageWrappedSoftware,
  };
  StorageType storage_type() const { return storage_type_; }
  // kStorageOwned / kStorageDmaBufs 时有效，其余返回空 span
  std::span<const uint8_t> visible_data(VideoFrame::Plane plane) const;
  ...
};
```

`kStorageOpaque` 就是解决 MediaCodec/VideoToolbox 输出无 CPU 像素的正确方式（Chromium 也是这么做的），比 ijkplayer 的 `SDL_VoutOverlay` 第二套 vtable 干净得多。

### D3 · 解复用线程模型（与 Chromium 的**有意偏离**）

Chromium 的 `FFmpegDemuxer` 跑在 media sequence 上，因为它的数据源（`BufferedDataSource` / `MultiBufferDataSource`）是**真异步**的，`av_read_frame` 不会阻塞（数据已在内存里，或 IO 在别的 sequence 上完成后回调）。

avbase 首期直接用 FFmpeg 的 `avformat_open_input` + 网络 protocol，`av_read_frame` **会阻塞**。如果把它放在 media sequence 上，`Flush()` / `Reset()` 就会被阻塞住，seek 响应变差。

**方案**（首期）：
- `FFmpegDemuxer` 拥有一个专用 `base::Thread`（名 `avbase-demux`）跑阻塞读循环
- 控制操作（`Initialize` / `Flush` / `Reset` / `MarkEndOfStream`）在调用方 sequence 上，通过**原子标志 + FFmpeg `interrupt_callback`** 与读循环通信
- 读到的包通过 `DemuxerStream::ReadCB` **PostTask 回消费者 sequence**（不跨线程直接调）

**方案**（二期，可选）：为本地文件实现基于 `base::File` + `BlockingTaskRunner` 的真异步 `DataSource`，把 `FFmpegDemuxer` 完全搬回 media sequence，达到 Chromium 级别的响应性。

这是需要确认的 **D3**。

### D4 · 变速用 WSOLA 而非 SoundTouch

ijkplayer 依赖 SoundTouch（GPL/LGPL 双许可，需要额外编译）。Chromium 的 `media::AudioRendererAlgorithm` 是自研的 WSOLA（Waveform Similarity Overlap-Add）实现，Apache/BSD 许可，约 600 行，效果与 SoundTouch 相当。

**建议直接对齐 Chromium 实现**：去掉一个第三方依赖，许可证更干净，且变速行为可与 Chromium 对比验证。
