本篇定义 `base/` → `media/` → `player/` → `platform/` 四层架构，目录结构与类名**一一对应 Chromium 的 `base/` 与 `media/`**。

## 1. 为什么镜像 Chromium

Chromium 的 `media/` 目录是工业界最成熟的开源媒体管线实现。它解决的是与我们完全相同的问题（解复用 → 解码 → 同步 → 输出），并且：

- `media/base/` 放**接口与核心值类型**，`media/filters/` 放**具体实现** —— 这个分离正是我们需要的"核心不依赖 FFmpeg"
- `media::DecoderBuffer` / `VideoFrame` / `AudioBus` 已经是 `scoped_refptr` 化的、带 `StorageType` 类型擦除的成熟设计
- `media::DemuxerStream::Read(count, ReadCB)` + `Status{kOk, kAborted, kConfigChanged, kError}` 是比"阻塞队列"更精确的背压表达
- `media::VideoDecoder::Decode(buffer, DecodeCB)` 异步回调式接口，天然适配硬件解码器（MediaCodec / VideoToolbox / VAAPI）
- `media::Pipeline` + `PipelineController` + `Renderer` + `VideoRendererImpl` / `AudioRendererImpl` + `VideoFrameCompositor` 的分层，正好对应 ijkplayer 里那坨 5400 行 `ff_ffplay.c` 应该被拆成的样子
- `media::AudioRendererSink::RenderCallback::Render(delay, delay_timestamp, glitch_info, AudioBus* dest)` —— 这正是我们想要的 pull 模型，且额外带了硬件延迟与 glitch 统计

采用它的命名与结构带来三个直接好处：**SDK 使用者上手成本低**（读过 Chromium 就能读懂）、**设计分歧有裁决依据**、**未来扩展路径清晰**（要接 Mojo/DRM/WebCodecs 语义时不用重构）。

代价：需要自研一个 `base/` 子集（见 §3），约 4000 行、2.5 周。

实际生效的规则以 `tools/check_invariants.py` 为准（它会随取舍增删，本表只列与分层有关的几条）：

| 门禁 | 守的分层 |

由 C26 管，而 C26 直到 FFmpeg 迁出 `platform/` 才可能加上（此前 `media/filters/` 有 19 个

## 3. `base/` — 自研的 Chromium base 子集

### 3.1 为什么自研而不是 vendor

| 方案 | 评估 |
|---|---|
| A. 从 Chromium 抽取 `base/` 子树 | ❌ 依赖 absl + Chromium 构建系统（`//base` 的 BUILD.gn）+ 大量 `base::*` 内部交叉依赖，抽取成本远超收益；且会带入我们不需要的 30k 行 |
| B. 用 Abseil | ❌ Abseil 明确不提供 task runner / `BindOnce` / `WeakPtr` / `TimeTicks` / message pump，而这些正是我们最需要的部分。只能覆盖 `StatusOr`/`Mutex`/`Notification` |
| C. **自研同名同语义最小子集** | ✅ 约 28 个文件 / 4000 行（含测试）。每个文件头注明 `API mirrors Chromium's base/xxx.h (BSD-3-Clause)`。调用方形态与 Chromium 完全一致，未来若要换成 vendored Chromium base 只需替换实现 |

`media/filters/audio_renderer_impl*.cc` 实现 `RenderCallback::Render()`。测试用的可控速度假

| 文件 | 职责 | ↔ Chromium |
|---|---|---|
| `audio_manager.h/.cc` | 音频设备枚举与 sink 工厂 | `media::AudioManager` |
| `audio_output_device.h/.cc` | ★拥有音频线程，周期调用 `RenderCallback::Render()` | `media::AudioOutputDevice` |
| `audio_parameters.cc` | — | 同名 |
| `null/null_audio_output_stream.cc` | 无声输出（headless / CI） | `media::NullAudioOutputStream` |
| `fake/fake_audio_output_stream.cc` | ★测试用：可控制推进速度的假设备 | `media::FakeAudioOutputStream` |

**注意**：Chromium 的 `AudioOutputDevice` 是"拥有音频回调线程并驱动 `RenderCallback`"的组件 —— 这正是我 v1 设计里"`IAudioSink` pull 模型"的成熟版本。我们直接采用它的接口。

### 4.4 `media/ffmpeg/` — FFmpeg 隔离区

**一个目录，一个目标（`avbase_ffmpeg`），一条判据：需要 `libav*`。** 胶水层与 `ffmpeg_*` 实现

同在此处，可以互相 include——这正是 D11 选的"链接隔离 + 目录隔离，放弃 include 隔离"。

| 类别 | 文件 |
|---|---|
| 版本与初始化 | `av_includes.h`（★唯一的 `extern "C"` 包裹点，也是本目录的 PCH）、`compat.h`（C8：全项目唯一允许 `#if LIBAV*_VERSION_*` 的文件）、`ffmpeg_glue.*`、`log_bridge.*` |
| 解复用 | `ffmpeg_demuxer.*`、`ffmpeg_demuxer_configs.*`、`ffmpeg_demuxer_track_select.cc`、`data_source_io.*`、`url_data_source.*` |
| 解码 | `ffmpeg_video_decoder.*`、`ffmpeg_audio_decoder.*`、`ffmpeg_hw_video_decoder.*`、`ffmpeg_hw_decoder_factory.*`、`ffmpeg_decoder_factories.*` |
| 像素与辅助 | `video_convert.*`、`color_space_bridge.*`、`av_packet_storage.*`、`hw_frame_readback.*`、`interrupt_callback.*`、`sei_timecode.*`、`ffmpeg_text_decoder.*`、`ffmpeg_image_snapshot.*`、`ffmpeg_audio_filter.*`、`ffmpeg_video_filter.*` |

**原来的第四类“编码 / 转码”不在这里**——它是离线转码产品线，已独立为 `media/transcode/`（§4.5）。

**它不在 `platform/` 下，尽管它是 vendor 依赖。** FFmpeg 可移植、在所有宿主上一致，而

`platform/` 装的是“按宿主挑”的代码（§6）。**三条门禁守着这个边界**：C4（libav 头只许出现在

这个目录）、C27（核心 media 不许 include 这个目录里的任何文件）、C25（每个 `.cc` 都有归属）。
`media/transcode/` 是 C27 名单之外的第四个 media 目录，**按设计**可以 include 本目录的文件；
让 G2 继续成立的是“它是独立 target、`avbase_media` 从不链接它”（§4.5），而不是禁止它越界。

### 4.5 `media/transcode/` — 离线转码产品线

**一个目录，一个目标（`avbase_transcode`），一条判据：Phase 5 的离线转码。** 它建立在
`avbase_ffmpeg` 之上——`av_includes.h`、`compat.h`、`video_convert.h` 三个胶水头都来自那里——
同样由 `AVBASE_ENABLE_FFMPEG` 门控。

| 类别 | 文件 |
|---|---|
| 编码器 | `ffmpeg_video_encoder.*`、`ffmpeg_audio_encoder.*`、`video_encoder_factory.*` |
| 封装写端 | `ffmpeg_encode_muxer.*`、`ffmpeg_remuxer.*` |
| 转码作业 | `ffmpeg_transcode_job.*`、`ffmpeg_transcode_job_async.cc`、`ffmpeg_transcode_streams.*`、`ffmpeg_transcode_audio.cc`、`ffmpeg_concat_job.*` |

**为什么值得单独成 target。** 这十个 `.cc` 在 `media/ffmpeg/` 之外共 13 条 `include`，**全部来自
测试**（六个 unittest）。唯一看起来像生产消费者的 `player` 截图走的是
`media/ffmpeg/ffmpeg_image_snapshot.*`——那是“抓一帧”，不属于这一类。把它们留在
`avbase_ffmpeg` 里，等于每个播放构建都背着编码器与封装写端；独立之后，转码的调用方显式链接
`avbase::transcode` 即可。它**刻意不进 `avbase::avbase` 聚合**，理由相同。

**它是唯一对 C5 有影响的目录。** `video_encoder_factory.{h,cc}` 在
`CreateVideoEncoderFactories()` 里用 `#if defined(__APPLE__) / __linux__` 挑 VideoToolbox /
VAAPI / NVENC。解码侧的兄弟（`ffmpeg_hw_decoder_factory.h`）早就做对了：spec 放
`platform/hwaccel/*_hw_spec.h`，由 `player/video_decoder_defaults.cc` 组装列表——**player 才是
注入点**（§6 规则 1）。编码侧还没改，所以门禁给的是**文件级**豁免（`ENCODER_SPEC_FILES`）
而非目录级：C5 仍然守着 `media/transcode/` 其余 16 个文件。待办记在 docs/12 §5。

## 6. `platform/` — 平台后端

**这一节装的是"被宿主选中"的代码。** 一个可移植的第三方库不是平台后端，即使它是

外部依赖：FFmpeg 在 macOS / Windows / Linux 上行为一致，它属于 `media/ffmpeg/`（见 §4.4），

不在这里。判据不是"是不是 vendor"，而是"**是不是按宿主挑的**"。

| 目录 | 内容 | 依赖 |
|---|---|---|
| `platform/sdl2/` | `sdl2_video_renderer_sink` / `sdl2_audio_renderer_sink` / `sdl2_window` / `sdl2_backend` | SDL2 |
| `platform/hwaccel/` | `d3d11_hw_spec.h` / `vaapi_hw_spec.h` / `videotoolbox_hw_spec.h`——三个后端各一个 spec 函数，喂给同一个参数化工厂 | FFmpeg hwaccel |
| `platform/linux/`（M12 计划） | `gl_video_renderer_sink`（OpenGL 3.3）/ `egl_context` / `glx_context` / `wayland_surface` / `x11_surface` / `alsa_audio_sink` / `pulse_audio_sink` / `pipewire_audio_sink` / `dmabuf_video_frame` / `present_extension` / `linux_backend` | GL / EGL / X11 / Wayland / ALSA / Pulse（全部 dlopen 可选） |
| `platform/android/`（预留） | MediaCodec / AAudio / OpenSL / ANativeWindow / JNI | NDK |
| `platform/ios/`（预留） | VideoToolbox / AudioUnit / Metal | iOS SDK |

**`platform/null/` 没有建，也不是漏建**：`NullVideoSink` / `NullAudioSink` 留在

`media/filters/`，理由写在 `media/filters/null_video_sink.h` 的头部——headless 路径属于框架

而非平台（Chromium 的 `media/video/null_video_sink.h` 同样在 `media/` 里），且"零配置可播"

（docs/10 规则 E1）要求没有任何窗口系统的机器上也能端到端跑起来。平台后端在有真实

surface 时才通过 `Deps` 提供自己的 sink。

**关键规则**：
1. `media/` **不得** include `platform/`——由门禁 **C26** 强制执行。在 FFmpeg 代码迁出
   `media/ffmpeg/` 之前这条只是愿望：`media/filters/` 里有 19 个文件直接 include
   `platform/...` 而无任何门禁拦得住（C5 查的是 `SDL2/` `X11/` `GL/` 这类第三方平台头，
   不查自家 `platform/` 路径）。`player/` 那一半不做检查是**故意**的：player 正是注入点，
   它是唯一有权指名某个后端的层（`video_decoder_defaults.cc` 就是这么取 hwaccel spec 的）。
2. 平台后端用 `dlopen` + 弱符号做**运行时可选**（如没装 PulseAudio 就自动回落 ALSA），避免硬链接依赖导致 SDK 难以分发。
3. `media/ffmpeg/compat.h` 是全项目唯一允许出现 `#if LIBAV*_VERSION_*` 的文件（check_invariants C8）。

详见 [09 Linux 平台实现方案](09-Linux平台实现方案.md)。

## 9. 关键设计决策（v2 更新）

### D2 · FFmpeg 类型不出现在 `media/base/`

`media::DecoderBuffer` / `VideoFrame` 用 `StorageType` 枚举 + type-erased 存储，对齐 Chromium：

```cpp
// media/base/video_frame.h
class VideoFrame : public base::RefCountedThreadSafe<VideoFrame> {
 public:
  enum class StorageType {
    kStorageOwned,        // CPU 内存，planes() 可读
    kStorageShmem,        // 共享内存（跨进程预留）
    kStorageDmaBufs,      // Linux dmabuf，零拷贝送 GL
    kStorageGpuMemoryBuffer,
    kStorageOpaque,       // 平台私有句柄（MediaCodec Surface / CVPixelBuffer）
    kStorageWrappedSoftware,
  };
  StorageType storage_type() const { return storage_type_; }
  // kStorageOwned / kStorageDmaBufs 时有效，其余返回空 span
  std::span<const uint8_t> visible_data(VideoFrame::Plane plane) const;
  ...
};
```

`kStorageOpaque` 就是解决 MediaCodec/VideoToolbox 输出无 CPU 像素的正确方式（Chromium 也是这么做的），比 ijkplayer 的 `SDL_VoutOverlay` 第二套 vtable 干净得多。

### D3 · 解复用线程模型（与 Chromium 的**有意偏离**）

Chromium 的 `FFmpegDemuxer` 跑在 media sequence 上，因为它的数据源（`BufferedDataSource` / `MultiBufferDataSource`）是**真异步**的，`av_read_frame` 不会阻塞（数据已在内存里，或 IO 在别的 sequence 上完成后回调）。

avbase 首期直接用 FFmpeg 的 `avformat_open_input` + 网络 protocol，`av_read_frame` **会阻塞**。如果把它放在 media sequence 上，`Flush()` / `Reset()` 就会被阻塞住，seek 响应变差。

**方案**（首期）：
- `FFmpegDemuxer` 拥有一个专用 `base::Thread`（名 `avbase-demux`）跑阻塞读循环
- 控制操作（`Initialize` / `Flush` / `Reset` / `MarkEndOfStream`）在调用方 sequence 上，通过**原子标志 + FFmpeg `interrupt_callback`** 与读循环通信
- 读到的包通过 `DemuxerStream::ReadCB` **PostTask 回消费者 sequence**（不跨线程直接调）

**方案**（二期，可选）：为本地文件实现基于 `base::File` + `BlockingTaskRunner` 的真异步 `DataSource`，把 `FFmpegDemuxer` 完全搬回 media sequence，达到 Chromium 级别的响应性。

这是需要确认的 **D3**。

### D4 · 变速用 WSOLA 而非 SoundTouch

ijkplayer 依赖 SoundTouch（GPL/LGPL 双许可，需要额外编译）。Chromium 的 `media::AudioRendererAlgorithm` 是自研的 WSOLA（Waveform Similarity Overlap-Add）实现，Apache/BSD 许可，约 600 行，效果与 SoundTouch 相当。

**建议直接对齐 Chromium 实现**：去掉一个第三方依赖，许可证更干净，且变速行为可与 Chromium 对比验证。

## 10. 扩展点清单（平台接入只需实现这些）

| 必须/可选 | 接口 | 位置 |
|---|---|---|
| 必须 | `media::VideoRendererSink` | `media/base/video_renderer_sink.h` |
