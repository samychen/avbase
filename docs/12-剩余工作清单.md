## 3. 已修关键缺陷（闭环记录）

- **关闭竞态**：`StopSync` 等队列排空而非管线停稳，~50% 播放退出路径
  踩 `~PipelineImpl` CHECK；改等 `!IsRunning()`，崩溃 14/29→0/35。
- **VOD 完成链死锁**：`VideoRendererImpl::Render` 仅在 present 后 re-arm 解码泵，
  fps-cap 丢帧时泵饿死；修 re-arm 条件（present 或 drop 都 re-arm）+ 去 `MaybeDeliver` 的
  `!end_of_stream_` 门禁；`media_unittests` 393/393。
- **解码器丢包**：`DecoderStream` 被 watermark 掐断的批次尾巴永久丢失；批次未
  消费完则 return。
- **corpus 三崩溃**：采样格式/声道布局/流量失败三类 `params.is_valid()` 进入方式；
  `AudioParameters` 显式携声道数 + 丢弃不可用音频流。
- **EOF 后 seek 永不回调**：`DemuxLoop` 在 `AVERROR_EOF` 处 break，任务结束；
  而 `StartPlayingFrom` 只发布请求 + signal、不重启循环 → 播到结尾再 seek 时无人消费请求，
  回调被永久扣住，调用方等自身超时。症状易误判为死锁：3s 素材实测 3/120 挂起，`sample`
  显示两线程都空闲在 `TaskQueue::Run()`（不是互等，是没人做这件事）。修法：循环仍在 EOF
  结束（驻留会饿死排在后面的 `Flush`），由 `StartPlayingFrom` 重挂，所有权规则是「谁把
  `LoopState` 从 `kGone` 改 `kRunning` 谁 `PostTask`」；`AVERROR_EXIT` 不再当致命错。
  确定性红测 `SeekAfterEndOfStreamIsAnsweredAndResumesReads`（修前 5/5 红、禁用重挂 3/3 红）。
  握手细节见 [04](04-线程模型与数据流.md) §2.1「EOF 与 seek 的握手」。
- **暂停中 seek 画面跑飞**：`StartPlayingFrom` 无条件 `paused_ = false`，
  于是暂停中 seek 后画面脱离暂停的时钟自己往前跑——实测 4.0 s seek 后 800 ms 已在 5.07 s，
  而音频静音、日志全绿。修法：`StartPlayingFrom` 只接管代际与重启解码，**不许**清
  `paused_`；sink 的播放状态收敛到唯一派发点 `VideoRendererImpl::SetPaused`，「该不该
  拉帧」的规则抽到 `media/base/video_sink_gate.h`（`Flush()` 的语义含「下一帧是另一幅
  画」，暂停中也放行一次）。见 [05](05-迁移对照表.md) Δ23。
- **丢帧计数变成刷新率的函数**：`ClassifyFrameOutcome` 把「这一拍没有帧」
  也记成 drop，于是 `frames_dropped` 在 30 fps / 60 Hz 下稳定 30/s、暂停时 60/s，既不是
  丢帧也不是用户能感知的事。新增 `FrameOutcome::kNone`（三个计数都不动），口径对齐
  ffplay：只有「帧到手、却被丢弃」才计数（`frame_drops_late` 与 `frame_queue_next()`
  同两行；队列空与暂停走 `goto display`，不碰计数器）。见 [05](05-迁移对照表.md) Δ24。
- **fps-cap 判错了对象**：`max-fps`（默认 31，ijk 原值；接线
  后才生效）原先拿「距上次呈现的**墙钟**时间」判断一帧是否来得太早。墙钟答不了这个
  问题——sink 按自己的节奏轮询（16 ms），一批帧可能全落在两次轮询之间，于是每一帧都
  拿同一个「轮询间隔」当帧间隔：30 fps 源实测读到 18 ms < 32.2 ms 上限，162 帧里
  151 帧因「太早」被丢，**画面 1 fps**，而 `frames_dropped_late` 全程为 0（它只记
  「晚了」，不记「早了」）。改问两帧的**时间戳**间隔（`next_timestamp -
  last_timestamp`），且只对配速判定为 due 的帧生效。见 [05](05-迁移对照表.md) Δ27。
- **丢帧原因说不出来**：compositor 早按四个原因分别计数（late /
  fps-cap / stale-serial / accurate-seek），但只有 fps 一路报到宿主，于是宿主看着
  `frames_dropped` 涨却分不清「管线慢」与「策略在稀释输出」——这两者要相反的处理。
  `frames_dropped_late` 更糟：它在 `PlaybackStats` 上有字段、也进了 JSON，却**没有任何
  地方赋值**，恒零的计数会被当成证据读。四个原因现已全部经 `PipelineStatistics` 上报。
- **起播后画面定格几秒**：症状是「有声音、画面停在第一帧、然后突然
  正常播」，看起来像配速公式的问题，其实是**音频设备的打开时机**。音频时钟只在设备
  第一次回调送出样本时起锚，而设备原先在 `StartPlayingFrom()` 才打开——与视频首帧
  同一时刻，但视频 22 ms 后就按帧率推进，设备却要 404 ms 才就绪（`SDL_InitSubSystem`
  129 ms + `SDL_OpenAudioDevice` 275 ms，本机实测）。这 400 ms 整段变成「视频领先主
  时钟」，被 `ComputeTargetDelay()` 一次性吸收成一次 370 ms 的冻结；设备启动慢的机器
  上就是几秒。改在准备阶段打开（设备 paused，不出声），由 `OnDecoderInitialized()` 成功
  后调用：修后错位 400 ms → 9 ms。诊断手法值得复用——`Render()` 的 hold/empty 两个出口
  各打一个探针（看 `pending_frames_.size()` 与 `wait_ms`），一步就能分清「队列空」还是
  「配速在等」；`AVBASE_QT_TRACE=<ms>` 打印屏上那一帧自己的 pts，用来分辨「计数在涨」
  与「画面在动」。见 [05](05-迁移对照表.md) Δ26。
- **时间线面板是假数据**：`apps/player_qt` 启动时调 `timeline.loadDemo()`
  铺六条硬编码 clip（intro.mp4 / b-roll.mp4 / …），于是不管打开什么文件，下面永远是一条
  属于**不存在的工程**的时间线；更糟的是 `duration()` 从这些 clip 推导（最后一条到
  18 秒），播放头被 clamp 到 18 秒——30 秒的文件播到 18 秒后**播放头再也不动**，控制栏
  却照常走。改法：`TimelineModel` 只认 `MediaInfo`，按真实媒体铺 V1/A1 各一条；没有时长
  的源（直播）清空面板而不是编一个长度；同时删掉兑现不了的编辑入口（`+ Clip` / `− Clip` /
  clip 拖拽——背后没有混音器，能拖的 clip 是接了空气的控件）。判据是新增的
  `tests/unit/qt/`（8 条，三条突变验过）。这一轮的教训不是 UI 细节而是**占位数据的危害**：
  空面板一眼看出没做完，假的会被当成真的读。
