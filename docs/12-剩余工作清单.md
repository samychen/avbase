### 2.4 验收发现的缺陷(未修,如实登记)

`~PipelineImpl` 的 `DCHECK(state_ == kNew || kStopped || kError)` 最初表现为**间歇性**
失败(此处 HLS 播到 kCompleted 后析构时状态仍是 `kReady`,随后连续三次全绿)。
**根因已定位并修复(第二十三轮末)**——是 corpus 度量把它从"偶见"变成 14/29 之后才值得动手。

**根因**:`PlayerImpl::StopSync` 等的是**队列排空**,不是**管线停稳**。它往 media 序列投
一个 barrier 任务并等它执行,读起来像"等到 Stop 被处理完";但 `DoStop()` 是**异步完成**的
——置 kStopping、把 Flush 交给渲染器、然后**返回**,真正到达 kStopped 的 `FinishStop()` 要
等 flush 完成并回跳 S1。于是 barrier 在状态仍是 kStopping 时就响了,`StopSync` 返回,
`~PipelineImpl` 拿着一条尚未拆完的管线跑析构。

**修法**:改等 `!pipeline_->IsRunning()`——该谓词的定义就是"可以安全析构"
(`pipeline_impl.cc` 的 `IsRunning()` 注释明确写了 kStopping **不算**安全),有界轮询,
与测试侧 teardown 同一做法。Δ15 的 detach 语义保留:超时仍记日志并返回,但日志现在会
**说明析构将面对活的状态**,而非静默进入竞态。

**实测(同一 corpus,修复前后)**:

| 指标 | 修复前 | 修复后(第二十四轮) |
|---|---|---|
| 崩溃/CHECK | **14 / 29** | **0 / 35** |
| 打开成功率 | 15/29 (51.7%) | **35/35 (100%)** |
| seek 成功率 | 12/29 (41.4%) | **32/35 (91.4%)** |
| 生成失败 | 静默消失 | **点名,并区分 SKIPPED** |

剩余 3 个 seek 失败与 3 个非零退出**全部是故意损坏的样本**(`damage_broken_header` /
`damage_half` / `damage_empty`),它们走 `prepare failed: InvalidState` 优雅降级,**不崩溃**
——这是期望行为,不是缺陷。

打开成功率 51.7% → 100% 说明那 14 次**根本不是"文件解不开"**:每次都播放成功、打印了
`completed at media time`,然后在退出路径上踩断言——是我的度量脚本把 CHECK 记成了
"打不开",于是一个**拆除(teardown)缺陷被当成解码问题报了一天**。release 构建 DCHECK 被
编掉,所以这个竞态此前一直是静默的。

**教训**:这条缺陷先被协议验收撞到 1 次(记为"间歇性"),再被 corpus 度量变成 14/29。
**文件类测试与任何单测都碰不到它——因为 bug 不在播放,在离开。**

### 4.3 corpus 度量 —— 把上面那个竞态的量级测出来了(第二十三轮)

`tools/check_corpus.py` 运行时生成维度矩阵(codec / 容器 / 分辨率 / 帧率场序 /
多轨 / 纯音频 / 损坏)并度量 docs/12 §12 的四个指标。**29 个样本里 14 个触发同一个
关闭竞态**——即 2.4 里记为"间歇性"的那个 `~PipelineImpl` CHECK。

量级必须写清楚,因为它改变了这一项的性质:

| 指标 | 实测(修复前) |
|---|---|
| 打开成功率 | 15/29 (51.7%) |
| 首帧平均 | 1.021 s(22 个样本有首帧) |
| seek 成功率 | 12/29 (41.4%) |
| 崩溃/CHECK | **14** |

**14 次全部是同一个缺陷**,且都发生在**播放成功之后**(`completed at media time`
先打印,再触发 CHECK)。所以这不是"某些文件解不开",而是**约一半的正常播放在退出路径
上踩断言**。在 release 构建里 DCHECK 是空的,于是它不响——但它意味着关闭路径的时序
本来就是不成立的,只是没被看见。

**下一位的修复优先级应该高于本清单里的多数条目**:一个每次播放结束都可能触发的关闭
竞态,比 corpus 数量或覆盖率更影响"能不能放心播完一个文件"。

### 4.3 "所有崩溃" —— 全量清扫与第二十四个真缺陷(第二十四轮)

上面那 14 次被修掉之后,又做了一次**跨预设的全量清扫**,结论是崩溃类问题**已清零**,
并且顺带挖出一个此前被 DISABLED 掩盖的崩溃。清扫范围与实测结果:

| 面 | 实测 | 崩溃 |
|---|---|---|
| corpus 播放(35 样本 × 打开/首帧/seek) | 打开 100% | **0** |
| `ffmpeg` 预设 5 个二进制 | 481 用例全过 | **0** |
| `asan` + `ubsan` 预设 | 476 用例全过 | **0** |
| `tsan` 预设 | 425 用例全过 | **0** |
| fuzz standalone(种子变异) | 325 个输入 | **0** |
| CLI 坏参数(空/不存在/目录/`/dev/null`) | 各工具均优雅报错 | **0** |

**新发现的崩溃在 `LiveCueExpiryTest::TearDown`**:它从头到尾**没调用过 `Stop()`**,
却在那儿轮询 `!IsRunning()`。`Stop()` 是异步的——它把 `DoStop` 投递到 media 序列,
由该序列冲刷渲染器后才走到 kStopped——所以析构函数替不了它:等 `~PipelineImpl` 跑起来时,
那条本该执行拆除的序列自身已经在离场。于是没人推动状态,管线停在 kReady 上被析构,
撞上 `~PipelineImpl` 里的 DCHECK。**这个崩溃此前一直被"用例已禁用"挡着看不见。**

**同一处还藏着一个反向断言**,值得单独记一笔:循环写的是 `EXPECT_LT(cue.pts, 1s)`,
要求**幸存**的 cue 携带**低**时间戳,而策略丢掉的正是低的那批。于是它在**证明策略
有效的那些 cue 上失败**,却会在**证明策略失效的那个 cue 上通过**。已改为 `EXPECT_GE`。
这类反向断言之所以能活过评审,是因为**它读起来仍然像一句断言**——只有把注释、
失败文案和断言方向三者放在一起对读才会露馅。

### 4.6 覆盖率门禁接入 CI —— 用棘轮(ratchet)而不是改小数字(第二十四轮)

旧 CI 是 `lcov --summary cov.info || true`,**构造上不可能失败**。现在换成真门禁,
但**不是**把 docs/07 §12 的阈值改小——那只是把差距藏起来。做法:

**双模式**
* 默认(absolute):spec 的可执行形态,不达标就红。**这是目标状态**。
* `--ratchet`:把**实测基线当地板**——覆盖率只能涨不能跌,同时打印每个模块距 spec
  还差多少。**这是过渡态**,哪个模块达到 spec 数字,棘轮对它即冗余,应切回绝对模式。

之所以不是"把数字调小":spec 阈值在棘轮模式下**仍然每次打印**,在绝对模式下
**仍然强制执行**,差距始终可见,不会被常态化抹平。

**实测基线(coverage 预设,全量 481 用例跑完,已提交为 `coverage_baseline.json`)**

| 模块 | line | branch | spec(line/branch) |
|---|---|---|---|
| `base/` | 93.5% | 67.1% | 95 / 90 |
| `media/base/` | 67.7% | 62.3% | 95 / 90 |
| `media/filters/` | 75.7% | 56.3% | 90 / 85 |
| `media/filters/ffmpeg_` | 72.9% | 52.3% | 70 / — |
| `player/` | 88.5% | 70.0% | 90 / 85 |
| **core overall** | **75.5%** | **58.8%** | **85 / 80** |

差距最大的两块是 `media/base/`(-27.3pp)和 `media/filters/`(-14.3pp);分支覆盖率
整体偏低(58.8% vs 80%),基本都落在同步与错误路径上。**补齐方式是写测试,
不是改阈值。**

**口径一致性**:所有平台统一由 `tools/gcov_to_lcov.py` 产出 tracefile,**不**在 Linux 上
改用 `lcov`。因为棘轮要跟基线逐模块比较,而 lcov 与 gcov 在分支口径和路径写法上的差异
足以凭空造出"回退"。CI 里因此不再安装 lcov。

**已知边界**:地板是"coverage 预设 + 当前系统编译器"下测得的。更换工具链会让数字整体
移动,那时应**显式重录基线**,而不是让门禁静默失守。

### 附带发现:构建树里的孤儿目标(本地卫生问题)

清扫时手动跑了 `build/*/bin` 下的每个可执行文件,其中 `integration_tests` 报了 1 个
失败。追下去发现它**不属于这个仓库**:

* `tests/integration/` **不在磁盘上**,`tests/CMakeLists.txt` 也未引用它;
* `git log --all --diff-filter=A -- tests/integration/*` **为空** —— 它从未被提交过;
* 但 `build/ffmpeg` 的 CMake 缓存里还留着 10-01 的 `.o` 与二进制,且 `cmake --build`
  不会重新链接它(时间戳始终是 10-01)。

也就是说:这个二进制测的是**已经不存在的代码**,它的结果对当前仓库没有意义;它在本机
CPU 争用时还会超时(同一个二进制,空闲时 3/3 通过,并发时 2/3)。ctest 不会跑到它
(`CTestTestfile.cmake` 里没有它),CI 是全新 checkout 也不会有它。**只是本地构建树脏了**,
扫二进制时要排除它,否则会追着幽灵找一天。
