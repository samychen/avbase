# 04 · 线程模型与数据流（Chromium Task Runner / Sequence 模型）

> 上一篇：[03 核心类与接口设计](03-核心类与接口设计.md) ｜ 下一篇：[05 迁移对照表](05-迁移对照表.md)

音视频播放器的 bug 90% 出在线程边界上。本篇把 avbase 的**控制面**（Chromium 风格：task runner + sequence + `WeakPtr`）与**数据面**（有界队列，ffplay 风格）的分工、每个 sequence 的职责与允许的操作、以及全部关键时序写死。

---

## 1. 模型选择：为什么是"混合"

Chromium 是纯 task-runner 模型：几乎没有阻塞调用，所有 IO 异步。它能做到这点是因为数据源（`MultiBufferDataSource` / `BufferedDataSource`）是真异步的 —— `av_read_frame` 只在内存里找数据，从不阻塞。

avbase 首期直接用 FFmpeg 的 protocol 层（`avformat_open_input("https://...")`），`av_read_frame` **会阻塞在网络 IO 上**。如果把解复用放在 media sequence 上，一次网络抖动就会让 `Flush()` / `Seek()` / `Stop()` 全部排队等待 —— 这正是 ijkplayer "seek 卡顿" 和 "release 卡死" 的根源之一。

**决策（D3）**：

| 面 | 模型 | 理由 |
|---|---|---|
| **控制面**（生命周期、状态机、事件、配置、seek 请求、flush） | **Chromium task runner + sequence**，全程非阻塞，`PostTask` + `WeakPtr` | 保证 API 永不卡死；对象销毁后残留任务自动失效 |
| **数据面**（packet 流、frame 流、PCM 流） | **有界队列**（`DecoderBufferQueue` / `VideoFrameQueue` / `AudioRendererAlgorithm` 内部队列）+ 专用线程 | 媒体数据是高吞吐、天然背压的流；队列表达背压比"回调地狱"清晰且开销更低 |
| **解复用** | **专用 `base::Thread`** 跑阻塞循环 + FFmpeg `interrupt_callback` | 见上；这是与 Chromium 的**有意偏离**，二期可用 `base::File` 异步 IO 消除 |
| **音频输出** | **sink 自有的音频线程**，pull 回调 | 对齐 Chromium `AudioOutputDevice`；延迟最低 |
| **视频送显** | **sink 自有的 render sequence**（vsync 驱动或定时器驱动） | 对齐 Chromium `VideoRendererSink::RenderCallback` |

**跨面通信规则**（强制，CI 检查）：
- 控制面 → 数据面：只通过原子标志、`base::WaitableEvent`、队列的 `Abort()/Flush()`。
- 数据面 → 控制面：只通过 `PostTask(BindOnce(&Foo::Bar, weak_ptr, ...))`。**绝不允许**数据面线程直接调用控制面对象的方法。
- 任何跨 sequence 的裸指针传递必须包在 `base::Unretained()` 里并有注释说明生命周期保证（clang-tidy `bugprone-unchecked-optional-access` 类的自定义检查）。

## 2. Sequence / 线程清单

| # | 名称 | 类型 | 拥有者 | 职责 | 允许阻塞？ |
|---|---|---|---|---|---|
| S0 | 调用方线程 | 任意 | 用户 | 调 `Player` 的方法 | — |
| S1 | `avbase-media` | `base::Thread` + `SequencedTaskRunner` | `Pipeline` | 管线编排、状态机、`RendererImpl`、`VideoFrameCompositor` 的写侧、`AvSyncController` 的写侧 | ❌ 严格禁止 |
| S2 | `avbase-demux` | `base::Thread`（**跑阻塞循环，不用 message pump 的任务队列**） | `FFmpegDemuxer` | `av_read_frame` 阻塞读、路由到各 `DemuxerStream` 队列、背压、物理 seek | ✅ 只允许阻塞在 IO |
| S3 | `avbase-video` | `base::Thread` + `SequencedTaskRunner` | `VideoRendererImpl` | `DecoderStream<VideoDecoder>` 泵、帧队列水位、`VideoFrameCompositor` 的部分读 | ❌ |
| S4 | `avbase-audio` | `base::Thread` + `SequencedTaskRunner` | `AudioRendererImpl` | `DecoderStream<AudioDecoder>` 泵、`AudioRendererAlgorithm` 填充、WSOLA 变速、音频时钟推进 | ❌ |
| S5 | `avbase-text`（可选） | `base::Thread` | `TextRenderer` | 字幕解码 | ❌ |
| S6 | sink render sequence | 由 `VideoRendererSink` 实现拥有 | 平台后端 | 周期性调 `RenderCallback::Render(deadline_min, deadline_max, ...)`，上传纹理，present | ❌（SDL2 后端在窗口事件循环里） |
| S7 | sink audio thread | 由 `AudioRendererSink` 实现拥有 | 平台后端（ALSA/Pulse/SDL2） | 周期性调 `RenderCallback::Render(delay, delay_ts, glitch, AudioBus*)` | ❌ **预算 < 100µs** |
| S8 | `avbase-event` | `base::Thread` | `EventHub` | 单线程 FIFO 派发用户事件回调 | ❌ |
| S9 | `base::ThreadPool` | 线程池 | 全局 | 短任务：日志落盘、统计聚合、诊断 dump、`StopSync` 的 join | ✅ 允许阻塞任务（显式 `MayBlock()`） |

**总计 6–8 个专用线程**，与 ijkplayer 的 6 个（`read_thread` / `video_thread` / `audio_thread` / `subtitle_thread` / `video_refresh_thread` / `message_loop`）数量相当，但每个的职责、边界、允许的操作都被明确约束并用 `SEQUENCE_CHECKER` 在运行时断言。

### 2.1 S2 `avbase-demux` 的特殊性（D3 的落地）

S2 是**唯一一个不跑标准 message pump 任务循环**的线程。它的主体是一个长驻的阻塞循环：

```cpp
// media/filters/ffmpeg_demuxer.cc
void FFmpegDemuxer::DemuxLoop() {
  // Runs on S2. The only sequence allowed to block on IO.
  DCHECK(demux_thread_->GetThreadRef() == base::PlatformThread::CurrentRef());
  while (!stop_flag_.IsSet()) {
    if (seek_request_.Exchange(nullptr)) { /* 物理 seek，见 §5.3 */ }

    if (buffer_controller_.ShouldPauseReading(GetBufferSnapshot())) {
      // 水位够了。等待消费者唤醒（不忙轮询）。
      resume_event_.TimedWait(base::Milliseconds(10));
      continue;
    }

    AVPacket* pkt = nullptr;
    int ret = av_read_frame(format_ctx_.get(), pkt);   // ★阻塞点
    if (ret == AVERROR_EOF) { MarkEndOfStream(); break; }
    if (ret < 0) { PostErrorToMediaSequence(ret); break; }

    auto buffer = MakeDecoderBuffer(pkt, current_serial_.Get());
    RouteToStream(std::move(buffer));       // 各 DemuxerStream 的内部队列
  }
}
```

`av_read_frame` 的可中断性靠 FFmpeg 的 `AVIOInterruptCB`：

```cpp
// media/ffmpeg/ffmpeg_source.cc
static int InterruptCallback(void* opaque) {
  auto* self = static_cast<FFmpegSource*>(opaque);
  // 返回 1 让 av_read_frame 立刻返回 AVERROR_EXIT
  return self->interrupt_flag().IsSet() ? 1 : 0;
}
```

`interrupt_flag_` 由以下三处置位（**只有三处，全部有注释和单测**）：`Stop()`、`StopSync()`、`~FFmpegDemuxer()`。ijkplayer 的 `abort_request` 需要在 5+ 处 signal `continue_read_thread`，漏一处就永久卡住 —— 这里从设计上消除了该类 bug。

**控制操作如何与 S2 通信**：

| 控制操作 | 机制 | 延迟 |
|---|---|---|
| `Flush()` | 置 `flush_flag_`（`base::AtomicFlag`）+ 设 `interrupt_flag_` 打断当前 `av_read_frame` + `resume_event_.Signal()` | < 10ms（网络超时下可能到 `rw_timeout`） |
| `StartPlayingFrom(t)` | 把 `SeekRequest` 写入 `std::atomic<SeekRequest*>` 交换槽 + signal | 同上 |
| `Stop()` | 置 `stop_flag_` + `interrupt_flag_` + signal，然后 `WaitableEvent::TimedWait` | ≤ `shutdown_timeout` |
| 查询（`GetBufferedTime` 等） | 原子变量读，不进 S2 | < 1µs |

**为什么这是可接受的偏离**：
1. `Flush`/`Seek` 的最坏延迟受 FFmpeg 的 `rw_timeout` 约束，而 ijkplayer 也是同样的机制，行为不会更差。
2. S2 只做一件事，阻塞在 IO 上不影响任何其他 sequence 的响应性 —— S1/S3/S4 仍然可以立即处理 `Pause()`、`SetVolume()`、`GetMediaTime()`。
3. 二期（M12+）把本地文件的 `DataSource` 改成 `base::File` + `BlockingTaskRunner` 异步读，`FFmpegDemuxer` 就能搬回 S1，达到 Chromium 级别的响应性，而**调用方代码一行都不用改**（`DataSource` 已经是接口）。

## 3. 锁与无锁边界

| 数据 | 保护 | 写侧 | 读侧 | 备注 |
|---|---|---|---|---|
| `DecoderBufferQueue` 内部 | `base::Lock` + `ConditionVariable` | S2 | S3/S4 | 每包一次，可忽略 |
| `VideoFrameQueue` 内部 | `base::Lock` + `ConditionVariable` | S3 | S3/S6 | — |
| `VideoFrameCompositor::pending_frames_` 等 | `base::Lock`（细粒度，见 03 §8.1） | S1/S3 | S6 | ★唯一跨 3 个 sequence 的共享状态，字段被刻意压到最少 |
| `AvSyncController` 时钟 | **seqlock**（`std::atomic<uint32_t> seq_` + atomic 字段） | S4（audio）/ S3（video） | 任意 | @hot，每帧多次读 |
| `AudioRendererAlgorithm` 内部队列 | `base::Lock` | S4 | S7 | S7 侧只做 `FillBuffer`，锁持有时间 < 5µs |
| `PlayerState` | `std::atomic<PlayerState>` + 迁移时 `base::Lock` | S1 | 任意 | 读无锁 |
| `EventHub` 订阅表 | `base::Lock` | S0 | S8 | 订阅极少变 |
| `EventHub` 事件队列 | `base::Lock` + `ConditionVariable` | 全部 | S8 | 有界，溢出策略见 §3.2 |
| `PlayerConfig`（运行时更新） | copy-on-write：`std::atomic<const PlayerConfig*>` + 引用计数 | S0 | 全部 | 读侧拿快照，无锁 |
| `SeekController` | `base::Lock` | S0/S1 | S1/S3/S4 | `IsAccurateSeekDropTarget()` 用原子快照，避免 @hot 加锁 |
| `BufferController` | 原子计数器 + `base::Lock`（仅状态迁移） | S2/S1 | S1 | — |
| `VideoRendererSink` 内部 | sink 自管 | S6/S0(`SetOutputTarget`) | — | 契约测试覆盖并发 |
| `PlaybackStats` | 各组件 `std::atomic` 计数器 | 全部 | S0 | 读快照，允许轻微不一致 |

### 3.1 加锁顺序（全局唯一，`LockOrderChecker` 在 debug 构建断言）

```
Player::Impl::lock_  >  StateMachine::lock_  >  SeekController::lock_
  >  BufferController::lock_  >  EventHub::lock_
  >  VideoFrameCompositor::lock_  >  DecoderBufferQueue::lock_  >  VideoFrameQueue::lock_
  >  AudioRendererAlgorithm::lock_

AudioRendererSink::RenderCallback::Render() 期间只允许持有 AudioRendererAlgorithm::lock_，
且禁止在其中获取上面任何一把锁。
```

**违反即 assert**。这条规则由 `base/test/lock_order_checker.h`（debug-only）在每次 `AutoLock` 构造时校验获取栈。

### 3.2 事件队列溢出策略（避免用户回调慢导致管线卡住）

| 事件类别 | 队列满时 | 理由 |
|---|---|---|
| 关键（`kPrepared` `kError` `kCompleted` `kStateChanged` `kSeekCompleted`） | **阻塞投递方**（带上限 100ms，超时丢弃并 LOG(ERROR)） | 绝不能丢 |
| 常规（`kVideoSizeChanged` `kRotationChanged` `kDecodingStarted` `kTimedText` `kBufferingStarted/Ended`） | 阻塞投递方最多 10ms，超时丢弃 + 计数 | 丢一条可容忍 |
| 高频（`kBufferingProgress` `kBuffered*Update` `kStats`） | **立即丢弃最旧的同类事件**（合并） | 只需最新值 |

`PlaybackStats::events_dropped_by_overflow` 计数暴露给用户，避免"静默丢事件"。

## 4. `serial` 世代号语义（继承自 ffplay，必须原样保留）

这是 ijkplayer/ffplay 里最精巧的设计，原版**完全没有注释**。这里正式文档化：

```
持有者：DecoderBufferQueue（每流一个）、VideoFrameQueue（每流一个）、
        每个 DecoderBuffer、每个 VideoFrame、AvSyncController 的每个时钟

R1  seek 发生时，FFmpegDemuxer 递增 current_serial_，并对所有 DemuxerStream
    的内部队列执行 Flush()（清空 + 递增各自 serial）。
R2  此后 S2 读到的每个 DecoderBuffer 都打上新的 serial。
R3  DecoderStream 丢弃 serial < stream->serial() 的过期 buffer，不送解码器。
R4  解码出的 VideoFrame 继承来源 buffer 的 serial。
R5  VideoFrameQueue::Flush() 也递增 serial 并清空。
R6  VideoFrameCompositor::DecideNextFrame() 比较 last_serial 与 next_serial：
    不同时跳过时长计算，直接用 fps 推导 duration，且不做丢帧判断。
R7  AvSyncController 的时钟 serial 必须与帧 serial 匹配，否则该时钟无效，
    主时钟退化到 external。
R8  精确 seek 期间，SeekController 用 target_serial 判断帧是否属于目标世代。
```

**R6 为什么至关重要**：seek 后第一帧与前一帧的 pts 可能相差几十秒。若照常计算 `last_frame_duration`，`ComputeTargetDelay()` 会得出荒谬的等待时间，表现为"seek 后画面卡住数秒"。ijkplayer 靠 `lastvp->serial == nextvp->serial` 判断，逻辑正确但埋在 400 行 `video_refresh()` 里、零注释、极易在重构中丢失。

avbase 的三重保护：
1. R1–R8 写进本文档与 `decoder_buffer.h` 的类注释。
2. `DecoderBufferQueue::Flush()` / `VideoFrameQueue::Flush()` / `VideoFrameCompositor::DecideNextFrame()` 三处有 `DCHECK` 与 `MEDIA_LOG(DEBUG)`。
3. `VideoFrameCompositorTest.SkipsDurationComputationAcrossSeekSerialChange` 是**回归测试**，永久守护（见 03 §8.1）。

### 4.1 serial 与 flush 的传播链

```
S0  Player::SeekTo(t, mode, cb)
     │  校验状态机 → PostTask 到 S1
     ▼
S1  PlayerImpl::DoSeek(t, mode)
     │  seek_controller_->Request({t, mode, request_id})
     │    → 合并进行中的请求（后者覆盖前者，旧 request_id 的结果不再派发）
     │  pipeline_->Seek(t, OnceClosure)
     ▼
S1  RendererImpl::Flush()  → 并行下发：
     ├─► S3 VideoRendererImpl::Flush(cb)
     │      ├─ DecoderStream::Flush()   // 丢弃 pending decode，decoder_->Reset()
     │      ├─ VideoFrameQueue::Flush() // ++serial，清空
     │      └─ compositor_->Flush()     // 重置 frame_timer / last_duration
     ├─► S4 AudioRendererImpl::Flush(cb)
     │      ├─ DecoderStream::Flush()
     │      ├─ audio_algorithm_->Flush()
     │      └─ sink->Flush()            // ★丢弃硬件缓冲，否则听到 seek 前的声音
     └─► S1 Demuxer::StartPlayingFrom(t)
            │  写 SeekRequest 到原子交换槽 + resume_event_.Signal()
            │  置 interrupt_flag_ 打断当前 av_read_frame
            ▼
S2  DemuxLoop: 取出 SeekRequest
     ├─ av_seek_frame(ic, stream, ts, flags)     // 可能耗时（网络）
     ├─ ++current_serial_
     ├─ 各 DemuxerStream::FlushInternal()        // ++serial，清空队列
     ├─ avcodec_flush_buffers() 由 DecoderStream::Flush 负责，不在此处
     └─ PostTaskAndReplyWithResult → S1: OnDemuxerSeeked(actual_pos)
            ▼
S1  seek_controller_->OnDemuxerSeeked(actual_pos, new_serial)
     │  若 config.seek.accurate → 进入 kAccurateSeekDropping
     │  下发 RendererImpl::StartPlayingFrom(actual_pos)
     ▼
S3/S4  解码并丢弃 pts < target 的帧（shouldDropForAccurateSeek）
     │  直到 pts >= target 或超时（config.seek.accurate_timeout）
     ▼
S1  seek_controller_->Complete()
     ├─ 事件：kAccurateSeekCompleted（若启用）
     ├─ 事件：kSeekCompleted{requested, actual, load_duration, result}
     └─ 运行 S0 传入的 SeekCB（PostTask 到 S8）
```

**与原版的关键差异**：
- 原版 `video_refresh()` 里靠轮询 `is->videoq.serial` 变化来触发 flush，时机不确定。新版由 `Flush()` 显式下发，且每个阶段都有 `SeekPhase` 可观测（`DumpDiagnostics()` 里能看到卡在哪一步）。
- 原版 seek 完成事件不带 `request_id`，快速连续 seek 时用户会收到错配的通知。新版每个 `SeekCompletedPayload` 带 `request_id`，可精确匹配。

## 5. 关键时序

### 5.1 `PrepareAsync()` → `kPrepared`

```
S0                S1 (media)              S2 (demux)          S3 (video)        S8 (event)
 │ PrepareAsync()
 │  state: kInitialized→kPreparing
 │  PostTask(DoPrepare)
 └─ return kOk（非阻塞）
                  │ DoPrepare()
                  │  创建 demuxer / renderer / sinks
                  │  demuxer->Initialize(host, media_runner, io_runner, cb)
                  ├────────────────────► S2 启动 + avformat_open_input()
                  │                       │ EmitStage(kOpenInput)
                  │                       ├──────────────────────────────────► kStageReached
                  │                       │ avformat_find_stream_info()
                  │                       │ EmitStage(kFindStreamInfo)
                  │                       ├──────────────────────────────────► kStageReached
                  │  OnDemuxerInitialized(status)
                  │  选流（StreamSelector）→ media_info_
                  │  EmitEvent(kVideoSizeChanged / kRotationChanged)
                  │  renderer->Initialize(media_resource, client, cb)
                  ├──────────────────────────────────────► S3: DecoderStream::Initialize
                  │                                          DecoderSelector 排序候选
                  │                                          decoder->Initialize(config,...)
                  │                                          EmitStage(kComponentOpen)
                  │                                          EmitEvent(kDecoderOpened)
                  │  sink->Initialize(compositor) + sink->Start()（若 !render_wait_start）
                  │  StartReading() 开始拉包
                  │  BufferController 等待起播水位
                  │  OnPrepared() → state: kPreparing→kPrepared
                  │  EmitEvent(kPrepared{media_info, stages})
                  ├──────────────────────────────────────────────────────────► 用户回调
                  │  若 config.start_on_prepared → PostTask(DoStart)
                  │  state: kPrepared→kStarted
                  ├──────────────────────────────────────────────────────────► kStateChanged
```

**`StageTimings` 的意义**：原版发 `FFP_MSG_OPEN_INPUT`(407) / `FIND_STREAM_INFO`(408) / `COMPONENT_OPEN`(409) / `VIDEO_DECODED_START`(406) / `VIDEO_RENDERING_START`(402) 的真实目的就是首帧耗时分解。新版结构化成一个 `StageTimings` 结构体随 `kPrepared` 一起给出，业务不用自己拼时间戳。

### 5.2 卡顿 → 缓冲 → 恢复

```
S3/S4 消费过快 → DecoderBufferQueue 空且 !eos
   │  DecoderStream::StartReading 的 Read() 回调返回空 → CanDecodeMore()==false
   ▼
S1  RendererImpl 检测到 buffered < 阈值
   ├─ client_->OnBufferingStateChange(kBuffering, memory_usage)
   │     └─► PlayerImpl → BufferController::OnUnderrun()
   │            ├─ state: kStarted→kBuffering
   │            ├─ EmitEvent(kBufferingStarted)
   │            └─ resume_event_.Signal()  // ★唤醒 S2（唯一唤醒点）
   └─ compositor_->SetBufferingBlocked(true)   // S6 的 Render() 返回 kRepeat
   ▼
S2  恢复读包，每包后 BufferController::ShouldPauseReading() 判定
   │  hwm_step: first(100ms) → next(1s) → last(5s)
   │  每次"卡顿→恢复"循环后 hwm_step += 1（原版逻辑，弱网下逐步加大缓冲）
   │  seek 后 hwm_step 重置为 0
   ▼
   达到 active_high_water_mark 且 min_frames 满足
   ├─ client_->OnBufferingStateChange(kHaveEnough, ...)
   │     ├─ state: kBuffering→kStarted
   │     ├─ EmitEvent(kBufferingEnded)
   │     └─ av_sync_controller_->Flush()   // 重置时钟，避免卡顿后时间跳变
   └─ compositor_->SetBufferingBlocked(false)
```

`kBufferingProgress` 事件在缓冲期间每 200ms 派发一次（Δ4，原版 1000ms）。

### 5.3 物理 seek 在 S2 上的执行

```cpp
// media/filters/ffmpeg_demuxer.cc, on S2
void FFmpegDemuxer::HandleSeekRequest(SeekRequest req) {
  // 1. 打断可能正在进行的 IO
  interrupt_flag_.Clear();

  // 2. 计算目标与 flags
  int64_t target_ts = compat::FromTimeDelta(req.target, stream->time_base());
  int flags = req.mode == SeekMode::kAnyFrame ? 0 : AVSEEK_FLAG_BACKWARD;

  // 3. 执行（可能阻塞在网络上，受 rw_timeout 约束）
  int ret = av_seek_frame(format_ctx_.get(), seek_stream_index_, target_ts, flags);
  if (ret < 0) { PostError(kSourceSeekFailed, ret); return; }

  // 4. 递增 serial 并清空各流队列 —— R1
  const int32_t new_serial = current_serial_.Add(1);
  for (auto* stream : streams_) stream->FlushInternal(new_serial);

  // 5. 回到 S1 报告实际落点
  media_task_runner_->PostTask(FROM_HERE,
      base::BindOnce(&RendererImpl::OnDemuxerSeeked, renderer_weak_ptr_,
                     actual_pos, new_serial, req.request_id));
}
```

### 5.4 `Stop()` / 析构

```
S0  Player::Stop()
     ├─ state_machine_.Transition(kStopping)     // 加锁，同步，<10µs
     ├─ PostTask(S1, BindOnce(&PipelineController::Stop, weak))
     ├─ demuxer_->Stop()  → 置 stop_flag_ + interrupt_flag_ + resume_event_.Signal()
     └─ return（★非阻塞，Δ1）

S1  PipelineController::Stop()
     ├─ renderer_->Flush(DoNothing())   // 触发各 sequence 的 flush
     ├─ demuxer_->Stop()
     ├─ sinks: Stop() → Flush()
     ├─ 各 sequence 的 pending task 因 WeakPtr 失效而自动跳过
     └─ PostTask(S0-ish, BindOnce(&PlayerImpl::OnStopped, weak))
           └─ state: kStopping→kStopped；EmitEvent(kStateChanged)

S0  Player::StopSync(timeout)
     └─ base::WaitableEvent ev; PostTask(..., BindOnce(&WaitableEvent::Signal, Unretained(&ev)));
        ev.TimedWait(timeout);
        if (timed out) LOG(FATAL-ish) + 记录 diagnostics + detach

~Player()
     ├─ 若 state != kStopped → StopSync(config.shutdown_timeout /* 默认 500ms */)
     ├─ 超时 → LOG(ERROR) << "shutdown timed out; detaching. diagnostics=" << DumpDiagnostics()
     │          ★宁泄漏一个线程也绝不卡死调用方（Δ15）
     └─ 成员逆序析构
```

### 5.5 播放中切换输出目标（X11 Window / wl_surface）

```
S0  Player::SetVideoSurface(new_display)
     └─ PostTask(S6, BindOnce(&VideoRendererSink::SetOutputTarget, sink_refptr, display))
           ├─ sink 内部加锁，与 Render() 互斥
           ├─ new_display == nullptr → 进入"丢弃模式"：Render() 仍被调用但只做时钟推进，不 present
           └─ 不中断播放、不 seek、不重建解码器
     └─ return（非阻塞）

★特例：解码器直接输出到窗口（MediaCodec→Surface / VAAPI→dmabuf 绑定的 window）
   此时必须重建解码器：
     S1 RendererImpl::RebindHardwareOutput(display)
       ├─ S3 DecoderStream::ReinitializeDecoder(cb)   // 复用 Chromium 的换解码器路径
       ├─ Demuxer::Flush() + ++serial                 // 从最近关键帧重新解
       └─ cb → 恢复播放
   这段逻辑集中在一个函数，对应原版 ijkmp_android_set_surface 的分散流程。
```

## 6. 数据面队列规格

### 6.1 `DecoderBufferQueue`（= 原版 `packet_queue_*`）

```cpp
// media/base/decoder_buffer_queue.h
class MEDIA_EXPORT DecoderBufferQueue {
 public:
  DecoderBufferQueue(std::string name, size_t max_buffers, size_t max_bytes,
                     MediaLog* log);
  ~DecoderBufferQueue();

  // Called on the producer sequence (S2). Blocks when full unless |cb| is
  // provided, in which case completion is posted.
  void Push(scoped_refptr<DecoderBuffer> buffer, base::OnceClosure done_cb);
  bool TryPush(scoped_refptr<DecoderBuffer> buffer);

  // Called on the consumer sequence (S3/S4). |cb| runs when a buffer is
  // available, the queue is aborted, or it is flushed.
  enum class PopStatus { kOk, kEmpty, kFlushed, kAborted, kEndOfStream };
  using PopCB = base::OnceCallback<void(PopStatus,
                                        std::vector<scoped_refptr<DecoderBuffer>>)>;
  void Pop(uint32_t count, PopCB cb);

  void Flush();      // 清空 + ++serial_ + 唤醒所有等待者（R1/R5）
  void Abort();      // 永久中止（析构路径）
  void MarkEndOfStream();

  int32_t serial() const;
  size_t size() const;                     // buffer 数
  size_t bytes() const;
  base::TimeDelta buffered_duration() const;   // 尾 pts - 首 pts
  bool empty() const;
  Stats GetStats() const;

 private:
  mutable base::Lock lock_;
  base::ConditionVariable not_full_;
  base::ConditionVariable not_empty_;
  base::circular_deque<scoped_refptr<DecoderBuffer>> buffers_ GUARDED_BY(lock_);
  size_t bytes_ GUARDED_BY(lock_);
  base::AtomicSequenceNumber serial_;
  bool aborted_ GUARDED_BY(lock_){false};
  bool eos_ GUARDED_BY(lock_){false};
  // ...
};
```

**与 Chromium 的差异说明**：Chromium 的 `DemuxerStream::Read()` 直接是异步的，没有显式队列类（队列藏在 `FFmpegDemuxerStream` 里）。avbase 把队列显式化，因为 S2 是阻塞线程，需要一个明确的"生产者阻塞点"。对外仍暴露 `DemuxerStream::Read(count, ReadCB)` 契约，`FFmpegDemuxerStream::Read` 内部转成 `queue_.Pop(count, cb)`。

### 6.2 `VideoFrameQueue`（= 原版 `pictq`）

保留 v1 的 **`SlotGuard` 两段式写入**设计（这是原版做不到、且能消除一整类 bug 的改进）：

```cpp
class VideoFrameQueue {
 public:
  // 两段式：reserve 一个槽位，commit 时才对外可见。
  // SlotGuard 未 commit 就析构 → 槽位自动归还。
  // 原版 frame_queue_peek_writable() 返回裸指针，任何 early return 都会
  // 永久泄漏一个槽位，最终死锁。
  class SlotGuard {
   public:
    SlotGuard(SlotGuard&&) noexcept;
    SlotGuard& operator=(SlotGuard&&) noexcept;
    SlotGuard(const SlotGuard&) = delete;
    ~SlotGuard();
    void Commit(scoped_refptr<VideoFrame> frame, int32_t serial);
    void Abandon();
    explicit operator bool() const;
  };
  SlotGuard Reserve();                     // 满时阻塞（可 Abort 打断）
  bool TryReserve(SlotGuard* out);

  scoped_refptr<VideoFrame> Pop();
  const VideoFrame* PeekCurrent() const;
  const VideoFrame* PeekNext() const;      // DecideNextFrame 需要 pts 差
  const VideoFrame* PeekLast() const;
  void Flush();
  void MarkEndOfStream();
  int size() const;
  int32_t serial() const;
  bool end_of_stream() const;
};
```

### 6.3 音频 PCM 通道（无锁）

```
S4  AudioRendererImpl
     │  DecoderStream<AudioDecoder> 输出 AudioBuffer
     │  → AudioRendererAlgorithm::EnqueueBuffer()
     │  → 按需 FillBuffer(AudioBus*, frames, playback_rate) 做 WSOLA 变速
     ▼
S7  AudioRendererSink::RenderCallback::Render(delay, delay_ts, glitch, AudioBus* dest)
     │  → AudioRendererImpl::Render(...)
     │       ├─ algorithm_->FillBuffer(dest, dest->frames(), rate_)   // 持锁 <5µs
     │       ├─ dest->Scale(volume_)
     │       ├─ av_sync_controller_->OnAudioFramesConsumed(filled, media_time)
     │       └─ return filled
     ▼
    声卡
```

**S7 的硬约束**（写进 `RenderCallback` 的注释并由契约测试验证）：
- 不阻塞、不分配内存、不获取除 `AudioRendererAlgorithm::lock_` 之外的任何锁
- 不回调 `Player` 的任何方法
- 执行时间 < 100µs（基准测试守护）
- `DCHECK(sink->CurrentThreadIsRenderingThread())`

对比原版：ijkplayer 的 `sdl_audio_callback` 在音频线程里做 `swr_convert`（可能几毫秒）+ 访问 `sampq`（持锁）+ 更新 `is->audio_clock`（无同步）。这是音频爆音的常见来源。

## 7. 竞态清单与防护

| # | 竞态 | 原版表现 | avbase 防护 |
|---|---|---|---|
| R1 | 时钟的非原子 `double pts/drift` 跨线程读写 | TSan data race；撕裂值导致跳帧 | `AvSyncController` seqlock；专项并发单测 |
| R2 | `is->paused` 无 barrier | 暂停后仍渲染几帧 | `VideoFrameCompositor::paused_` 在 `base::Lock` 内 |
| R3 | `seek_req` 与 `seek_pos` 非原子成对写 | 偶发 seek 到错误位置 | `SeekController` 用 `base::Lock` 保护整个 `SeekRequest`；S2 侧用原子指针交换槽 |
| R4 | `ffp->vout` 在 S0（setSurface）与 S6（display）并发 | 崩溃/黑屏 | `scoped_refptr<VideoRendererSink>` + sink 内部锁；契约测试 `PresentIsThreadSafeWithSetOutputTarget` |
| R5 | `audio_clock` 由音频线程写、视频线程读 | A/V 抖动 | seqlock；音频线程是唯一写者 |
| R6 | 用户在事件回调里调 `stop()` | **死锁**（原版 `message_loop` 派发时持 `mp->mutex`） | S8 派发时不持任何锁；`Player` 方法只 PostTask |
| R7 | `stream_close` 与 `read_thread` 同时访问 `ic` | use-after-free | `FormatCtxPtr` 归 S2 独占；`Stop()` 只置标志 |
| R8 | `packet_queue_flush` 与 `packet_queue_get` 并发 | 返回已 unref 的包 | `scoped_refptr<DecoderBuffer>` + 队列锁覆盖全部操作 |
| R9 | 分辨率变化时 `img_convert_ctx` 被 S3 重建、S6 使用 | 崩溃 | 转换在 S3 完成，S6 只见成品 `VideoFrame` |
| R10 | `abort_request` 后线程仍卡在 `av_read_frame` | stop 超时 | `interrupt_flag_` → `AVIOInterruptCB`；`stop_under_load` 测试守护 |
| R11 | 对象已析构但任务还在队列里 | use-after-free | ★**`WeakPtr` 从根上消除**（Chromium 模型的核心收益） |
| R12 | 回调跨 sequence 传裸指针 | use-after-free | 只允许 `scoped_refptr` / 值类型 / `base::Unretained`（后者需注释 + review） |
| R13 | `AudioRendererSink::Stop()` 后仍收到 `Render()` | use-after-free | Chromium 契约：`Stop()` 返回后保证不再调 `Render()`；契约测试验证 |

**R11 是本次重构最大的稳定性收益**：ijkplayer 里"释放播放器后回调触发导致崩溃"是长期 issue；Chromium 的 `WeakPtr` + task runner 模型让这类 bug 在结构上不可能发生。

**验证手段**：TSan 构建跑全部 unit + contract；`stress/` 的 11 项压力测试；`LockOrderChecker` 在 debug 构建全程开启。

## 8. 性能预算

以 1080p30 + 48kHz stereo 为基准（帧间隔 33.3ms）：

| 路径 | 预算 | 说明 |
|---|---|---|
| `DecoderBufferQueue::Push/Pop` | < 5 µs | 一次 `AutoLock` + `scoped_refptr` move |
| `VideoFrameQueue::Reserve/Commit` | < 5 µs | — |
| `VideoFrameCompositor::DecideNextFrame()` | **< 1 µs** | ★纯函数，无分配、无锁、无日志 |

| `AudioRendererSink::RenderCallback::Render()` | **< 100 µs** | 只 `FillBuffer` + `Scale` |
| `AudioRendererAlgorithm::FillBuffer()`（含 WSOLA） | < 60 µs / 1024 帧 | rate==1.0 时走快速路径（纯 memcpy） |

| `PostTask` | < 2 µs | 一次锁 + `OnceClosure` move |

## 9. 与原版线程模型的对照

| 关注点 | ijkplayer | avbase |
|---|---|---|
| 线程创建 | `SDL_CreateThreadEx` 手工 | `base::Thread` RAII + `SetName` |
| 线程退出 | `abort_request` 标志 + 各处轮询 | `base::AtomicFlag` + `WaitableEvent` + `WeakPtr` 自动失效 |
| 跨线程调用 | 直接调对方函数（易 use-after-free） | `PostTask` + `BindOnce` + `WeakPtr` |
| 条件变量 | 7 组 `SDL_mutex`/`SDL_cond` 手工配对 | 队列/事件封装；`base::ConditionVariable` |
| 唤醒 demux | `continue_read_thread` 在 ≥5 处 signal | **1 处**（`resume_event_`），且只有 3 个置位点 |
| 音频回调线程负载 | 重（swr_convert + 队列访问 + 时钟更新 + 持锁） | 极轻（`FillBuffer` + `Scale`） |
| 用户回调线程 | `message_loop`，派发时持 `mp->mutex`（死锁风险） | S8，派发时不持锁 |
| stop 是否阻塞 | 是（可能 ANR） | 否（异步 + 事件确认；`StopSync` 备选） |
| 时钟线程安全 | 无（data race） | seqlock |
| seek 状态跟踪 | 分散在 4 处 | `SeekController` + `SeekPhase` 集中 |
| 分辨率变化 | 分散在 3 处 | `DecoderStream::ReinitializeDecoder` 一处 |
| 对象销毁后残留任务 | 靠人肉审查 | **`WeakPtr` 结构性消除** |
| sequence 归属 | 无概念 | `SEQUENCE_CHECKER` 运行时断言 + `GUARDED_BY_CONTEXT` 编译期注解 |

## 10. 一图总结：数据面 vs 控制面

```
     控制面（Chromium task runner，全程非阻塞）
     ─────────────────────────────────────────────────────────────
     S0 ──PostTask──► S1 ──PostTask──► S3 / S4 / S5
      ▲                │                    │
      │                │                    │
      └── S8 ◄──Emit───┴────────────────────┘
          (事件 FIFO)

     数据面（有界队列，天然背压）
     ─────────────────────────────────────────────────────────────
     S2 ══DecoderBufferQueue══► S3 ══VideoFrameQueue══► S1/S6 ──► 显示器
      ║                         S4 ══AudioRendererAlgorithm══► S7 ──► 声卡
      ║
      ╚══ resume_event_ / interrupt_flag_ / stop_flag_  ◄── S1 控制
```

控制面用 `PostTask`，数据面用队列，两者只通过**原子标志**与**有界队列的 Abort/Flush** 交互。这是 avbase 线程模型的全部。
