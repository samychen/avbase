### 5.1 高危风险（R ≥ 15）专项预案

#### R1 · 音视频同步移植出错 —— 唯一可能让项目失败的风险

**三重防线**：

1. **移植纪律**：M6 开始时把 `ff_ffplay.c` 的 `compute_target_delay` / `video_refresh` / `synchronize_audio_to_video` / `get_master_clock` 四个函数打印出来对照，逐行实现，每个魔法数字写注释标明原值与原出处。**禁止"顺手优化"**。文件头注明出处与许可证（R8）。
2. **测试防线**：`DecideNextFrame` 是纯静态函数，120+ 用例、行覆盖 100%、分支覆盖 ≥95%。用 `SimpleTestTickClock` 构造原版难以复现的边界（迟到恰好等于阈值、serial 切换、`kNoTimestamp`、负 duration、rate 切换瞬间）。
3. **数据防线**：Golden g06/g07/g11/g12 逐帧比对，任何差异必须定位到具体帧并解释。

**触发预案**：M6 结束时若 `av_diff` 稳态 > 40ms，暂停后续里程碑，投入 1 周做"同步专项"：用 `avbase-inspect play --trace sync,compositor` 输出逐帧决策，与原版 trace 日志并排 diff。

#### R2 · 自研 `base/` 工期超支

**分级降级预案**（在 M2 的第 5 天做 go/no-go 决策）：

| 级别 | 内容 | 触发条件 | 代价 |
|---|---|---|---|
| L0 完整 | 完整实现 Chromium 同名 API | 正常 | — |
| L1 `BindOnce` 子集 | 只支持 lambda + 成员函数+WeakPtr + ≤4 绑定参数；不支持 `Passed`/`Owned`/变参包 | M1 超期 > 30% | 少数调用点写法变啰嗦 |
| L2 `SimpleTaskRunner` | `std::jthread` + `deque<OnceClosure>` + `condition_variable` 实现 `SequencedTaskRunner`，**接口形态不变**；`TaskEnvironment` 改为"同步执行 + 手动推进虚拟时钟" | M2 超期 > 50% | 无嵌套 RunLoop；延迟任务精度降低；M13 后补齐 |
| L3 vendor 抽取 | 从 Chromium 抽取 `base/time` + `base/memory` + `base/functional` 最小子树（BSD-3，需处理 absl 依赖） | L2 仍不满足 | 构建复杂度上升 |

**关键点**：L1/L2 都**保持接口形态不变**，所以 `media/` 与 `player/` 的调用方代码零改动，后续替换实现是纯内部工作。这是"参照 Chromium API 而非 Chromium 实现"这个决策的直接收益。

#### R5 · 析构/stop 死锁

1. **设计防线**：固定销毁顺序（先停消费端再停生产端）；`WeakPtr` 让"对象已销毁但任务在队列"自动安全；`stop()` 非阻塞。
2. **超时兜底**：`WaitableEvent::TimedWait(config.shutdown_timeout)`（默认 500ms），超时 detach + `LOG(ERROR)` + 输出 `DumpDiagnostics()`。**宁泄漏一个线程也绝不卡死调用方**（Δ15）。
3. **测试防线**：4 项压力测试进每次 CI（`stop_under_load` / `destructor_timeout` / `callback_reentry` / `lifecycle_flood`）。
4. **工具防线**：`DumpDiagnostics()` 输出每个 sequence 的存活状态与阻塞位置，线上卡死能立刻定位。
