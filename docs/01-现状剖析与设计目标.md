## 2. 十二条具体病灶（附代码取证）

### 病灶 1：`ff_ffplay.c` 单文件 5400 行

一个文件里塞进了：解复用、三路解码、音视频同步、帧调度、丢帧策略、精确 seek、缓冲水位、滤镜、字幕、统计、平台分支。`VideoState *is` 这一个指针在 **80+ 个函数**间传递。改 `video_refresh()` 得先读完全文，因为 `is->` 的字段随时可能被别的线程改掉。

### 病灶 2：`VideoState` / `FFPlayer` 是上帝结构体

```c
// ff_ffplay_def.h（节选，真实形态）
typedef struct VideoState {
    SDL_Thread *read_tid;  SDL_Thread *video_tid;
    AVFormatContext *ic;
    Clock audclk, vidclk, extclk;
    SDL_mutex *play_mutex;
    int audio_stream, video_stream, subtitle_stream;
    PacketQueue audioq, videoq, subtitleq;
    FrameQueue pictq, sampq, subpq;
    int av_sync_type;
    double audio_clock;  int audio_clock_serial;
    int seek_req, seek_flags, seek_rel, seek_pending;
    int64_t seek_pos, seek_target;
    int paused, last_paused, step, step_to_start, abort_request;
    int accurate_seek_pending, ...
    struct AudioParams audio_src, audio_tgt;
    struct SwsContext *img_convert_ctx;   struct SwrContext *swr_ctx;
    ...   // 共约 200 个字段
} VideoState;
```

后果：**没有任何字段是某个模块私有的** → 任何模块能改任何状态 → 数据竞争只能靠人肉审查发现；想测 `compute_target_delay()` 得构造整个 `VideoState`；`is->paused` 与 `is->last_paused` 混用不会有编译错误。

### 病灶 3：六套重复的手写"面向对象"

| 手写 vtable | 位置 |
|---|---|
| `IjkMediaPlayer` | `ijkplayer_internal.h` |
| `ffpipeline` | `pipeline/ffpipeline_internal.h` |
| `ffpipenode` | `pipeline/ffpipenode_internal.h` |
| `SDL_Vout` | `ijksdl/ijksdl_vout_internal.h` |
| `SDL_Aout` | `ijksdl/ijksdl_aout_internal.h` |
| `SDL_VoutOverlay` | `ijksdl/ijksdl_vout_overlay_internal.h` |

每套都要写 `func_alloc` / `func_free` / `func_run_sync_l` + `mutex` + `cond` + `opaque` + 引用计数：

```c
// ijksdl_vout.c —— 这类代码在 ijkplayer 里出现了 6 遍
SDL_Vout *SDL_Vout_CreateInternal(size_t obj_size) {
    SDL_Vout *vout = SDL_calloc(1, sizeof(SDL_Vout));
    if (!vout) return NULL;
    vout->opaque_class = &vout_class;          // ← 手写 class
    vout->opaque = SDL_calloc(1, obj_size);     // ← 手写 this
    if (!vout->opaque) { SDL_Vout_FreeInternal(vout); return NULL; }
    vout->mutex = SDL_CreateMutex();
    if (vout->mutex == NULL) { ... }
    return vout;
}
```

C++ 里这些由语言免费提供。**仅这一项就能省掉 ~2000 行纯样板**。

### 病灶 4：`goto fail` 阶梯式资源释放

`ff_ffplay.c` 里有 **50+ 处** `fail:` 标签：

```c
static int video_thread(void *arg) {
    AVFrame *frame = av_frame_alloc();
    if (!frame) { ret = AVERROR(ENOMEM); goto fail; }
    ...
    if (ret < 0) goto fail;
fail:
    avcodec_flush_buffers(...);       // ← 逆序、易漏、易双重释放
    av_frame_free(&frame);
    av_packet_unref(&pkt1);
    av_packet_unref(&pkt);
    return ret;
}
```

漏一个 `av_packet_unref` 就是泄漏，顺序错一个就是 use-after-free。

### 病灶 5：选项系统是"编译期无检查的字符串"

`ijkmp_set_option_int(mp, IJKMP_OPT_CATEGORY_PLAYER, "max-buffer-size", 1024*1024)` —— 拼错 `"max-bufer-size"` **静默不生效**。

```c
// ff_ffplay_options.h
#define OPTION_OFFSET(x) offsetof(FFPlayer, x)
{ "max-buffer-size", "max buffer size should be pre-read",
    OPTION_OFFSET(dcc.max_buffer_size), OPTION_INT(MAX_QUEUE_SIZE, 0, MAX_QUEUE_SIZE) },
```

字段名、选项名、类型、范围分散在四处，改一个要同步改四处；无编译期检查；IDE 无法跳转；布尔/枚举/时长/字节数全塌缩成 `int`。

### 病灶 6：消息系统是"三个 int + 一个 void*"

```c
// ff_ffmsg.h（已核对全文）
#define FFP_MSG_VIDEO_SIZE_CHANGED   400   /* arg1 = width, arg2 = height */
#define FFP_MSG_BUFFERING_UPDATE     502   /* arg1 = buffering head position in time,
                                              arg2 = minimum percent in time or bytes */
#define FFP_MSG_SEEK_COMPLETE        600   /* arg1 = seek position, arg2 = error */
#define FFP_MSG_GET_IMG_STATE       1000   /* arg1 = timestamp, arg2 = result code, obj = file name */
```

参数含义**只存在于注释里**。`FFP_MSG_BUFFERING_UPDATE` 的 arg2 注释甚至自相矛盾（"percent in time **or** bytes"）。发送侧 `ffp_notify_msg2(ffp, FFP_MSG_VIDEO_SIZE_CHANGED, width, height)` 传反了编译器不会吭声。

### 病灶 7：属性查询同样是 int 常量

`FFP_PROP_INT64_VIDEO_CACHED_DURATION` / `..._BYTES` / `..._PACKETS` / `FFP_PROP_FLOAT_AVDIFF` / `..._DROP_FRAME_RATE` 共 **30+ 个**，想画一张监控图要调 20 次 `ijkmp_get_property_int64`，每次进一次互斥锁。

### 病灶 8：平台代码侵入核心

```c
// ff_ffplay.c 本体里就有平台分支
#ifdef __ANDROID__
    if (ffp->mediacodec_all_videos || ffp->mediacodec_avc || ...) {
        ffp->node_vdec = ffpipeline_open_video_decoder(ffp->pipeline, ffp);
    }
#endif
#if defined(__APPLE__)
    if (ffp->videotoolbox) { ... }
#endif
```

核心文件依赖平台宏 → **核心无法在纯净环境下编译和测试**，CI 必须为每个平台跑一遍才能验证核心逻辑。

### 病灶 9：侵入式修改 FFmpeg

`tools/` 下维护着对 FFmpeg 源码的补丁，同时通过 `av_register_input_format()` / `av_register_protocol()` 注册 `ijkurlhook`、`ijklivehook`、`ijklongurl`、`ijkhttphook`、`ijksegment`、`ijkasync`。

代价：**无法使用发行版/官方 FFmpeg**；每次 FFmpeg 升级都要重新对齐 patch —— 这是 ijkplayer 长期停留在旧 FFmpeg 版本的根本原因之一；URL 重写用 hook protocol 实现，调试时栈深 6–7 层。

### 病灶 10：线程同步靠人肉纪律

`VideoState` 里有 **7 组** mutex/cond 配对，加锁顺序无任何文档约定。`read_thread` 的唤醒条件尤其脆弱：

```c
if (!is->seek_req && !is->eof && ... && stream_has_enough_packets(...) || ...) {
    SDL_CondWaitTimeout(is->continue_read_thread, wait_mutex, 10);
}
```

这个 `continue_read_thread` 条件变量必须在**至少 5 个不同位置**被 signal，漏一处就是"播放卡住不动"。

### 病灶 11：`release()` / `stop()` 卡死

`ijkmp_shutdown()` → `stream_close()` 需按特定顺序唤醒所有线程并 join。因为阻塞点分散且无统一取消令牌，实践中出现过：
- 用户回调里再调 `ijkmp_stop()` → **死锁**（`message_loop` 派发时持 `mp->mutex`，`ijkmp_stop` 也要拿它）
- 网络 IO 阻塞在 `av_read_frame` 里，`abort_request` 无法及时中断
- `ijkmp_stop()` 阻塞到线程退出，在 Activity `onDestroy` 里调用导致 ANR

### 病灶 12：几乎没有测试，且**结构上无法测试**

仓库里没有 `test/` 目录。`compute_target_delay()`、`synchronize_audio_to_video()`、`packet_queue_*` 这些**纯逻辑**函数其实极易测试，但因为它们全部以 `VideoState*` 为参数、依赖 `av_gettime()` 实时时钟，实际上无法脱离真实媒体与真实时间测试。

| **G12** | **Linux 出画**：X11 与 Wayland 上流畅播放 1080p30，双后端（SDL2 + 原生 GL）均通过契约测试与 xvfb 端到端验收 | CI `e2e-linux` job（见 [09 §9](09-Linux平台实现方案.md)） |

### 非目标（明确不做）

- ❌ 不重写 FFmpeg。解复用/解码能力照用。
- ❌ 不做 Java/OC 层 UI 组件（`IjkVideoView` 等）。
- ❌ 首期不做 `ijkio` 边下边播缓存（见 [08](08-实施路线图与风险.md)，理由：3000 行、复杂度最高、可后置）。
- ❌ 首期不做 C ABI 兼容层（已选现代 C++ API）。
- ❌ 不做 DRM / CDM（`media/base/cdm_context.h` 只留空接口位）。
- ❌ 不做 Android / iOS 后端（本次范围是 Linux；接口已冻结，后续增量）。
- ❌ 不内建 libass 字幕排版（输出 `raw_ass` 交上层）。
- ❌ 不追求 100% option 行为等价（`ijkurlhook` 的 URL 重写会重新设计成显式拦截器，Δ11）。

## 4. 十三条设计原则（编码时的裁决依据）

后续所有争议都拿这十三条判。P1–P10 是通用架构原则，**P11–P13 是本次新增的风格与参照原则**。

**P1 · 依赖倒置**
上层定义接口，下层实现。`RendererImpl` 依赖 `media::VideoDecoder` / `VideoRendererSink`，不依赖 `FFmpegVideoDecoder` / `GlVideoRendererSink`。构造时通过 `Deps` 注入。

**P2 · FFmpeg 是插件，不是地基**
`AVFormatContext` / `AVCodecContext` / `AVFrame` / `AVPacket` 只允许出现在 `platform/ffmpeg/` 与 `media/filters/ffmpeg_*`。跨边界一律转换成 `media::DecoderBuffer` / `media::VideoFrame`。

**P3 · 值语义优先，共享语义显式**
`DecoderBuffer` / `VideoFrame` / `AudioBuffer` 用 `scoped_refptr`（Chromium 约定），配置与事件用值类型。独占所有权用 `std::unique_ptr`，非拥有用 `raw_ptr<T>` 或 `T&`。**永不裸指针表示所有权。**

**P4 · 不跨模块抛异常，且全局禁用异常**
Google/Chromium 规定：`-fno-exceptions -fno-rtti`。模块边界返回 `base::expected<T, MediaError>` + `RETURN_IF_ERROR` / `ASSIGN_OR_RETURN`。`CHECK()` 用于不可恢复的编程错误，`DCHECK()` 用于 debug 断言。理由详见 [STYLE §3.1](../STYLE.md)。

**P5 · 时间是强类型**
禁止裸 `int64_t` 表示时间。统一用 `base::TimeDelta`（媒体时长）、`base::TimeTicks`（单调墙上时钟）、`base::Time`（Unix 时间），与 Chromium 完全一致。`media::kNoTimestamp` 是显式哨兵常量，不是魔法值 `INT64_MIN`。

**P6 · 时间可注入**
所有需要"当前时间"的地方走 `base::TickClock`。生产用 `base::DefaultTickClock`，测试用 `base::SimpleTestTickClock`（手动推进）与 `base::test::TaskEnvironment`（`TimeSource::MOCK_TIME`）。**这一条直接决定了 `VideoFrameCompositor` 能否单测。**

**P7 · 状态显式化**
播放状态用 `StateMachine` + 迁移表管理，不允许散落 `if (state == X)`。每个非法迁移记录日志并返回错误，而不是静默忽略。

**P8 · 阻塞必须可取消，跨 sequence 只 PostTask**
所有阻塞等待走 `base::WaitableEvent::TimedWait`。跨 sequence 通信**只**通过 `PostTask` + `base::BindOnce` + `WeakPtr`，绝不直接调用另一个 sequence 拥有的对象方法。这是消除 R11（对象已析构但任务还在队列里）的结构性手段。

**P9 · 数据流单向，控制流反向**
数据（Buffer→Frame→Sink）沿管线单向流动，用有界队列解耦。控制（seek/pause/flush）反向传播，通过 `serial` 世代号 + `base::AtomicFlag` 实现，不允许跨 sequence 直接改对方状态。

**P10 · 性能敏感处显式标注**
每帧都会走的路径（`VideoFrameCompositor::DecideNextFrame`、`AvSyncController::GetMasterClock`、`AudioRendererSink::RenderCallback::Render`）标注 `// @hot`，禁止在其中做内存分配、日志、粗粒度加锁。用基准测试守护（见 [04 §8](04-线程模型与数据流.md)）。

**P11 · ★Google C++ Style 是硬约束，不是建议**
`.clang-format`（`BasedOnStyle: Google`、80 列、2 空格）+ `.clang-tidy`（`google-*` `modernize-*` `performance-*` `bugprone-*`）+ `cpplint` 三重把关。命名规则：类型 `CamelCase`、方法 `CamelCase()`、getter `snake_case()`、成员 `snake_case_`、常量 `kConstant`、文件 `lower_snake_case.cc`。违反即 CI fail。完整规则见 [STYLE.md](../STYLE.md)。

**P12 · ★Chromium `media/` 是设计参照与裁决依据**
目录结构（`media/base/` 接口 + `media/filters/` 实现）、类名（`DecoderBuffer` / `VideoFrame` / `DemuxerStream` / `VideoDecoder` / `Renderer` / `Pipeline` / `VideoFrameCompositor` / `AudioRendererSink` / `DecoderStream` / `DecoderSelector` / `MediaLog`）、接口签名（`Decode(buffer, DecodeCB)`、`Read(count, ReadCB)`、`Render(delay, delay_ts, glitch, AudioBus*)`）全面对齐。设计分歧时，**默认答案是"Chromium 怎么做我们就怎么做"**，偏离必须写明理由（如 D3 解复用线程模型、Δ17 变速算法）。

**P13 · ★SDK 视角优先于实现视角**
公开 API 的每一个形状都要过 [10 §2](10-SDK易用性设计.md) 的 E1–E10 十条人体工学规则。判据：**`examples/play_sdl2/main.cc` 的行数**（目标 ≤ 300）与 **新人冷启动时间**（目标 ≤ 15 分钟）。若为了内部实现方便而让公开 API 变复杂，改内部实现。

## 5. 一个对照样例：同一件事的三种写法

**场景**：视频解码线程拿到一个 buffer，解出一帧，塞进帧队列。

### (a) ijkplayer

```c
static int frame_queue_peek_writable(FrameQueue *f)
{
    int ret = 0;
    SDL_LockMutex(f->mutex);
    while (f->size >= f->max_size && !f->abort_request) {
        ret = SDL_CondWait(f->writeready, f->mutex);
        if (ret != 0) { av_log(NULL, AV_LOG_ERROR, "SDL_CondWait(): %s\n", SDL_GetError()); goto fail; }
    }
    if (!f->abort_request) ret = f->size;
fail:
    SDL_UnlockMutex(f->mutex);
    return ret;
}

static int video_thread(void *arg)
{
    FFPlayer *ffp = arg;
    VideoState *is = ffp->is;
    PacketQueue *queue = &is->videoq;
    FrameQueue *queue_picture = &is->pictq;
    AVFrame *frame = av_frame_alloc();
    AVPacket pkt1, *pkt = NULL;
    int got_picture, ret = 0;
    if (!frame) { ret = AVERROR(ENOMEM); goto fail; }
    av_init_packet(&pkt1);
    for (;;) {
        if ((ret = ffp_decode_frame(ffp, queue, &pkt, &got_picture, ...)) < 0) goto fail;
        if (got_picture) {
            Frame *vp;
            if ((vp = frame_queue_peek_writable(queue_picture)) == NULL) goto fail;
            if (vp->frame->width != frame->width || ...) { /* 重新分配 */ }
            av_frame_move_ref(vp->frame, frame);
            vp->pts = ...; vp->serial = pkt->serial; vp->duration = ...;
            frame_queue_push(queue_picture);
        }
    }
fail:
    av_frame_free(&frame);
    av_packet_unref(&pkt1);
    return ret;
}
```

问题：`goto fail` ×3、手工 `av_frame_free`、`vp->serial` 手工维护、`ret` 语义混淆（既是错误码又是队列长度）、`frame_queue_peek_writable` 返回裸指针后若 early return 会永久泄漏槽位。

### (b) ijkpp（Chromium 风格）

```cpp
// media/filters/decoder_stream.h —— 一份模板覆盖 video/audio/text 三路
template <typename DecoderType, typename OutputType>
void DecoderStream<DecoderType, OutputType>::ReadFromDemuxerStream() {
  DCHECK_CALLED_ON_VALID_SEQUENCE(sequence_checker_);
  if (state_ != State::kNormal || !decoder_ || !demuxer_stream_)
    return;

  const int max_pending = decoder_->GetMaxDecodeRequests();
  while (pending_decodes_ < max_pending && pending_buffers_ < kSelectedWaterMark) {
    demuxer_stream_->Read(
        kReadChunk,
        base::BindOnce(&DecoderStream::OnBufferReady, weak_factory_.GetWeakPtr()));
    return;   // 异步：结果通过 OnBufferReady 回来
  }
}

template <typename DecoderType, typename OutputType>
void DecoderStream<DecoderType, OutputType>::OnBufferReady(
    DemuxerStream::Status status,
    DemuxerStream::DecoderBufferVector buffers) {
  DCHECK_CALLED_ON_VALID_SEQUENCE(sequence_checker_);
  if (status != DemuxerStream::Status::kOk) {
    OnReadError(status);
    return;
  }
  for (auto& buffer : buffers) {
    if (buffer->serial() < demuxer_stream_serial_)
      continue;                                    // 过期 buffer，直接丢（R3）
    ++pending_decodes_;
    decoder_->Decode(std::move(buffer),
                     base::BindOnce(&DecoderStream::OnDecodeDone,
                                    weak_factory_.GetWeakPtr()));
  }
  ReadFromDemuxerStream();                         // 背压：水位够了就不读
}

template <typename DecoderType, typename OutputType>
void DecoderStream<DecoderType, OutputType>::OnDecodeOutput(
    scoped_refptr<OutputType> output) {
  DCHECK_CALLED_ON_VALID_SEQUENCE(sequence_checker_);
  TRACE_EVENT1("media", "DecoderStream::OnDecodeOutput", "timestamp",
               output->timestamp().InMicroseconds());
  output_queue_.Push(std::move(output));           // VideoFrameQueue 内部处理背压
  client_->OnDecodeOutput(this);
}
```

改进点：
- **零 `goto`、零手工释放** —— `scoped_refptr` + `unique_ptr` + RAII
- **`WeakPtr` 结构性消除"对象已销毁但回调还在飞"**（原版最大的崩溃源）
- **`DCHECK_CALLED_ON_VALID_SEQUENCE`** 在 debug 构建断言 sequence 归属，误用立刻暴露
- **`TRACE_EVENT1`** 免费获得 Chrome tracing 时间线
- **异步 `Decode(buffer, cb)`** 天然支持 `GetMaxDecodeRequests()` 并行解码（硬解吞吐关键）
- 一份模板覆盖 video/audio/text 三路（原版是三个近乎重复的函数）

**行数从 ~55 降到同等功能的清晰结构，且每一行的意图都明确、每一个误用都有编译期或运行期检查。**

这就是"C++ 审美"在这份设计里的具体含义 —— 不是 `auto` 和花哨模板，而是：
1. **让非法状态无法表达**（强类型时间、`base::expected`、状态机）
2. **让资源管理不需要人记得**（RAII、`scoped_refptr`、`WeakPtr`）
3. **让线程误用无法通过测试**（`SEQUENCE_CHECKER`、`GUARDED_BY`、TSan）
4. **让每个设计决策都有可查证的参照**（Chromium `media/`）

## 6. 保留什么（避免为了重写而重写）

ijkplayer 里有大量经过十年线上验证的**算法与调参经验**，必须原样继承：

| 必须继承的资产 | 原位置 | ijkpp 去向 | 为什么不能动 |
|---|---|---|---|
| 音视频同步算法（`compute_target_delay` + `synchronize_audio_to_video`） | `ff_ffplay.c` | `media/filters/video_frame_compositor.cc` + `av_sync_controller.cc` | ffplay 十余年演进，含大量经验阈值 |
| 三级高水位缓冲（first/next/last-high-water-mark-ms） | `read_thread` | `player/buffer_controller.cc` | 弱网起播速度的核心调参，B 站线上验证过 |
| 丢帧策略（`framedrop` / `max-fps`） | `video_refresh` | `VideoFrameCompositor::DecideNextFrame` | 低端机流畅度关键 |
| 精确 seek（`enable-accurate-seek` + timeout 兜底） | `ff_ffplay.c` | `player/seek_controller.cc` | 用户可感知体验 |
| **`serial` 世代号机制** | `PacketQueue`/`FrameQueue` | `DecoderBufferQueue` / `VideoFrameQueue` | seek 正确性的基石，设计极精巧（见 [04 §4](04-线程模型与数据流.md)） |
| A/V 起播对齐（`sync-av-start`） | `ff_ffplay.c` | `BufferController` + `AvSyncController` | 避免开头音画不同步 |
| 各类经验阈值常量 | `ff_ffplay_def.h` 顶部 `#define` | `media/base/media_constants.h` | 用 `tools/extract_constants.py` 提取，**禁止手抄** |

**原则**：重构改变的是**代码的组织方式与类型安全**，不改变**算法与参数**。凡涉及阈值的改动，一律走 Golden Test + A/B 基准，不凭感觉。

**唯一例外**：变速音频从 SoundTouch 换成自研 WSOLA（`AudioRendererAlgorithm`，对齐 Chromium），这是 Δ17，需要 A/B 音质验证。
