# avbase_gl —— 可独立使用的 GL 渲染模块

> 代码：`render/gl/`（8 个头 + 5 个源，外加 `third_party/glad/` 的生成物）。
> 属性：`avbase::gl`，安装后 `find_package(avbase_gl)`。
> 本文面向**不关心 avbase 播放器、只想拿一套 GL 基础设施**的使用者。

---

## 1. 这个模块是什么

四件东西，都是「任何 GL 项目都要写、每次都写得不一样」的那部分：

| 组成 | 文件 | 解决什么 |
|---|---|---|
| **context 契约** | `native_gl_context.h` | 把「窗口系统」与「GL 调用」之间的接缝固定成一个 6 方法的接口（4 个纯虚 + `ReleaseCurrent`/`GetError` 带默认实现），模块本身不认识任何窗口 SDK |
| **入口点装载器** | `gl_api.h` / `gl_api.cc` | 按 context 实例化地持有一张 GL 3.3 core 入口点表（表本身是 glad 的生成物，见 §4.2），附带版本、扩展串、limits 查询 |
| **渲染原语** | `gl_program` · `gl_texture` · `gl_quad` | 着色器编译/链接/link 错误回传、2D 纹理与上传、贴满 NDC 的单位四边形 |
| **着色器方言** | `gl_shaders` | 按 context 生成正确的 `#version` 行（桌面 vs GLES），并提供可复用的 shader body |

### 它**不**做什么（这是设计的一半）

- **不碰 `VideoFrame`。** YUV→RGB 的矩阵、平面拆分、I420/YV12/NV12 差异全在 `media/gl/gl_present.*`。
  判据很简单：任何被 `VideoFrame` 塑形的东西都留在 media，因为 `avbase_gl` 的目标是能被一个
  「从没听过 VideoFrame」的项目拿走。
- **不创建窗口、不创建 context。** 宿主创建，模块只借用（`NativeGLContext` 是 borrowed 语义的包装，
  析构不销毁宿主的对象）。
- **不依赖任何外部库。** 不依赖 media/base，不依赖窗口 SDK，也不需要消费者去取任何东西。
  GL 的枚举与入口点表是 glad 的**生成产物**，已经入库在 `render/gl/third_party/glad/`：
  构建时不需要联网、不需要 Python、不需要装 glad。见 §5。

## 2. 作为独立模块使用

### 2.1 安装

```bash
cmake --preset no-ffmpeg          # 任何配置都行：模块本身与 FFmpeg 无关
cmake --build build/<cfg>
cmake --install build/<cfg> --prefix /your/prefix
```

装出来的东西：

```
<prefix>/include/avbase/render/gl/*.h               # 8 个头
<prefix>/include/avbase/render/gl/third_party/glad/include/
                            /glad/gl.h          # glad 生成物，随模块一起装
                            /KHR/khrplatform.h
<prefix>/lib/libavbase_gl.a                     # 模块本体
<prefix>/lib/cmake/avbase_gl/avbase_glConfig.cmake
                            /avbaseGlTargets.cmake
```

### 2.2 外部项目（推荐）

```cmake
cmake_minimum_required(VERSION 3.16)
project(my_player CXX)
set(CMAKE_CXX_STANDARD 20)

find_package(avbase_gl REQUIRED)
add_executable(my_player main.cc)
target_link_libraries(my_player PRIVATE avbase::gl)     # 注意：不是 avbase_gl
```

```bash
cmake -S . -B build -DCMAKE_PREFIX_PATH=/your/prefix
```

include 路径与仓库内一致，所以从 avbase 里抄出来的代码不用改：

```cpp
#include "render/gl/gl_api.h"
#include "render/gl/gl_shaders.h"
#include "render/gl/gl_program.h"
#include "render/gl/gl_texture.h"
#include "render/gl/gl_quad.h"
```

> **为什么是 `avbase::gl` 而不是 `avbase::avbase_gl`**：`install(EXPORT ... NAMESPACE avbase::)`
> 会把 target 名直接接在命名空间后面，而 target 叫 `avbase_gl`。所以
> `render/CMakeLists.txt` 里有一行 `set_target_properties(avbase_gl PROPERTIES EXPORT_NAME gl)`，
> 让导出的名字变成 `avbase::gl`。删掉那行不会报错，只会让消费者把模块名写两遍。

### 2.3 源码内嵌

```cmake
add_subdirectory(third_party/avbase)
target_link_libraries(my_player PRIVATE avbase::gl)
```

`install()` 规则被 `if(AVBASE_IS_TOP_LEVEL)` 守着，`add_subdirectory` 引入时不会往宿主的
prefix 里写东西。

## 3. 最小可用路径

模块只要求宿主交出两样东西：**一个 context** 和 **一个 `GetProcAddress`**。

```cpp
#include <memory>
#include <string>

#include "render/gl/gl_api.h"
#include "render/gl/gl_program.h"
#include "render/gl/gl_shaders.h"

// 1) 把窗口系统的 context 包成 NativeGLContext。在你自己的项目里这一步就是把
//    glfwMakeContextCurrent / SDL_GL_SwapWindow / eglSwapBuffers 转发进来。
class MyContext : public avbase::gl::NativeGLContext {
 public:
  void* GetProcAddress(const char* name) override { return MyLoader(name); }
  bool MakeCurrent() override { return true; }
  void SwapBuffers() override { /* swap */ }
  void GetDrawableSize(int* w, int* h) override { *w = width_; *h = height_; }
};

// 2) 装载入口点。
avbase::gl::GlApi gl;
std::string error;
if (!gl.Load(&ctx, &error)) {
  // 只有两种失败，都指向 context 本身而不是某个符号：没有 current context，
  // 或者 context 比本模块能画的还老——此时 error 里是驱动自报的版本串。
  return false;
}

// 3) 编译一个画贴图的 program。
const std::string vs = avbase::gl::ShaderPrologue(gl) +
                       avbase::gl::kQuadVertexShaderBody;
const std::string fs = avbase::gl::ShaderPrologue(gl) +
                       avbase::gl::kTextureFragmentShaderBody;
auto program = avbase::gl::GlProgram::Create(gl, vs.c_str(), fs.c_str(), &error);
if (!program) return false;                    // error 里带 driver 的 info log

auto quad = avbase::gl::GlQuad::Create(gl);    // 属性约定：0 = vec2 pos, 1 = vec2 uv
auto tex  = avbase::gl::GlTexture::Create(gl);
tex->SetLinearClamp();
// 枚举是 glad 生成的 GL_* 宏，跟着 gl_api.h 一起进来（全局命名空间，
// 没有 avbase::gl:: 前缀）。
tex->SetImage2D(GL_RGB8, 640, 360, GL_RGB, GL_UNSIGNED_BYTE, nullptr);
tex->SetSubImage2D(0, 0, 640, 360, GL_RGB, GL_UNSIGNED_BYTE, pixels);

program->Use();
tex->Bind(0);
program->SetInt("uTex", 0);
quad->Draw();
```

**生命周期规则**：`GlApi` / `GlProgram` / `GlTexture` / `GlQuad` 都借用 context，
都必须在 context **current 的线程上**创建和销毁。一个 context 对应一个 `GlApi`。

这一点上它如今是「用对了 glad」而不是「不用 glad」：表来自 glad 的 `--mx` 模式，
函数指针装在 `GladGLContext` 结构体里，一个 `GlApi` 一份。glad 默认模式和 GLEW 走的是
另一种语义——所有指针放进**进程全局**变量，两个线程两个 context 就是 bug 来源；
本模块不采用那个模式（理由见 §4.2）。

## 4. 三条维护规则

### 4.1 加入口点：多数情况不用改代码

`GlApi::context()` 返回的是 glad 的 `GladGLContext`，里面装着 **GL 3.3 core 的全部入口点**，
不是我们从 48 个里挑的那批。所以「我要用 `glMapBufferRange`」这件事不需要动任何文件：

```cpp
gl.context().MapBufferRange(...);   // 已经在表里
```

表里没有的只有两类，处理方式完全不同：

| 情形 | 做法 |
|---|---|
| 某个扩展带来的函数 | 把扩展名加进 §4.2 的 `--extensions` 重新生成。例：`GL_ARB_copy_image` 带来了 `CopyImageSubData` |
| 桌面 `gl` 规格里根本没有的（ES 专有） | 生成器会**直接拒绝**，只能自己解——今天的唯一一例是 `glEGLImageTargetTexture2DOES`，见 `gl_api.h` 里的注释 |

「扩展是否支持」由三个层次回答，按手头有什么选：

```cpp
if (gl.has_copy_image()) { ... }                       // 汇总判断，首选
if (gl.context().CopyImageSubData != nullptr) { ... }  // 只要入口点
if (gl.HasExtension("GL_ARB_copy_image")) { ... }      // 只要扩展串
```

三者都保留是有理由的：glad 在装载时填好的那些标记只覆盖**生成时点过名的**扩展，
而 `HasExtension()` 对任何名字都答得出来——包括这个模块暂时用不上的。

### 4.2 重新生成 glad：那条命令就是契约

`render/gl/third_party/glad/` 下的文件是 glad 2.0.8 的**输出**：不是我们写的，也不手工改。
完整命令与每个选项的理由在 `render/gl/third_party/glad/README.md`，这里只留要点：

```bash
pip install glad2==2.0.8
python -m glad --api gl:core=3.3 \
  --extensions "GL_EXT_texture_sRGB_decode,GL_ARB_copy_image,GL_NV_copy_image,\
GL_EXT_texture_filter_anisotropic,GL_KHR_debug,GL_ARB_debug_output,\
GL_EXT_EGL_image_storage" \
  --out-path render/gl/third_party/glad --quiet c --mx
```

- `--mx` **必须**开：只有它生成「一 context 一实例」的 `GladGLContext`，也就是 `GlApi`
  一直以来的语义。默认模式把函数指针放进全局变量，两个线程两个 context 就是 bug。
- `--loader` **不能**开：那会引入 glad 自带的 dlopen/WGL 装载路径，而本模块的装载入口
  只有一个——`NativeGLContext::GetProcAddress`。
- `--alias` **不要**开：它会静默地把所有「与 core 3.3 函数互为别名」的扩展一并拉进来，
  7 个扩展会变成 **75** 个。不开的话 `CopyImageSubData` 与 `CopyImageSubDataNV` 是两个
  独立指针，这正是 `has_copy_image()` 想知道的。

生成物带时间戳，所以重新生成永远不是空 diff——看的是 API/扩展集合变了没有，不是 diff 干不干净。

这些文件不走本项目的告警策略（它们在 `avbase_gl_vendor` 这个独立目标里编），`third_party/`
也被 `check_invariants.py` 和 CI 的格式扫描跳过。理由是同一个：**生成物里出现告警，
正确的修法是重新生成，不是打补丁。**

> 这里曾经是一张手写的常量表（`gl_constants.h`，116 项）加一台机核脚本
> （`tools/check_gl_constants.py`）。那台机器本身是好的——正是它抓出了 `GL_VERTEX_SHADER`
> 被写成 `0x8B33`（结果：`glCreateShader()` 返回 0、info log 为空，整条链路看起来像驱动坏了）。
> 但它守的是一个本可以不存在的问题：常量值本来就躺在 Khronos 的 XML 里。
> 现在那个失败模式被**删掉**了，而不是被守住——所以脚本和它的 CI job 一起退役。

### 4.3 加着色器：先要 prologue

桌面 GLSL 与 GLSL ES 是**同一套语法、两种语言**：`#version 330 core` 在 ES context 上是编译错误，
`#version 300 es` 在桌面 context 上也是；而完全不写 `#version` 会默认成 1.10，
然后以「不认识 `in vec2`」的形式报一个指错方向的错。

所以 `gl_shaders.h` 给的是**不带 `#version` 的 body**，由 `ShaderPrologue(gl)` 决定头：

```cpp
const std::string src = avbase::gl::ShaderPrologue(gl) +
                        avbase::gl::kQuadVertexShaderBody;
```

自带的 4 个 body 里，`kQuadVertexShaderBody` / `kQuadVertexShaderWithRectBody` 依赖
`GlQuad` 的属性约定（location 0 = `vec2` 位置，1 = `vec2` 纹理坐标）；
两个 fragment body 带 `uTex`，带 tint 的那个多一个 `uTint`。

## 5. 零依赖是怎么做到的，以及它的边界

| 问题 | 做法 |
|---|---|
| 不认识窗口 SDK | 入口点**逐个按名字**从 `NativeGLContext::GetProcAddress` 取；模块里没有一处 include 窗口头 |
| 不 include **系统** GL 头 | 系统的 GL 头按平台割裂（Windows 停在 1.1、Apple 的是 2.1），所以用的是内嵌 glad 生成物里自带完整类型与枚举的那一份 `<glad/gl.h>` |
| 不用**外部** GLEW/glad | 表由内嵌的 glad 生成物提供（`render/gl/third_party/glad/`，见 §4.2）。它是**随源码走的**，不是依赖：消费方不装 glad、不跑生成、不联网，也不继承任何额外链接项 |
| 不依赖 media/base | 日志靠 `std::string* error` 回传，不用 avbase 的 logging；对象不引用 `VideoFrame` |
| 符号可见性 | `gl_export.h` 提供 `AVBASE_GL_EXPORT`，只有模块自己的源定义 `AVBASE_GL_IMPLEMENTATION` |

**边界**：模块要求 **GL 3.3 core 或 GLES 3.0+**。再老的设备（GLES2）只有 `GlQuad` 考虑了兼容
（顶点写进 VBO 而不是用 `gl_VertexID`），其余路径不承诺。

### 换装载器时，接缝在哪（这个预言已经被验证过一次）

接缝是 `GlApi` 的**内部**，不是调用方：`NativeGLContext::GetProcAddress` 这条不动，
`Load()` 的实现换成 glad 生成的代码即可。第五十七轮真的做了这件事（手写表 → 内嵌 glad2），
`gl_program` / `gl_texture` / `gl_quad` 的结构与职责一行没变。

但要说清代价，别信「调用方零改动」这种漂亮话：**调用方确实改了，改的是名字，不是形状。**
换表之后枚举从 `kGLTexture2D` 变成 glad 的 `GL_TEXTURE_2D`（没了 `avbase::gl::` 前缀、
也没了 `k`），入口点从 `gl.Clear(...)` 变成 `gl.context().Clear(...)`——因为指针如今装在
`GladGLContext` 结构体里。这是一次机械替换（常量 73 处 + 入口点 73 处、5 个 `.cc`），
不是契约破裂：没有任何调用方需要重新理解「谁装载、几时装载、失败怎么报」。

真要说教训，是这一条：**只要模块把 GL 的枚举和入口点当自己的名字暴露给调用方，
换表就一定会泄漏到调用方。** 想让替换对调用方真正透明，就得在 `GlApi` 里给每个函数留一个
转发方法——那正是本模块刻意不做的（见 `gl_api.h` 的注释：转发买不到东西，还会把这些
驱动给的指针伪装成本类的方法）。两害相权，选了「名字会变、形状不变」。

## 6. 与 avbase 其余部分的关系

```
platform/{sdl2,glfw,egl}/   窗口 + context 的 3 个实现
        │  实现 NativeGLContext
        ▼
render/gl/  ← avbase_gl      零依赖模块（本文）
        │  被 media 借用
        ▼
media/gl/                    VideoFrame 语义：YUV→RGB、平面上传、overlay 合成
```

方向是单向的：`platform` → `render/gl` ← `media/gl`。
`render/` 里不允许 include `platform/` 或 `media/`（构建不变量会拦）。

**一个反直觉但有用的副作用**：因为 `render/gl` 零依赖，对它跑 clang-tidy 不会牵入
`base/*.h`、`media/*.h` 这些头，检查面干净得多——这一点在排查存量静态检查债务时很好用。

```bash
python3 tools/check_invariants.py --root .          # 架构/风格不变量
clang-format --dry-run --Werror --style=file <files>
```

CI 的格式扫描与 `check_invariants.py` 都跳过 `render/gl/third_party/`——它是生成物，
改它的正确方式是重新生成（§4.2），不是打补丁。曾经守着常量表的那股 `check-gl-constants`
job 已随常量表一起退役。
