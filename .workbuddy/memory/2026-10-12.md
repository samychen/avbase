### 新增的一条测试：`ASourceHoldsTheFrameItsLayerIsShowing`

`GlLayerSource` 的类注释声称「保留它上传的那一帧是零拷贝安全的原因」，但此前**没有任何
测试钉住它**。用带 release 回调的原生帧（不可映射）来钉：

- `Publish` 后丢掉本地引用 → 回调未跑；
- `Sync` 后 → 回调仍未跑（图层正在采样这块 surface）；
- `Detach` 后 → 回调跑了。

**为什么必须专门测**：拷贝路线上这句话看不出差别（像素已经在纹理里），所以本机（无导入
后端）任何像素测试都会过，而**有导入后端的机器会采到已释放的 surface**。这跟「有朝向的
代码必须配像素断言」是同一类理由。

### 反证（4 条突变 + 2 条实测）

## 与 MediaComponent 的能力面对照（盘点，不改代码）

用户问「L5 之后还差哪些」。做了一次全仓盘点，结论是**差距已经从渲染层搬到
播放器层和 SDK 层**。分层记录（都带文件:行证据）：

### 渲染层：基本闭合，但残留几个半截
- 3 条呈现路径（单帧 / 场景 / 转场）`media/gl/gl_present.h:32-37`；
  转场**只有 cross-fade 一种**（`render/gl/gl_transition.h:19` 原文
  "the only transition the module ships"），36 个转场 GLSL 属**刻意不移植**
  （docs/12 §4 5.5：avbase 无此产品形态）。
- 图层属性**只有 5 个**：rect / z / opacity / visible / id（`gl_scene.h:143-151`）。
  缺 rotation、背景色（硬编码 `ClearColor(0,0,0,1)` `gl_scene.cc:186`）、
  blend mode（固定 SRC_ALPHA `gl_scene.cc:194`）、源矩形裁剪、aspect-fit。
- **全仓 `.glsl` / `.frag` / `.vert` 文件数 = 0**，shader 全是 C++ 字符串字面量。

### 播放器层：单源仍是硬限制
- 一条 Pipeline = 1 条视频轨：`renderer_impl.h:303` 只有 `video_` 一个成员，
  换轨走 `SwitchVideoRenderer()` 是**替换**不是并存。
- **旋转元数据是条死路**：`decoder_config.h:69` → `video_frame.h:128` →
  `player.h:117` → 事件 `kRotationChanged` 一路解析上报，但
  `media/gl/`、`render/gl/`、`platform/` 里 grep `rotation` **零命中** ——
  渲染不看它。手机竖拍靠 rotation 标记的素材会显示成横的。

### SDK 层：L3/L5 的能力没有出口
`player/public/player.h`（47 个公开方法）与 `deps.h` 里 grep `scene|layer|pip`
**零命中**。也就是说多图层合成、多源编排**只有 host 自己绕过播放器才能用**
（examples 里的 `--second` 就是这么绕的）。

### 一个内部矛盾（本轮最有价值的发现）
**CPU avfilter 滤镜与 L4 硬件零拷贝互斥，且互斥方式是「静默退化」。**
滤镜在 `video_renderer_impl.cc:370-403`，位置是**解码之后、
`compositor_.PutCurrentFrame()` 之前**；`ffmpeg_video_filter.cc:151`
要求格式匹配，而 `visible_data()` 对不可映射的 GPU 原生帧返回**空 span**
（`video_frame.cc:150-155`）。于是开了 `filter_graph` 就得先读回或软解，
`upload_path` 从 `hw_zero_copy` 退回 `cpu_sync` —— **没有日志说明这不是配置
错误，也没有反证钉住这条退化**。

### 已确认「没有」的能力
录制（播放侧落盘，转码侧的不算）、推流/RTMP publish（`rtmp` 只作输入协议）、
缩略图/seek preview（`get_frame_mode` 是**死选项**：配置+注册表有，`media/`
里零命中）、HDR tone mapping（`player_config.h:51` 有枚举、
`:117` 有字段，但 `hdr_tone_mapping` 在 `media/`/`render/` 里**零命中**，
`kHdrUnsupported` 事件**从未被 emit**）、PBO 上传（`kPbo` 枚举注明
"not built"）、真色彩管理（只有 YUV→RGB 矩阵，无 gamut/EOTF）。

## ：渲染侧消费 rotation（TODO §1 落地）

盘点时翻出的一个真 bug，比「缺功能」麻烦：

**`VideoFrame::rotation()` 全仓没有任何写入者。** 有 getter、默认 0、被 demuxer
从 display matrix 解析（`ffmpeg_demuxer_configs.cc:67`）、被 `Player::video_rotation()`
报给宿主，但从来没写进过任何一帧。于是「渲染看 rotation」和「渲染忽略 rotation」
是**同一份代码** —— 渲染侧无论写得多正确，测的都是个常量。
后果：手机竖拍素材横着显示。

**为什么能活这么多轮**：① 链路看起来是通的（grep 得到解析、上报、SDK 接口，断点也
断得到值）；② 缺的是末端一次赋值，而帧的构造路径有多条（测试帧/解码帧/转换帧），
没有单一收口；③ 改了也不报错，画面照出只是方向不对。

### 改动（按依赖层次切 8 个提交）
- `media/base/video_frame.{h,cc}`：`set_rotation()`（对齐既有 `set_color_space()`
  风格）+ `NaturalSizeForRotation()`
- `render/gl/gl_shaders.{h,cc}`：`kQuadVertexShaderWithRectBody` 加 `#ifdef ROTATE`，
  `uRotation` = (cos, sin)；新增 `kVertexRotationDefine`
- `media/ffmpeg/ffmpeg_video_decoder.cc` + `ffmpeg_hw_video_decoder.cc`：
  出帧时 `set_rotation(config_.rotation)` —— **软硬两条路都要**
- `media/gl/gl_scene.{h,cc}`：`SetLayerRotation()` / `LayerRotation()`；
  `Upload()` 时捕获帧的旋转
- `media/gl/gl_present.cc`：单帧路径按帧的旋转设 uniform
- `tests/unit/gl/gl_rotation_unittest.cc`（新，6 条）+ `gl_test_frames.h` 加
  `MakeTopHalfFrameRotated()`

### 关键教训：方向写反了，测试抓出来的
第一版 shader 转错方向（rotation=90 时白色半边落在左边，推导说右边）。
**根因**：手推的是「几何旋转」，实现用的是「纹理坐标旋转」，两者互逆。
**再次印证「有朝向的代码必须配像素断言」—— 手推一遍不算数。**

### 遗留限制
旋转后仍按 stretch-to-fill 铺进 rect，竖拍转正会横向拉伸。
**aspect-fit 是独立的第四项**（渲染层完全不读 `natural_size()`），本轮不缠在一起做。
