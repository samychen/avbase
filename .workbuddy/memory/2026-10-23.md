## PBO 为什么是 "not built"（用户提问引出的核查）

`media/base/render_perf_stats.h:28` 的 `kPbo` 标着 reserved / not built。核查结论：

- **它是抄词汇表时一并搬来的预留枚举**，不是「实现过又删掉」。注释明说
  vocabulary mirrors MediaComponent's UploadPath，为的是两库之间不用翻译。
  名字（`cc:32` 返回 "pbo"）、JSON 序列化、单测全齐，**唯独没有赋值点**——
  全树只有三处赋值，全是另外两个值：`gl_video_layer.cc:263`（`kHwZeroCopy`）、
  `gl_video_layer.cc:370` 与 `platform/sdl2/sdl2_output_target.cc:159`（`kCpuSync`）。
- **没做的原因是它被真零拷贝超越了，不是工时不够**：PBO 只把 1080p 那 8.2 ms
  的同步拷贝搬出渲染线程（双缓冲 + `glMapBufferRange(UNSYNCHRONIZED)`，写法见
  `docs/archive/09` 的 Linux 方案），**字节数一点没少**（1080p 每帧 3.1 MB 照样
  过总线）。路线图当初写「首期软解 + PBO 已够 1080p60」，零拷贝定为 P1 之后：
  能零拷贝的平台上它多余，没零拷贝的平台应直接做 docs/12 §1 的 3.1/3.2。
- 保留枚举而不删：注释正是为了防止它被读成「这条路走过」。

## 顺手修掉的文档假数据（同「占位数据比空面板坏」那一类）

`docs/07` §11.3 的 `DumpDiagnostics()` 样例 JSON 里 `"upload_path":"pbo"` 挂在
`sink.video` 下——**两个错叠在一起**：① `pbo` 是永远不会被生产的值；② 这个字段
真实位置是 `render.upload_path`（`PlaybackStats::render` ← `present_stats.cc:87`，
`bench_render.sh:216` 读的就是 `stats["render"][...]`）。已把字段挪进新增的
`render` 块（形状照 `RenderPerfStats::ToJson` 逐字段对齐），值改成 `cpu_sync`——
样例里解码器是 `"hw":false`（软解 hevc），没有 GPU 帧可导入，只可能走 CPU 上传。
同时补一句说明哪三个值会被生产。

## 转码入口核查（用户问「ffmpeg transcode 有入口吗」）

- 生产入口只有一处：`tools/inspect/inspect_transcode.cc` → `avbase-inspect transcode`。
  grep 全树，`FFmpegTranscodeJob` / `FFmpegConcatJob` 的生产消费者只有它（其余是单测）。
- `player/public/` 全树零 `transcode` 命中 —— SDK 门面与 C ABI 都没有入口。
- 实测（macos-sdl2-werror 树）：默认 mjpeg+aac，3.029s 片源 0.28s 转完 764313 B，
  重开验证 2 stream(s)。`--vcodec libx264` 被**拒绝并列出本构建真有的编码器**：
  `h264_videotoolbox hevc_videotoolbox mjpeg`（setup_ffmpeg.sh 白名单构建，libx264
  不在）。这是「工厂说出编码器名字 ≠ 这个构建真有」的又一次现场确认。

## 教训

- **文档里的 JSON 样例要按 `ToJson` 逐字段对齐，不能凭印象摆位置**：这次是
  bench 脚本的读法（`s["render"][key]`）暴露了样例摆错了父节点。
- **「枚举有名字 + 有单测」不等于「有人会赋这个值」**：判断一条路径是否存在，
  要数赋值点，不是数枚举项。
