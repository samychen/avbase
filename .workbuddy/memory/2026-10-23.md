## PBO 为什么是 "not built"（用户提问引出的核查）

`media/base/render_perf_stats.h:28` 的 `kPbo` 标着 reserved / not built。核查结论：

- **它是抄词汇表时一并搬来的预留枚举**，不是「实现过又删掉」。注释明说
  vocabulary mirrors MediaComponent's UploadPath，为的是两库之间不用翻译。
  名字（`cc:32` 返回 "pbo"）、JSON 序列化、单测全齐，**唯独没有赋值点**——
  全树只有三处赋值，全是另外两个值：`gl_video_layer.cc:263`（`kHwZeroCopy`）、
  `gl_video_layer.cc:370` 与 `platform/sdl2/sdl2_output_target.cc:159`（`kCpuSync`）。
- **没做的原因是它被真零拷贝超越了，不是工时不够**：PBO 只把 1080p 那 8.2 ms
  的同步拷贝搬出渲染线程（双缓冲 + `glMapBufferRange(UNSYNCHRONIZED)`，写法见
  `docs/archive/09` 的 Linux 方案），**字节数一点没少**（1080p 每帧 3.1 MB 照样
  过总线）。路线图当初写「首期软解 + PBO 已够 1080p60」，零拷贝定为 P1 之后：
  能零拷贝的平台上它多余，没零拷贝的平台应直接做 docs/12 §1 的 3.1/3.2。
- 保留枚举而不删：注释正是为了防止它被读成「这条路走过」。

### 方法教训（本轮新增）

- **BSD grep 不支持 `\b`**（词边界是 GNU 扩展）：写成 `\b` 的正则会**静默返回零命中**，
  看起来像"确认不存在"，其实是什么都没查。本轮 `grep -n "C9\b"` 就是这样空手而归的，
  改用仓库自带检索工具才拿到结果。这类安静的失败比报错危险。
- **zsh 会把 `--include=*.cc` 当 glob** 并报 `no matches found` → 同理改用检索工具。

  而输出看起来像你要的那个**。
- **子代理报告必须复核，正面例子也要复核**：本轮 3 处订正里有 1 处是轴一把不存在的
  C19 当成了"纪律由机器守卫"的**优点**。正面断言同样会错，且更不容易被怀疑。
- **`logging.cc:49` 的 `delete` 与 `default_tick_clock.cc:10` 的 `new` 是同一类偏离，

## base/check.h 讲解（用户点名要的两个类）

`CheckOpStreamHelper` 与 `NullCheckStream` 是同一个约束的两半：**宏必须能接 `<<`，但
失败路径要直到分号才执行**。做法是把「格式化」和「中止」缝进一个活到语句末尾的临时
对象——临时对象的析构点 = 完整表达式结束 = 分号。`operator<<` 只在 `!condition_` 时才
真写 `std::ostringstream`，检查通过时整条链是空转。

**实测出来的两个坑（都已编译验证，不是推测）**：

1. **位置信息是错的**：`LOG(FATAL)` 写在 `base/check.cc:20`，`LogMessage` 记的
   `__FILE__:__LINE__` 是 check.cc 而不是调用点。实测输出
   `[FATAL check.cc:20] Check failed: (a) == (b). caller said hi`。
   这就是 `NOTREACHED()` 在宏里手工流 `<< __FILE__ << ":" << __LINE__` 的原因——**宏
   在调用点展开，析构函数里的 LOG 不会**。所以写 `CHECK(x)` 想定位就得自己带上下文。
2. **DCHECK 关掉时，`<<` 的操作数照样求值**：`NullCheckStream::operator<<(const T&)`
   的实参绑到 const 引用前必须先求值。实测
   `DCHECK(Cond()) << SideEffect();` 在关闭构建下 `Cond()` 求 0 次、`SideEffect()` 求
   1 次。Chromium 的 release DCHECK 用 `true || (...)` 短路，整个流都不求值——**这里
   不一样**。规则：`DCHECK(...) <<` 后面只放常量字符串或已存在的变量。

**通过时的代价实测**（2,000,000 次循环，clang++ -O2）：裸 if ≈0 ns，
`CHECK_EQ` **43 ns**，`DCHECK_EQ`（关）0 ns。`stream_` 是成员、无条件构造，所以
**逐帧路径上摆 CHECK 等于每帧付 43 ns**——对比 ReserveCommit 预算 489 ns，一条就吃掉
约 9%。冷热分工的判据在此。

`NullCheckStream` 存在的**唯一理由**是「不编译」和「不执行」是两件事：直接
`#define DCHECK(x)` 删掉会让所有带 `<<` 的调用点编译失败。

另注：`tests/unit/base/` 下**没有 check_unittest.cc**，且全树零 `DEATH` 用例——这一族的
失败路径（abort）没有任何用例覆盖。

### 已补：`tests/unit/base/check_unittest.cc`（236 行，12 个用例）

`tests/unit/base/*.cc` 是 glob，新文件无需改 CMake。四组：
① 通过时不死不出声（含 RecordingDelegate 断言零日志）；② 六个比较宏全通过；
③ `NullCheckStream` 两个契约（链式返回自身 + **操作数仍被求值**）；
④ 失败路径用 gtest 死亡测试在子进程里观察（`EXPECT_DEATH` 是全树首例）。

**突变反证的两个教训（都是我自己的错，值得记住）**：

1. **「突变后测试仍绿」可能是突变脚本的锅，不是测试没用。** 我把
   `stream << bump()` 换成 `stream << 42`，结果构建因 `bump` 未使用被
   `-Werror` 拒了，ninja 留着旧二进制，跑的还是旧代码——看上去像"测试
   空过"，其实是**没编上**。判据：突变脚本必须单独检查构建退出码，构建
   失败要单列，不能混进"仍绿"。改用可编译的突变（`stream << bump`）后
   正常变红。

2. **`#else` / `#if defined(...)` 分支是门禁照不到的角落。** DCHECK 默认
   ON（cmake/AvbaseOptions.cmake:52），只有 `release` preset 关它，而**没有
   任何 CI job 跑 release**。我写的 `#else` 分支因此从未被编译过——第一次
   手动编（不带 `-DAVBASE_ENABLE_DCHECK`）就红：`DCHECK(cond)` 把参数整个
   丢掉 → `condition` 未使用 → `-Wunused-variable` → `-Werror`。
   修法：`[[maybe_unused]]`。顺带一提，**需要这个属性本身就是契约的证据**：
   它只在"条件真的被丢弃"时才必要。
   → 规则：条件编译的分支，落成代码后要**逐个配置单独编译验证一遍**。

## 修正「错误处理」章节中断言的表述（用户：文档要改掉缺陷）

`base/check.h:35` 在 debug 下就是 `#define DCHECK(c) CHECK(c)`，失败一样走
`check.cc:15-22` 的 `LOG(FATAL)` + `abort()`。已改成：

- 断言只抓「程序员写错了」，不用来校验数据；给出三选一判据表 —— 不可信输入
  （码流 / 容器头 / 网络 / 调用方传参）→ `base::expected`；违反后继续跑 = UB /
  内存破坏 / 安全边界失守 / 延迟爆雷 → `CHECK`；其余内部契约与对账、尤其热路径
  → `DCHECK`。
- 补两条 release 下的求值陷阱：`DCHECK_EQ(a, b)` 两边完全不求值（禁止放副作用）；
  `DCHECK(c) << f()` 的 `f()` 仍会求值。

同时订正 `docs/02` §3.2：`base/check.h` 一行误列了 `DCHECK_CALLED_ON_VALID_SEQUENCE`
（它实际在 `base/sequence_checker.h:49`，且同表已有 `sequence_checker.h` 一行），
删去重复项并指向正确文件。

`build/full/lib/libavbase_base.a`，分别带/不带 `-DAVBASE_ENABLE_DCHECK` 编译后跑，
