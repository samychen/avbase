- 形态是**发一批 + 末尾一个 FIFO 哨兵等排空**，不是「发一个等一个」：事件枢纽按设计异步
  （docs/04 §1 的 S8 就是为了让管线不等用户代码），逐个等会测到两次线程唤醒（≈10 µs 量级），
  不是预算写的那条路径。数字因此是 **max(入队, 派发)**。
- 实测 ≈1.94 µs（预算 3 µs）。容差单独给 35%：安静时三次 p75 1892/1937/1947 ns（±2%），
  有负载时最高 +23%。**「跨线程」不等于「噪声大」——噪声源是「每事件一次唤醒」。**
- 突变反证：每次迭代 Post 两次 → +100.3% → REGRESSION，其余 4 项无误伤。

### ★ EventHub 静态存储期析构会让进程退出时崩溃（实测，非推测）
函数内 `static HubFixture fixture;`（静态存储期）→ 6 次里 5 次 SIGABRT、1 次 SIGILL，
且都在数字全部打印完之后。`~EventHub` 会 join 派发线程，而静态析构期 base 的进程级状态
已在拆解。**常规作用域内析构安全**（同形态 3/3 rc=0）。bench 改为进程内共享一个**有意泄漏**
的 hub（每轮栈上重建也能跑，但首轮冷线程+冷调度会高 32%：2644 vs 1978/1997 ns）。
→ 已验证（见本日末「Player 静态存储期」）：宿主把 `Player` 放在全局静态对象里有
  **同样**风险——`Player` 经 PIMPL 持有 `EventHub`（按值 `event_hub_`），且
  `~PlayerImpl`（player_impl.cc:89）在析构体里就 `event_hub_.Shutdown()` +
  `media/video/audio_thread_.Stop()` **显式 join**，atexit 下走的就是同一个崩的
  join（且一次 join 4 条线程）；base 无 AtExitManager 所以没有兜底。

- **安全写法**：栈上 / `unique_ptr` 等 main 返回前显式销毁；要全程存活就 `new Player`

  `thread_.join()` 由析构触发、对 `static` 对象在 atexit 执行——按构造等价，不另造二进制
  复跑（那次崩溃本就 flaky 5/6，造二进制性价比低）。

  便宜得多（零拷贝那条没做）。

**踩到的三个坑（都已修，前两个是真知识点）：**
1. **ABI 宏不一致导致堆破坏**（最重要）。app 没调 `avbase_configure_target()` 时
   `AVBASE_ENABLE_DCHECK` 未定义 → `SEQUENCE_CHECKER` 展开为空 → 宿主看到的
   `VideoFrame` 比库里的少一个成员 → app 侧内联 `scoped_refptr::AddRef()` 写错偏移 →
   引用计数不涨 → 帧在 compositor 手里被释放。症状极不像：先是
   `malloc_zone_error` in `VideoFrameCompositor::Render`，后来漂到 Qt `QRegion::resize`，
   连**无媒体、双 null sink** 都崩，害我先怀疑自己的 poll 线程两轮。
   靠 `-fsanitize=address` 全量插桩（项目内 `AVBASE_SANITIZERS` 只插核心库，覆盖不到 app）
   才拿到真结论：`heap-use-after-free 40 bytes inside 232-byte region`，
   freed by `VideoItem::refresh()`、allocated `VideoFrame::CreateBlackFrame`。
   修法：从 `AvbaseCompilerFlags.cmake` 抽出 `avbase_configure_abi_definitions()`，
   `avbase_configure_target()` 复用它；宿主调前者**不调后者**（后者带 `-fno-rtti`，
   moc 的 cast 与 QML 类型转换需要 RTTI）。修完 ASan 0 error。
2. **`QtVideoSink` 关闭竞态，两轮才修对**。第一版轮询线程绑 `this`，`Stop()` 在别线程
   `worker_.reset()` → SIGSEGV in `PollOnce()`。改成 mutex+快照 → 变
   `mutex lock failed: Invalid argument`（锁已失效仍在跑）。正解是**轮询只持有自己的
   `shared_ptr<Context>`，完全不碰 `this`**；`Stop()` 在锁内 join。另加
   `rendering` CAS 守卫保证 `Render()` 同一时刻只有一个。
3. **`visible_data()` 含 padding**。按 `stride()` 逐行读，紧包 `w*h` 读在非对齐宽度花屏
   （1080p 恰好看不出来）。`video_item.cc` 里对 `y_plane.size()` 做下界检查后拒帧。

**UI 三处缺陷（截图发现，全修）：** 状态停在 `Prepared` 不播（`kPrepared` 时自动 `Start()`）；
`paint()` 画的 "no signal" 与 QML 空状态文字重叠（无帧只填背景，空状态改成「无源/出错」）；

### apps/player_qt 的 GPU 上屏路径（QQuickFramebufferObject + platform/qt）
接上一轮留下的那句话（「要零拷贝就得往下走一步」）。这一步走完了，但**结论和预期相反**。

- 新增 `platform/qt/QtGLContext`：第四个窗口系统适配器，52 行。它头一次有**两个方法
  是空的**——`MakeCurrent()`（Qt 调 renderer 前已绑好）与 `SwapBuffers()`（没有我们的
  后缓冲，Qt 合成时统一呈现）。这两个空方法就是「Qt 是场景图宿主、不是可嵌入窗口」的
  全部技术后果，也是用不上 `GlPresenter` 的原因：它的契约结尾是 blit canvas + swap，
  而 Qt 项里这两样都不归你。
- 应用侧按 **glad / Qt-GL 头冲突**拆成两个 TU：`gl_video_item.cc`（Qt 半边，不含 glad）
  与 `gl_video_renderer.cc`（GL 半边，不含任何 Qt GL 头），接缝是 `void*`。
- 三个坑（都实测）：
  1. **Qt 在 macOS 默认给 OpenGL 2.1 兼容 profile**（实测 `2.1 INTEL-23.7.4`），
     `avbase_gl` 要 3.3 core → `GlApi::Load` 拒绝、项显示 "gl unavailable" 画纯色，
     其余 Qt 一切正常。修法：建任何窗口**之前** `QSurfaceFormat::setDefaultFormat()`
     要 3.3 core（驱动随后给 4.1 core）。
  2. **整幅倒像**：GL 原点左下、Qt 合成 FBO 假设行从上往下 → 要
     `setMirrorVertically(true)`。零 GL 错误、零日志，只是完全合法的一幅倒像。
  3. **glad 与 Qt GL 头同 TU 直接编译失败**（macOS 上经 `<QtGui/qopengl.h>` 拉进
     `<OpenGL/gl3.h>`，`PFNGLTEXIMAGE2DMULTISAMPLEPROC` 等 typedef 冲突，十几条 error）。
- **像素判据怎么做的**（这条以后还会用）：`AVBASE_QT_GRAB_REF` 逐像素比较两条路径的
  抓图，但画面内容必须与时间无关——会动的片子抓到的是「两个不同的帧」，`testsrc2`
  也不行（每帧烧时间码，改回去验证过：`md5` 不同）。可用做法是 `smptebars` 合成静止片
  + 白/黑**对角标记**（SMPTE 本身上下对称，不加标记测不出翻转），宽度选 854
  （非 16 对齐才压得出 stride 花屏），`-loop 1` 循环成 10s。
  结果 `mean_abs=0.82 / max_abs=207`；**改回错误朝向立刻 34.9** → 这个数有鉴别力。
- **实测成本（Intel Iris Plus 655）**：1080p 软件路径 `I420ToImage` 10.6 ms/帧；
  GPU 路径上传 8.2 ms + 绘制提交 0.45 ms。854x480：软件 2.86，GPU 3.73+0.47=4.2
  → **小尺寸下 GPU 反而更慢**。
- **推翻了我自己上一轮的估计**：「接上 NativeGLContext 就能把 CPU 转换消掉」是错的。
  算术搬到 GPU 了，**字节没搬**：1080p 每帧 3.1 MB 仍要从 CPU 内存进显存，在这块核显上
  这次拷贝和整段定点转换一样贵。真正能消掉的是让解码器直接交 GPU 帧
  （`GlHwTextureImporter` + `CVPixelBuffer`/`IOSurface`，`platform/hwimport` 的 CGL
  实现已有，`GlVideoLayer::Upload` 也分好三条路线）。这条 GPU 路径买到的不是 10x 帧率，
  是「GUI 线程不再做像素算术 + 一条能承接硬件帧的管线」。
- **顺带发现两个没修的问题**（都不属本轮，写下来免得重查）：
  1. 暂停时 sink 不拉帧（`GlVideoSink::PresentOne` 也是同一 `playing_` 条件），
     所以**暂停后 seek 画面不更新**——这是产品级行为，不是 Qt sink 独有。
  2. 这台沙箱机播放只有 **~2 fps**（10 秒只产生 18~21 帧，日志队列反复 `DRY`），
     两条路径一样；每帧成本不受影响，但「能不能跑满 30fps」无答案。
- 门禁：`check_invariants` 511 文件全过；clang-format 干净（**本机 PATH 里没有
  clang-format，要用 Xcode 里那个**）；ASan 全插桩 0 error；15s `EXIT=0` 六线程干净停；
  关掉 `AVBASE_ENABLE_QT` 时 `cmake --preset macos-sdl2` 仍正常配置。


## ：暂停中的 seek（暂停门 + 一次刷新）

修上一轮我自己留下的「暂停后 seek 画面不更新」。**那条观察本身是错的**——先造出判据
才看清真相，这也是这轮最值得记的一条。

- **判据**：`/tmp/colorsteps.mp4`，每 0.25s 换一次纯色（40 色、g=30），抓窗口中心像素
  反查帧号（`/tmp/whichframe.py`）。上一轮靠「看截图觉得没变」得出的结论不可信。
- **实测（修前）**：暂停 + seek 到 4.000s，800ms 后画面在 **5.07s** —— 不是没动，是
  **一路往前跑**。根因：`VideoRendererImpl::StartPlayingFrom` 无条件 `paused_ = false`，
  而 `PipelineImpl::FinishSeekIfBothDone` 的 `playing_` 含义是「启动过」，暂停中 seek
  照样调它（也必须调：`Flush` 的 `HoldReads(true)` 与新 serial 只有它能接管）。于是
  视频腿脱离音频与时钟自己播，画面跳走还静音。
- **修法三处**：① `StartPlayingFrom` 尊重 `paused_`（只做接管代际 + 重启解码）；
  ② `SetPaused` 成为 sink 播放状态的**唯一**派发点（此前用户 pause 根本到不了 sink，
  resume 只能靠 seek 顺带 `Play()`）；③ `PumpDecoder` 暂停时允许为「欠一帧」读一次。
- **「欠一帧」的账本**：compositor `Flush()` 置 `refresh_pending_`，暂停门放它过一次，
  `Render` present 时清；sink 侧同一概念抽成 `media/base/video_sink_gate.h`
  （三个 sink 曾各写一遍 `if (playing_)`，正是「规则写两遍只修一遍」的形状）。
- **踩到的坑**：refresh 分支若**跳过配速算术**直接 present，`target_delay` 就成了 0，
  下一帧立刻「到期」→ `RendererMultiSourceTest.ASecondaryLegHoldsItsFramesForTheOffset`
  立刻红（次级源 offset 的保持被绕过）。改成「走完第 9 步的算术、只覆盖决策」。
  这条多源老用例是这轮唯一的护栏。
- 验证：新增 5 个 gate 用例 + 2 个 compositor 用例 + 1 个 renderer 用例；
  media_unittests 412 全过；四次突变各自打红（清暂停标志 → 2 帧、撤泵放行 → 0 帧、
  撤暂停门例外 → hold、把 refresh 挪到拒绝规则之前 → 显示 seek 目标之前的帧）；
  真机 4.00s / 4.00s / 4.00s（0.8 / 3 / 6 秒三个等待点）；GL vs 软件 `mean_abs=0.778`；
  ASan 0 error；15s `EXIT=0`；`check_invariants` 513 文件全过；列宽 0 超标。

## ：丢帧口径对齐 ffplay（没帧不是丢帧）

上一轮结尾记了「暂停时 frames_dropped 以 60/s 增长」，本轮按 ijkplayer/ffplay 的算法修。

- **原版口径**（`ffplay.c: video_refresh`）：`frame_drops_late++` 只出现在
  `frame_queue_next(&is->pictq)` 的**同一行**——即「帧已经进了队列，被主动跳过」。
  队列空（`nb_remaining == 0`）与暂停（`if (is->paused) goto display;`）都走到
  `goto display`，**一个计数器也不碰**。`frame_drops_early` 是另一笔账，在解码侧
  （队列满丢新帧）。
- **我们的错**：`ClassifyFrameOutcome` 里 `if (discard || !has_frame) return kDropped;`
  —— 把「这一拍没有帧」当丢帧。而 sink 是每显示窗口问一次（Δ18 的 sink 驱动模型，
  不是 ffplay 的主动轮询），空问频率 = 刷新率：30 fps / 60 Hz 下 30/s，暂停时 60/s。
  `frames_dropped` 于是变成刷新率的函数，不是视频的函数。
- **修法**：`FrameOutcome` 新增 `kNone`；`!has_frame → kNone`（readback_failed 仍排
  最前，因为读回失败会把 frame 置 null，顺序反了就变成「什么都没发生」）；
  `discard && has_frame → kDropped`；`discard && !has_frame → kNone`。
  三个 sink（GlVideoSink / Sdl2VideoSink 子类 / NullVideoSink）同走一个函数，改一处全改。
- **反证**：突变回 `kDropped` → `AWindowWithNothingToShowIsNoEvent`、
  `DiscardingWithoutAFrameIsAlsoNoEvent`、`DefaultRendererFactoryTest.AnEmptyAskIsNotADroppedFrame`
  三条各自红（真 sink 那条报 1 vs 0）。还原后 media 415 全过、player 56 全过。
- **顺带发现的腐化注释**：`AlwaysFrameCallback` 上写着「null frame 会被记为 drop，
  所以这里必须非空」——前半句已经随本轮修复失效。写测试注释时引用的是**当时代码的
  行为**，行为改了注释不会自己红。与「注释里的鉴别力声明也会假绿」是同源病。
- **两个同名字段，不同义**：`media::VideoSinkStats::frames_dropped` = 到手但没显示
  （本轮修的）；`PlaybackStats::frames_dropped` = compositor 选帧时被拒
  （`RendererImpl::GetStatistics` 只累加 `compositor_stats().frames_dropped`，
  **不含** sink 的）。宿主读的是后者。别以为改了前者会动后者的数。
- 真机：正常播放 1.07s、暂停 seek 仍 4.00s（第 120 帧）、15s `EXIT=0` 六线程干净停止。
  文档 `docs/05` 新增 Δ24；`check_invariants` 513 文件、cpplint、clang-format 全过。

## ：显示层自己的三个计数上报到宿主

上一轮结尾记的「两个同名字段不同义」是本轮的正题：sink 那笔账算出来了，但**没人读得到**。

- **真正的语义（改名前先查了代码）**：`GlVideoSink::discard_` 不是「seek 时丢弃」，
  它在**构造时 / `SetOutputTarget` 时**被置成「没有 display、或 display 类型不对、
  或没有 raw surface」。所以 sink 的 `frames_dropped` = 「帧到手了，但没有地方可画」。
  于是它是 **`frames_presented` 的子集**（帧被选中了、没被画出来），**不是**
  `frames_dropped`（compositor 选帧时就拒了）的同类，两者不能相加。
- **漏在哪**：`RendererImpl::GetStatistics` 遍历每条腿只取 `sink_stats().render`，
  另外三个字段（`frames_dropped` / `submit_failures` / `measured_refresh_hz`）掉在地上；
  `OnFrameSubmitFailure` 也没有任何计数器接住。后果：显存/上下文挂掉、surface 没接上，
  与「播得很好」在宿主眼里完全一样。全树也没有一个测试调用 `GetStatistics()`
  （只有 `renderer_option_wiring_unittest.cc` 读两个 compositor 字段），
  所以这条链路腐化了很多轮没人红。
- **改法**：`PipelineStatistics` + `PlaybackStats` 各加三个字段
  `video_frames_dropped_by_sink` / `video_frames_submit_failures` / `measured_refresh_hz`
  （宿主侧去掉 `video_` 前缀，与既有 `frames_presented` 一致）；计数类按腿求和，
  刷新率与 `render` 一样只取主腿。`playback_stats.cc::ToJson` 加三行。
- **假 sink 改成真计数**：`FakeVideoSink` 里塞 `PresentStats`，`PullFrames` 走
  `ClassifyFrameOutcome`，另加 `set_has_output(false)` / `set_submits_fail(true)` 两个
  开关。这样测试断言的期望来自 **sink 自己算出来的数**，不是测试编的数。
- **反证四发**（逐行删再跑）：`+= sink.frames_dropped` → 无 surface 那条红；
  `+= sink.submit_failures` → submit 那条红；`= sink.measured_refresh_hz` → 刷新率那条红；
  `stats.frames_dropped_by_sink = last_stats_...` → player 映射那条红。
  注意「有 surface 不是丢帧」那条在突变下**仍绿**（它断言 0 == 默认 0）——这正是
  为什么它必须和正例配对存在。
- **玩家侧怎么测**：`PlayerImpl::OnStatisticsUpdate` 是私有 override，测试走
  `media::Pipeline::Client*` 调用（真实调用就是这么进来的），不为此加 `_for_testing` 门子。
- `Pipeline::Statistics`（media/base/pipeline.h）是第二个统计形状、**没人调用**，
  头注释自己就写了该合并或删除；本轮没往这个死结构里继续加字段。
