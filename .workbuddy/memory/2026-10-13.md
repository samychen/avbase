# 2026-10-13

## 第六十七轮：CPU 滤镜 × 硬件零拷贝（TODO §3）

第六十五轮盘点时发现的「两个功能各自都对、合起来互相拆台」，本轮落地。

### 原来的形状

`VideoRendererImpl` 在解码之后、`compositor_.PutCurrentFrame()` 之前挂 CPU
avfilter 图。硬解帧的 `visible_data()` 是**空 span**，于是喂给 avfilter 的是
**空 plane 指针**；`Process()` 返回 false 时老代码**直接 return 而不重投 pump**
→ video 腿停死，**画面冻结且什么都不报**，唯一痕迹是 "buffersrc rejected a
frame"（读起来像 FFmpeg 的错，实际是配置冲突）。

### 落地

新增 `media/filters/video_filter_stage.{h,cc}`：`VideoFilterStage`（原有纯接口）
+ `VideoFilterStageRunner`（拥有 stage 的**整个生命周期**，包括「这个流到底能不能
喂它」这个之前没人回答的问题）。渲染器的三条 `filter_*` 成员缩成一个
`filter_runner_`。

三个要点：

1. **拒绝发生在建图之前**，并**给它名字** —— `VideoFilterState` 五个取值，
   分得清「没要滤镜」和「要了但静默没跑」。放 `render_perf_stats.h` 里
   `UploadPath` 旁边，因为它俩是**同一个决定从两头看**（要 CPU 滤镜 = 放弃硬件
   导入）。叫 *refused* 不叫 *failed*：不可能成立的配置不是要重试的运行时故障。
2. **统计里可见**：`RenderPerfStats::filter_state` 进 `ToJson()`，而
   `playback_stats.cc:31` 正是用 `render.ToJson()` 出 JSON。日志按流只说一次。
3. **拒绝的代价是图，不是画面** —— 所有 refusal 分支都把解码帧原样送去显示；
   只有 EAGAIN 返回 false。**刻意不** `ToI420()` 兜底：那会把每一帧拖回系统内存、
   悄悄撤销零拷贝。

### 反证（6 条突变，每条只红该红的）

runner 去掉拒绝 / 拒绝时返回 false → 只红 `HardwareFramesRefuseTheGraphButStillShow`；
几何变了不重建 → 只红 `GeometryChangeRebuildsTheStage`；stage 不清理由 →
只红 `SuccessClearsTheRejectionReason`；FFmpeg stage 去掉硬件帧拒绝 →
只红 `RefusesAHardwareFrame`；失败的 stage 保留 → 只红 `AStageThatFailsOnceIsNeverRetried`。

### 两处「测试其实没钉住」（本轮最值钱的部分）

- **假反证**：`SuccessClearsTheRejectionReason` 原本用**全新 stage**，而新 stage
  的理由本来就是空的 —— 去掉「清空」那行照样绿，等于断言构造函数。改成先喂一帧
  几何不匹配的帧**攒出理由**再验证清除。
- **观测不到**：「失败后丢掉 stage」用**永远失败**的 stage 钉不住 —— 无论丢不丢，
  输入帧都照常显示，两条路**逐像素输出相同**。补了一个「只失败第一次、之后能恢复」
  的 stage，差别才可见。

跟第六十五轮「引擎早退没有反证」同类：**从公开 API 观测不到的性质，写多少测试都
只是重复代码的行为。** 发现它的唯一办法是把突变跑一遍看有没有红的。
