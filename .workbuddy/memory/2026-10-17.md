## :M15 C ABI 接门禁(已推送)

**为什么做**:上一轮 C ABI 落地推送后,我回头看接线,发现**它一个门禁都没有**——
不是不严,是没有。三件事同时成立:(1) `AVBASE_ENABLE_CAPI=ON` 不在任何 preset 里,
CI 从未构建过 `avbase_cabi`;(2) 唯一验收 `tools/check_capi.sh` 写死了
`-mmacosx-version-min` 和七个 `tools/build/lib/*.dylib` 路径,**在 Linux CI 上跑不起来**;
(3) 于是 `avbase_c.h` 可以腐化而不红。

**这件事优先级高于它看起来的样子**:C ABI 是兼容层,腐化方式恰好最安静——往公共头塞
一个 C++ 默认参数,**所有既有 C++ 调用方照常工作**,只有第一个 C/JNI 宿主编不过。
门禁缺位的代价不是「早发现」,是「第一个真实用户替我们发现」。

**交付**:`tools/check_capi.c` → `player/public/c/capi_smoke_test.c`(目录即 target)
+ CTest 用例 `capi_smoke_test` + `capi` preset + CI `capi` job。**删掉 check_capi.sh**。

**鉴别力证据(本轮最有说服力的一条)**:往 `avbase_c.h` 塞 C++ 默认参数 →
`cc -std=c99` 报 `error: C does not support default arguments`,
而 `c++ -std=c++20` **通过**。这就是旧形状下那个 bug 的完整样子。变异已还原(git diff 空)。
另一变异(断言反向)也确认测试会红。

**一个静默失效:`add_test()` 落在 `enable_testing()` 之前**
`player/public/c` 原在 `CMakeLists.txt:67` 被 add_subdirectory,`enable_testing()` 在 76 行。
**CMake 会静默丢弃测试系统启用前的 `add_test`**:configure 成功、构建成功、
`ctest` 报 "No tests were found!!!" **且退出码 0**。即「看起来装了门禁,一次没跑」。
**这类缺陷不会以失败出现,只会以「门禁不存在」出现。**

**顺线修掉 4 处真实缺陷**(全部是「真的编进一次构建」才暴露)
1. `avbase_c_internal.h` 6 个函数定义缺 `inline` → 每 TU 报 `-Wunused-function`;
   **且这在 C++ 里本身就是错的**(非 inline 定义被 3 个 TU 包含 = 重复符号)。
2. `avbase_c_export.h` + smoke test 缺行尾换行 → `-Wnewline-eof`,**`-Werror` 下是硬错误**。
3. `avbase_cabi` 缺 `avbase::` 别名(全树其它 target 都有)。
4. **上一轮 M15 的全部文件都不符合 clang-format** —— 因为 format 门禁只扫 `*.cc *.h`,
   `.c` 从来不在范围。已把 `player/public/c/*.c` 纳入 CI(精准到该目录,
   不是 `*.c`:全树另一个 `.c` 是 cmake 的 try_run 探针,纳入即首跑红 = R12)。

### 发现 2:`pull_frames` 稳定触发一次非法状态转换(3/3 复现)

## (收尾):VideoToolbox「bug」是假的,真问题是 stale 二进制

### 我上一轮的两个诊断结论,一个是错的

**「VideoToolbox 硬解 EOS 卡死」——不存在。** 根因是我在诊断一个
**10/15 的旧二进制**(库是 10/17 14:32 的)。重链后
`build/macos-sdl2/bin/headless` **3/3 正常 completed at media time**。
VideoToolbox 路径从来没坏过。

诊断过程中我确实观察到了真实现象(position 无上限冲到 24s、ffmpeg 构建无
`avbase.vdec` 日志行),那些观察是对的 —— **基于错误的因果**。
写了个临时探针程序(/tmp/vtprobe,不在仓库)打印完整事件流,结果它 3/3 拿到
`[EVT] Completed`;逐项排除轮询频率(50 vs 200ms)、`BindRepeating` vs
`EventHandler`、start_on_prepared、seek 默认值 —— 全部排除后才发现是二进制本身旧。

### 真正的缺陷:stale 二进制 + 一条每次必报的 ERROR

1. **`ninja` 不跟踪静态库内容** → 库重建了而可执行文件没重链时,
   `cmake --build` 输出 `no work to do` 并**报成功**。本轮 10 个二进制中招。
   **我上一轮报的「ctest 736/736 全绿」是旧数据,真数据 784/784,
   差的 48 个用例就是铁证。**
2. **`examples/pull_frames.cc`**:`PlayerConfig::start_on_prepared{true}`
   让 `PrepareSync` 内部已 Start,示例在返回后又无条件 `player.Start()`
   → **每次运行必报** `Player::Start in state Started is not legal`。
   `headless.cc` 早有 `if (state() != kStarted)` 守卫,这个示例漏了。已修 + 变异验证。

### 判新鲜度:必须读 .ninja_log,不能读 stat

我按 `stat` 判过一次,**误报成「10 个二进制过期」**—— `base_unittests`
根本不链接 `libavbase_player.a`。两个原因:
1. 静态库内容没变时 **ninja restat 会把 mtime 回退**;
2. 每个二进制只能跟**它自己链接的库**比(依赖取自 `build.ninja` 显式输入段,
   **不含 `||` 后的 order-only 段**)。
正确实现 = 新增的 `tools/check_binary_freshness.py`。

**触发条件比想象中窄**:`touch player/player_impl.cc && ninja -C <dir>`
会正确重链全部下游。落坑的是「库重建了但当轮没走链接边」。

## ：ijkplayer 对照 → 注释在撒谎 → 补上零覆盖的单测

问「ijkplayer 怎么做、能否借鉴」，结论是**不能借鉴**，但对照暴露了avbase 的注释在
说假话。

**ijkplayer 的 `start-on-prepared` 根本不是「prepared 后调 Start()」**：
```c
is->pause_req = !ffp->start_on_prepared;   // stream_open 里就算好
ffp_notify_msg1(ffp, FFP_MSG_PREPARED);     // 先发通知
if (!render_wait_start && !start_on_prepared) while (is->pause_req) SDL_Delay(20);
```
它的 `ffp_start_l()` 只做 `toggle_pause(ffp, 0)` —— **不碰状态机**，所以重复调无害；
且值在 stream_open 就定好，**没有竞态**。要借鉴就得加 `pause_req` 式中间位（状态机大改）
或让 `Start()` 幂等（撞 `state_machine_unittest` 钉住的拒绝）——都不该在清理轮次做。

**真问题在这里**：`player_impl_prepare.cc:403` 原注释写「Start() already ran by the
time the event fired」，**而代码是 `prepared_event_.Signal()` 在 `Start()` 之前**——
注释描述了一个不存在的时序。**不是「契约被违反」，是注释在撒谎**。三个调用点各自踩过
一次正是因为它。已改写成陈述真实顺序，并说明为何 Signal 在前（挪位是行为变更）。

**「竞态」要照实测写**：探针显示 20/20 **主线程全输**（autostart 总赢，Start() 只在
state_lock_ 下做几指令，主线程还要从 condvar 醒）。所以注释写「每次实测都是
kStarted，但没有代码钉住这个顺序」——**断言不变量不断言计数**，钉死竞态本身才是反效果。

**零覆盖缺口**：`start_on_prepared` 在整个测试套件里**一个用例都没有**。补
`tests/unit/player/prepare_autostart_unittest.cc`（2 例），已做**变异验证**：
删掉 `PrepareSync` 的 `kStarted` 分支 → 567转红；还原+touch → 转绿。

**写这类单测踩到的坑（都是既有约定，不是我新造的）**
1. **`PlayerImpl::PrepareSync` 没有默认参数**（`player.h` 有）——override 不挂默认参，
   单测里必须显式传 `base::Seconds(30)`。
2. **ctest 的工作目录是构建树**，`"tests/testdata/x.mp4"` 在 `./bin/xxx` 下能跑、
   在 ctest 下必然失败。**测试依赖 cwd ＝最坏的失败位置**。解法是项目既有的
   `AVBASE_TESTDATA_DIR` 编译期宏；`player_unittests` 原先**没有定义它**（因为既有
   player 单测从不碰真实媒体），已给该target 补上。
3. 同一二进制 `./bin/player_unittests` 全绿、`ctest` 全红——**先看工作目录，别怀疑代码**。

## ：挪 Start() 到 Signal() 之前 → **注释里写了句假话，被自己的变异验证抓住**

执行上一轮留下的时序修复（`OnPipelineReady` 里 `Start()` 挪到 `prepared_event_.Signal()`
之前，两行）。改完顺手把测试注释写成「把顺序改回去这个单测会红」。

**变异验证当场打脸：改回旧顺序，单测 2/2 全绿。**

**根因（查出来的，不是猜的）**：`Signal()` 在媒体线程**持有 WaitableEvent 的 mutex**
（`base/synchronization/waitable_event.h`：注释明写「Notifies *while still holding the
mutex*」），而 `TimedWait()` 返回必须拿**同一把 mutex**。所以等待者醒来时 autostart
早跑完了 —— **20/20 次主线程全输**。竞态窗口比代码形状暗示的窄得多，靠重复撞是
撞不到的。

**这条比结论更重要**：我在测试注释里写下的鉴别力承诺是**没有验证过的**。它读起来像
事实、且正好是我想说的话。**「注释声称 X 能被抓住」与「X 真能被抓住」是两件事**，
前者极易在写注释时凭意图生成。三处注释（单测头、单测断言处、`OnPipelineReady`）都
据此重写成实测陈述，包括「旧顺序并非可靠可观测的 bug」这个反直觉的事实。

**没往产品代码加测试钩子**去缩小那个窗口 —— 为测试污染 prepare 路径不值得；改为
如实记录「顺序由注释承载，不由测试承载」，并说明要真钉住需要 prepare 路径的钩子。

**净效果仍是正的**：顺序不再依赖调度运气（correctness by construction），即使它
本来就没被观测到破坏过。三处「原本就是假话」的注释（`player.h` 的「already called
Start()」、`OnPipelineReady` 的「signal first is fine」）一并纠正。

**验证**：786/786、no-ffmpeg 570/570、`pull_frames` 3 帧 + 0 ERROR、
`headless` `completed at 3.003339s`（完成链未断）、双门禁 exit 0。

## 接回 4 个 buffer key：让 BufferController 消费 BufferConfig

上文「移除 6 个死选项」的 4 个 buffer key 本轮**接回**（另 2 个 nodisp/enable-accurate-seek
仍未接，仍在死选项表）。关键：**只把 BufferConfig 喂进 BufferController 而不接 Evaluate 调用点
= 接回仍静默 no-op**（Evaluate 原本零调用方，真实门控在 RendererImpl 的 frames_pending）。
故方案分三条下游同时接：

- **时间域** `BufferController(config.buffer)`（新 ctor）：由 first/next/last_high_water_mark
  推导三级 mark（保留升序修复 Normalize），enabled 来自 packet-buffering。Evaluate 在
  `!enabled_` 时直接放行（真实 underflow 仍靠 renderer 帧饥饿暂停），progress 报 100。
  PlayerImpl ctor 改 `buffer_controller_(config.buffer)`（注意 -Wreorder：buffer_controller_
  声明在 config_ 之后，init list 必须放最后）。
- **字节域** `BufferQueueLimits{max_buffers,max_bytes,min_buffers}`（media/base/decoder_buffer_queue.h）；
  max_bytes=0 即无限（infbuf）。FFmpegDemuxer/Stream 透传，PlayerImpl 在 CreateDemuxerFor
  把 BufferConfig 映射成 limits（invariant C22：media 不见 PlayerConfig）。默认 ctor 用
  `kDefaultDemuxerQueueLimits`（256 包 / 7.5MiB）保持既有测试行为。
- **门控** `PipelineImpl` 新增 `SetBufferingGate(mark)/Enabled/MinPackets`；在
  `OnBufferingStateChange(kHaveEnough)` 处按「buffered_time ≥ mark 且 包数 ≥ min-frames」
  推迟上报，`OnBufferedTimeUpdate` 里复评并释放；kHaveNothing 立即转发并清 hold。
  **min-frames 报 0（未跟踪/队列清空）时以时长 mark 为准**——否则合成源会永久卡住
  （Demuxer 加非纯虚 `GetBufferedPacketCount()` 默认 0，FFmpeg/Composite 覆盖）。
  PlayerImpl 用 `SyncBufferingGate()` 在 prepare/OnBufferingStart/两处 OnSeekCompleted 推送。

**踩坑**：① C1 ratchet——`ffmpeg_demuxer.cc` 本就在 1030 行线上，加方法直接 1037 超限；
把 `GetBufferedPacketCount()` 改成 header 内联（-8 行）回 1029。② 一度把 gate 写成 AND 且
`count>=min` 硬判，合成 demuxer 报 0 会死锁 → 改 `count>0 && count<min` 才 hold。
③ `Status`（expected<void,E>）operator bool 是 explicit，`ASSERT_TRUE(Status)` 不编译，
用 `.has_value()`。

**验证**：新增/改测试 `BufferController.ConfigCtor/Disabled`、`DecoderBufferQueueLimitsTest.*`、
`OptionRegistryBufferTest.*`、`ValidateConfigBufferTest.*`（min_frames>256 报死锁）。

### 本轮副产物：查出一个既有 P0（EOF 之后 seek 永不回调）

写 seek 门控单测时测试 1~3% 挂死。**不要**以为这是新代码引入的——追下去是

## ：修掉上轮登记的 P0（EOF 后 seek 永不回调）

### 修法：EOF 结束任务，由 `StartPlayingFrom` 重挂（不是原地驻留）

先按候选 (a)（EOF 后 `TimedWait` 驻留）写了一版，验证通过，**然后自己推翻**：驻留会
把 demux 线程上排队的 `Flush` 一起饿死 —— `DemuxRunner` 上只有三个任务（open、DemuxLoop、
Flush），`DemuxLoop` 不返回，`Flush` 的闭包永远跑不到，而 `Demuxer::Flush` 的契约是回调
必须执行。于是改成「任务在 EOF 处结束 + `StartPlayingFrom` 重挂」。

**握手不能用两个布尔各自对读**。我第一版是「DemuxLoop 置退出标志后再读一次
`pending_seek_`；StartPlayingFrom 发布后再读一次退出标志」。这个写法在一种交错下两侧都会
`PostTask` → **两个循环任务**，后一个会在 seek 已经 flush 过的流上**重新通告一次 EOS**。
改成显式状态 + 一条所有权规则：

> 谁把 `LoopState` 从 `kGone` 改成 `kRunning`，谁负责 `PostTask`。

`DemuxLoop` 结束前取锁：`pending_seek_` 非空 → 保持 `kRunning`、**在本任务里继续读**（不
post）；否则置 `kGone` 再返回。`StartPlayingFrom` 发布后取锁：`kGone` → 置 `kRunning` +
post。单侧 CAS，不会丢也不会重复。

### 顺手修的第二个洞：`AVERROR_EXIT` 不能当致命错

`interrupt_flag_` 的**唯一用途**是打断阻塞读好让 seek 被拾起；而旧代码对 `av_read_frame`
的任何失败都 `return false` → 循环 break。也就是说「打断去服务 seek」这个动作，把 seek 需要
的那个循环本身打死了。现在 `AVERROR_EXIT` 清标志回循环顶部，不退出。

**这条没有单测，而且我失败过两次**，记下来免得下一个人重写：
- 256 字节 burst 的 `ThrottledDataSource` 测试：突变（改回 `kError`）**50/50 全绿**。
- 1 字节 burst：连 `bytes_served()` 都不动，因为队列 256 包已满，循环其实停在**背压等待**
  里（那里本来就消费 `pending_seek_`）。
- 结论：本地限速源到不了「阻塞在读里、且读完之后还需要再读一次」的状态。删掉这个测试，
  把实测结论写进代码注释。

### `ReadAndRouteOnePacket` 返回三态

`bool` → `enum class ReadStep { kContinue, kEof, kError }`。把「源读完了」和「读失败了」
塞进同一个 `false`，就是这次缺陷的形状。
