## 两个"假绿"(本轮真正的收获)

修完编译,9 个用例全绿。其中**两个掩盖了正在丢数据的缺陷**:

### E4 拼接缝:每道缝静默丢一帧

底层 sequence:
1. 一次性探针(`/tmp/dts_probe.cc`,链接本项目静态库 + pinned FFmpeg)读回我们自己 muxer 写的
   AAC MP4:**16 包,首包 pts=dts=-1024,max_pts=14336**(AAC priming 样本)。
2. 旧算法 offset = max_pts+1 = 14337 → 下一段首包 -1024+14337 = **13313 < 上一段末 dts 14336**。
3. muxer 拒收(`14336 >= 13313`),丢包。
4. **静默的原因:`WritePacket()` 返回值全被丢掉。**
5. 旧断言只要求"比一个片段长"——619 > 320,绿。

修法 = 改模型而非修数字:把每个片段**归一化到延伸的输出时间轴上**(首片段落 0,后续落前一段末尾)。
同时修掉同源缺陷"输出时间轴从 -1024 起步"。
实测:2 段 682ms(=32 帧)、3 段 1024ms(=48 帧),与 `n × 1024 / 48000` 逐位吻合。

### E3 `-ss`:duration 是对的,文件是错的

第一版测试断言"输出时长 ≤ 输入 - 150ms"**通过了**(426ms → 234ms)。
真相:输出时间轴**从 192ms 开始**,前 192ms 是空的。任何 duration 类断言都看不见。
**真断言是 `MediaInfo::start_time`**。改成 `start_time <= 1ms` 后立刻变红,再修。

> 教训:**"算对了"和"量的是那个东西"是两件事。**写一个断言之前先问一句
> "这个数字能不能掩盖错误"——本轮两个缺陷都是被一个**看起来完全合理的数字**藏住的
> (一个藏在 duration 里,一个藏在"比一个片段长"里)。

## E3b:缺口是"取消",不是"调度器"

第二十七轮给 E3 登记"trim/进度/**异步**",第二十八轮落了前两个,异步以
"没有调用方之前不加调度器(调用方 `std::thread` 即可)"挂起。这句只对一半:**调用方自己能起
线程,但拿不到任何东西去停**——`Transcode()` 是 run-to-completion。

三层落地:
1. `TranscodeCancelToken`(一个 atomic)+ `Transcode(cancel=nullptr)` 可默认参数 → 既有调用方零改;
2. 取消点 = 包边界(`!cancelled() && av_read_frame(...)`)+ **AVIO interrupt callback**。
   关键:`avformat_alloc_context()` 自己分配、在 `avformat_open_input` **之前**装回调,
   否则卡住的读要等它自己返回才发现 token。**中断导致的读失败必须被识别为取消而不是 EOF**,
   否则"取消"会被写成"成功";
3. `TranscodeJob` 句柄(worker thread + Start/Cancel/Wait/IsRunning + DoneCB)。
   析构 = Cancel + Wait;回调内再 Start 直接拒绝而非 join 自己。

C1 又挡了一次:`ffmpeg_transcode_job.cc` 加完正好 **499 行** → 拆出
`ffmpeg_transcode_job_async.cc`(97 行),泵回 414。

# 第三十六轮(同日续做):4.3b 计数三例:修掉一个真死锁 + 三处泵改造,两例转绿

用户说「要」,即继续做 4.3b。**结果比预期深**:竟揪出 `SyntheticDemuxer` 的一个真缺陷。

## 真 bug:`VideoStream::Read` 解锁一个从未持有的 mutex

`AudioStream::Read` 开头 `std::unique_lock guard(owner_->lock_)`;`VideoStream::Read`
**没有任何入口加锁**,却在 paced park 里直接 `owner_->lock_.unlock()` / `.lock()`
(synthetic_demuxer.cc)。而 `lock_` 的声明注释早就写明「S3/S4 并发读两条流」,
`decoder_stream.cc:252` 也说 `DemuxerStream::Read` 是在 **renderer 自己的序列**上调用
(video=S3, audio=S4)。**所以两条腿并发进同一个 mutex。**

Darwin 的 normal mutex 对「非持有者 unlock」不会干净失败:它把 mutex 内部状态改成
「有人持锁」,于是音频腿(它 park 后会 relock 同一个 mutex)在 `guard.lock()` 上**永久阻塞**。
unpaced 时 park 分支不可达,所以从未暴露;paced 一开必挂。**修法**:video 也持锁整个 read
(与 audio 一致),并把 `synthetic_demuxer.h` 里那条「只在 media 序列调用,无锁」的过时注释改对。

## 三处泵改造(`pipeline_fixture.h` + `pipeline_counts_unittest.cc`)

1. **设备线程独立(S7)**:render 原本 marshal 到 S4 = decode-pump 序列。paced read 在 S4
   park 等墙钟,排在它后面的 render 就被堵住 → 整个套件 1/4 速(每轮 64ms 而非 16ms)。
   新增 `base::Thread render_thread_{"avbase-pipe-S7"}`(S7 正是 `audio_renderer_ring.cc`
   给设备线程的名字),render 走它。
2. **pull 摊开 + 显示帧并入最后一 slice**:3 个 device period 背靠背拉会在 1ms 内抽干
   audio ready ring(只有 `kReadyChunks=4` chunk),1x 源补不上 → 每个突发都从空 ring 起,
   ~1/7 的 period 返回静音。改成摊到整轮,最后把 `PullFrames(1)` 塞进最后一段。
3. **按媒体驱动**:墙钟 pacing 落不准「625 个 16ms 轮」——本机 `sleep_until` 过冲高达
   ~3.8ms,纯自旋也只到 16.1ms/轮(残差在跨线程 work)。改成 `PlayFor(media)` 驱动到
   **媒体目标**:某轮静音就不推进媒体,循环自动多跑一轮。**泵仍按墙钟自我 pacing**
   (源与显示要同步),**只挪了停止条件**。

`PumpRoundRealtime` 另加:`start` 提前到 `RunUntilIdle()` 之前;`PaceUntil()` 用纯自旋。

## 结果

- **视频、音频两例转绿**(631/626 轮 → 媒体 10.01s),**三预设全绿**;
- **双速保持 DISABLED**,理由在**源侧**:paced 源固定 1x,喂不动 2x 消费者——5 秒媒体在 2x
  下仍要 5 秒墙钟,落到 75 帧(源的那一半)而断言要 150。启用它需要 VOD 源形态
  (包按消费者速度给,由**时钟**而非源决定 due),属 `SyntheticDemuxer` 的 rate 模型改动。
- `pipeline_throttle_unittest.cc` 删掉显式 `set_render_runner`(fixture 每轮都会 arm,那行 no-op)。
