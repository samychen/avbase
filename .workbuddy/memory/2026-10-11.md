## 追加排查：设置页为何没有 BigModel 选项

用户反馈设置里只有 Z.ai 和 Start Plan，没有 BigModel。**纠正上一轮的结论**：
切通道这条路在当前 UI 里走不通，不是"找不到入口"，是设计上就不给海外账号显示。

### 关键证据：解包 asar 找到内置提供方清单
- 内置清单文件（3.14.5 本地 runtime 缓存）：
  `~/.zcode/v2/runtime/provider/darwin-x86_64/3.14.5/endpoint-*/zcode-builtin.json`
  （应用包内副本在 `/Applications/ZCode.app/Contents/Resources/config/provider/zcode-builtin.json`）
- **BigModel 确实内置**：`bigmodel-api`（BigModel Coding Plan，baseUrl `https://open.bigmodel.cn/api/anthropic`）
  和 `bigmodel-standard-api`（BigModel API，23 个模型）都在，共 20 个模板
- `providerConfigRules.providerRules` 里两套家族各 3 个：
  `account:{zai,bigmodel}-{individual,team}-coding-plan`、`account:{zai,bigmodel}-start-plan`
  以及两个 `visibility: "hidden"` 的 offpeak-idle-plan（只是闲时任务，非 BigModel 隐藏原因）
- 只有 2 处 hidden，都挂在 offpeak-idle-plan 上，**与 BigModel 不可见无关**

### 真正原因
设置页按 `providerFamilyDomain` 过滤，当前值 `zai` → 只渲染 Z.ai 家族。
providerId 历史统计里 bigmodel 系列各出现 50 次（= 配置表里的静态条目数），
而**运行时实际请求的 providerId 100% 是 `account:zai-start-plan`**，从未真正激活过 bigmodel 通道。
即：切换 domain 需要**重新登录国内 BigModel 账号**，当前登录态下 UI 不提供该选项。

### asar 解析手法（可复用）
ZCode 的 `app.asar` 有 7MB header（27060 个条目），直接 `strings` 会刷屏。
正确解法：asar 头部从 offset 9 开始是 JSON，字节扫描括号匹配：
```python
raw = open(path,'rb').read(64*1024*1024)
i = raw.find(b'{"files"')   # offset 9
depth=0
for j in range(i, len(raw)):
    if raw[j]==0x7b: depth+=1
    elif raw[j]==0x7d:
        depth-=1
        if depth==0: end=j+1; break
hdr = json.loads(raw[i:end].decode())
```
不过日常排查直接看 `~/.zcode/v2/runtime/provider/**/zcode-builtin.json` 更快，
那是运行时已解出的同一份配置。

## 架构争议：platform/gl/ 放错层（用户提问，待决策）

用户质疑：`gl` 与 backend 无关，egl/glfw/sdl2 才是 backend，把 gl 放 platform/ 下是否合适。

### 结论：用户是对的，且本仓库自己的文档已经给出判断标准
- docs/02 §6 原文：**"platform/ 这一节装的是'被宿主选中'的代码"**；FFmpeg 正因为
  "可移植、在所有宿主上一致"而被迁出 platform/（决策 D11）。同一条判据套到
  `platform/gl/`：它**不由宿主选择**（sdl2/glfw/egl 三个 backend 都无条件依赖它，
  且它不是 option 门控的）、**零 SDK include**（实测 platform/gl/ 下 `grep '#include <'`
  无任何结果，GL 符号全部经 NativeGLContext::GetProcAddress 动态解析）、所有宿主一致。
  → 按本仓库自己的判据，它不该在 platform/。
- 根因：**两个正交轴被压平到同一层目录**。图形 API 轴（GL / 未来 D3D11、Metal）
  与窗口系统轴（SDL2 / GLFW / EGL）目前是同级兄弟目录。
- 实际代价：结构不可组合。加第二个图形 API 会变成 N×M 个目录
  （platform/metal-sdl2 之类），且本不存在的组合（Metal on EGL surface）变得可表达。

### OBS 的做法（已核实）
- OBS 根本没有装图形的 platform/ 目录。图形 API 轴 = **仓库根级同级模块**：
  `libobs-opengl/`、`libobs-d3d11/`、`libobs-metal/`，各自独立动态库。
- API 无关层在核心库里：`libobs/graphics/`（graphics.h 头注释即
  "API-independent graphics subsystem wrapper"），含 gs_* API、graphics_t、
  gs_exports 函数指针表、graphics-imports.c 运行时装载。
- **窗口系统轴 = 图形 API 模块内部的"文件"而非目录**：libobs-opengl/ 里
  gl-subsystem.c、gl-shader.c 等纯 GL 文件与 gl-windows.c(WGL)、gl-nix.c、
  gl-x11-egl.c、gl-wayland-egl.c、gl-egl-common.c、gl-cocoa.m 并列。GLAD 做符号装载。
  → 即 OBS 中**窗口系统从属于图形 API 模块**，不是它的兄弟目录。用户的模型正确。
- 差异（非错误）：OBS 由 Qt(frontend) 拥有窗口，从未需要 SDL2/GLFW 适配层；
  avbase 可嵌入/无头，接受宿主已有的东西（含 SDL2/GLFW 这类库）——这是第三类，OBS 没有对应物。

### 建议方案（待用户拍板）
拆成两轴：`render/gl/` 提到顶层（= platform/gl/ 搬家，重命名为
avbase_render_gl），platform/ 只留 sdl2/glfw/egl + hwaccel。
- 约束核算：render/ 依赖 media ✅；platform/* 依赖 render/gl ✅；
  media/ 仍不 include platform/ → C26 成立 ✅；C5 只管 base/media/player 三目录，
  render/ 可合法含 GL 头（虽然今天并不含）✅；C25 改 glob 即可；
  C23 旧 platform/gl/* 基线条目变成 stale note（非失败），新路径当前 0 超长行。
- 成本很小：引用 `platform/gl/` 的仅 14 个文件 / 18 处 include。

`base/test/task_environment.{cc,h}` 同时命中忽略规则。根因是 **`~/.gitignore_global`
第 4 行有一条裸的 `test`** —— 无斜杠的模式匹配**任意层级**的同名目录，于是把
`./base/test/` 整个吞了。实证后果：在该目录新建文件 `git status` 完全看不见，

### 验证方法沉淀
判断「某路径到底有没有被忽略」要用退出码，不能用 `check-ignore -v` 有输出就当被忽略：
命中**反忽略**（`!`）规则时 `-v` 照样打印那行，但路径实际不被忽略。
可靠三件套：
- `git check-ignore -q <path>` → 退出码 1 = 未被忽略，0 = 被忽略
- `git ls-files -c -i --exclude-standard` → 列出「已跟踪且被忽略」陷阱，应恒为空
- 放一个探针文件看 `git status` 是否显示 → 最终判据

## 第五十四轮：真机跑通 GL 后端 —— 「编译通过 ≠ 能跑」

### 拿到 GLFW 依赖的办法
`brew install glfw` 依旧失败（Homebrew API 超时 + ghcr.io 连不上），而 **GitHub release

新增的 `tools/setup_glfw.sh`（装到 `tools/build/glfw`，gitignored，仿 setup_ffmpeg.sh）。

### 运行时才暴露的三个 bug（都是编译期看不见的）
1. **`render/gl/gl_loader.h` 的 `kGLVertexShader = 0x8B33` 是错的**，官方 `GL_VERTEX_SHADER
   = 0x8B31`。后果：`glCreateShader` 收到无效 enum 返回 0，随后 compile status=0 且
   **info log 为空** —— 症状伪装成「驱动坏了」。这条让此前号称「已验证」的 SDL2 `--gl`
   路径在真机上也从没出过画面。
   → 既然错了一个，就把全部 32 个常量用 SDK `gl.h`/`glext.h` **机器逐项核对**，又揪出
   `kGLRG8 = 0x822A`（应为 0x822B，NV12 的 UV 平面格式）。**常量要用脚本核，不靠肉眼。**
2. 三个示例的 `GlRuntimeWorks()` 照抄了上面的错值；且探针 shader 都缺 `#version`
   指令 —— Core Profile 无 `#version` 会被当 GLSL 1.10 拒绝（driver 原话 `ERROR: 0:1: ''
   : #version required and missing.`）。桌面 → `#version 330 core`，EGL ES3 → `#version 300 es`。
3. **CMake target 名是 `glfw` 不是 `glfw3`**（产出文件叫 `libglfw3.a`，名字不一致）。写成
   `glfw3` 会被降级成裸 `-lglfw3`，include 目录不传递。

### 方法沉淀
- **不能用能否编译推断「能不能跑」**。这次靠「真跑一次二进制」才挖出核心层的常量错误。
- 诊断要用**对照探针**（最小独立程序）做二分：这里依次排除了「本机 GL 环境」
  （probe1 静态链接 OK）、「GL 函数指针」（probe2 打印非 null）、「渲染线程」
  （probe3 worker thread OK），最后才落到自己的常量表上。避免直接在复杂工程里盲改。
- 编译期看不到、日志又空白的失败，优先怀疑**枚举/常量值无效**（会返回 0 而无 log）。
- `ThrottledDataSourceTest.AbortUnblocksAStalledRead` 是**负载相关 flaky**：并行跑构建时
  会失败，单独跑 0.16s 通过。不要把并发跑出来的首次失败当回归。

## 第五十六轮：GL 层做成独立可分发模块 avbase_gl

用户：「做成成熟 gl 方案，可以单独作为一个模块供其他项目使用」。边界三问全部选推荐项：
模块边界 = 加载器+context+渲染原语（对标 libobs-opengl，不含 VideoFrame 语义）；
扩展策略 = 手写表 + 机器核对（零第三方依赖）；交付 = `avbase_gl` + install/export。

### 目录重划：render/gl 零依赖模块 ↔ media/gl 视频语义
- `render/gl/`（14 文件 = 9 头 + 5 源）构成 `avbase_gl`：`gl_api`（per-instance 装载器）、
  `gl_constants.h`、`gl_program` / `gl_texture` / `gl_quad` / `gl_shaders` / `gl_export.h`、
  `native_gl_context.h`、`overlay.h`。**不依赖 media/base/GL 头/第三方装载器**。
- 迁出的半边：`render/gl/gl_present.*` → `media/gl/gl_present.*`（YUV→RGB、平面拆分、
  色彩矩阵），`render/gl/gl_video_sink.*` → `media/gl/` 并改用 `gl::` 命名空间。
- 删除 `render/gl/gl_loader.h`（被 `gl_api` 取代）。
- 判据写进 `render/CMakeLists.txt` 头部注释与 docs/13。

### 关键设计点（都用注释留在代码里）
- **per-instance `GlApi`**：一 context 一实例，无进程全局表 —— 这是与 GLEW/glad 最大的语义差别
  （那两个的多线程多 context 是 bug 来源）。
- 两张 X-macro 表语义不同：`AVBASE_GL_CORE_ENTRY_POINTS` 缺一即 `Load()` 失败并**报出函数名**；
  `AVBASE_GL_EXT_ENTRY_POINTS` 缺则成员留 null、功能标记不可用。加函数 = 加一行（展开三次）。
- 扩展检测**双判据**（扩展串 + 入口点非空），因为有的扩展只加枚举不加入口点。
- `ShaderPrologue(gl)` 决定 GLSL 方言（`#version 330 core` vs `#version 300 es` + precision）。
- `EXPORT_NAME gl`：否则 `install(EXPORT NAMESPACE avbase::)` 会把 target 导成
  `avbase::avbase_gl`，消费者得把模块名写两遍。

### 手写常量表 + 机核脚本（`tools/check_gl_constants.py`）
- 手写枚举的理由：系统 GL 头按平台割裂（Win `<GL/gl.h>` 停 1.1、Apple 是 2.1），库里不能因
  谁的 SDK 编的就变形。代价是写错不报错 —— 这个代价真实发生过（`GL_VERTEX_SHADER` 曾写 0x8B33）。
- 脚本折叠两侧名字（`kGLTexture2D` ⟷ `GL_TEXTURE_2D`）**不猜词边界**；加两条增强：
  ① **厂商后缀回退**（`GL_RGBA16F_ARB` 也认，依据是「提升为 core 时值不变」这条 GL 硬规则）；
  ② **Khronos 头缓存** `tools/build/khronos/{glcorearb.h,glext.h,gl2ext.h}`（三条 curl，
  registry.khronos.org **可直连**，与 raw.githubusercontent 被拦不同）。
- 覆盖率实测：macOS 单跑 SDK 头 **100 核对 / 16 查不到**；带 Khronos 缓存 **116 / 0**。
  那 16 项是：3 个 GL 3.0 查询 + 12 个 KHR_debug + `GL_TEXTURE_EXTERNAL_OES`。
- 顺手改：`kGLActiveTexture0..3` → `kGLTexture0..3`（改成 GL 自己的名字后即可被核到，+4 项）。

无法在本机复现 CI 的 18。二进制在 `/usr/local/opt/llvm/bin/`，`run-clang-tidy` 需要把它加进 PATH。

### lint 抑制注释要同时伺候两个工具
`// NOLINTNEXTLINE(performance-no-int-to-ptr)` → cpplint 报
`Unknown NOLINT error category [readability/nolint]`（只认自己的类别表）；
而 `// NOLINTNEXTLINE -- 散文说明` → clang-tidy 不再识别该抑制。
可用形态只有一个：**类别名写进上一行的散文注释，`// NOLINTNEXTLINE` 裸着单独一行**。

### 本轮在 render/gl 里修掉的 27 条 clang-tidy 发现（都是真问题）
C 数组 → `std::array` / `const char* const`；`rfind(...,0)==0` → `starts_with`；
`std::any_of` → `std::ranges::any_of`；`gl_quad.h` 的私有构造**漏了 `explicit`**（另两个有）；
宏参数加括号；int→ptr 走 `uintptr_t` 中转 + 裸 NOLINT。
另：`const auto x = f()` **也会**被 `ConstantPrefix: k` 判定（实测），所以 const 局部量一律
k 前缀；生产代码里零例非 k 的 `const <具体类型>` 局部量，这是被机检强制的真约定。

## 咨询：有没有成熟开源的 GL 框架能替掉 gl_api / gl_constants（已调研，未拍板）

用户问「现在还是 gl_api* gl_constants.h 写法，有没有成熟开源的 gl 框架」。本轮只调研，未改代码。

### 关键事实（本轮核实，别再重查）
- **我们这条路线不是土办法。** ImGui 的 `backends/imgui_impl_opengl3_loader.h` 是同一类东西：
  公共领域、单头约 760 行、由 `gl3w_gen.py` **按 `imgui_impl_opengl3.cpp` 实际用到的符号裁剪**
  到 54~58 个函数，内部自带 `wglGetProcAddress` / `dlsym` / `glXGetProcAddressARB`。它头注释给的
  理由几乎照抄我们的场景：让用户不必自带 loader、也不必被绑到我们的 loader，否则是 endless
  problems。Chromium 的 `ui/gl/gl_bindings.h` 也自建了一个 `GLApi` 结构装函数指针（同名）。
- **迁移面可以量**：`GlApi` 48 core + 25 ext = **73 入口点**；`gl_constants.h` **116 常量**；
  真正调用方只有 **5 个 .cc**（render/gl 的 gl_program/gl_texture/gl_quad/gl_shaders +
  media/gl/gl_present），其余 6 个是头文件与定义本身。
- **glad2**：MIT，由 gl.xml 派生的生成器。`--mx` 生成 `GladGLContext` = per-context 实例，
  调用形如 `gl->Clear()`，与我们 `gl_.Clear()` 几乎同形 → 迁移接近 sed。
  **坑：`--mx` 与 debug 选项互斥**（我们正好要用 `DebugMessageCallback`）。
  glad2 支持 header-only（`GLAD_GL_IMPLEMENTATION`）。OBS 用的就是它。
- **libepoxy**：MIT，**零初始化代码**、自动 alias 解析、GL/GLES 统一、EGL/GLX/WGL 全覆盖，
  1.5.10 维护中（提交到 2025-04）。代价：它是**系统运行库**（dlopen 型），不能当源文件内嵌。
- **GLEW**：2.2.0 停在 2021-06，维护停滞；进程全局表；不支持 EGL（osgEarth 已因此移除它）。
- **glbinding**：MIT，类型安全最强（enum class），但编译开销与生成物体量都大。
- 更高一层（会一并替掉 `GlProgram`/`GlTexture`/`GlQuad` 甚至 platform 层）：bgfx / sokol_gfx /
  Magnum / Diligent / ANGLE —— 另一个量级的决定，且会放弃「avbase_gl 零依赖可独立分发」。
- **倾向结论**：这一层的瓶颈不在「用不用第三方」，在「常量与入口点是不是机器生成的」。
  两条值钱的路：① 常量表改由 gl.xml 生成（零依赖不变、`check_gl_constants.py` 可退役）；
  ② 将来要更多扩展时把 glad 生成物塞进 `GlApi` 背后（接缝已在 `Load` + `GetProcAddress`）。

## 第五十七轮：内嵌 glad 2.0.8 替换手写装载器（已落地，未提交）

### 生成物与那条命令（就是契约）
`render/gl/third_party/glad/`：`include/glad/gl.h`(1920) + `include/KHR/khrplatform.h`(311)
+ `src/gl.c`(641)。完整命令与选项理由写在 `third_party/glad/README.md`，
`docs/13 §4.2` 留要点。三个选项都别动：

```sh
pip install glad2==2.0.8
python -m glad --api gl:core=3.3 \
  --extensions "GL_EXT_texture_sRGB_decode,GL_ARB_copy_image,GL_NV_copy_image,\
GL_EXT_texture_filter_anisotropic,GL_KHR_debug,GL_ARB_debug_output,\
GL_EXT_EGL_image_storage" \
  --out-path render/gl/third_party/glad --quiet c --mx
```

- `--mx` 必须开（否则函数指针进全局，两线程两 context 是 bug）；`--loader` 不能开
  （装载入口只能是 `NativeGLContext::GetProcAddress`）；`--alias` **不要**开
  （7 个扩展会被静默放大成 **75** 个，且 `CopyImageSubData` 与 `CopyImageSubDataNV` 会
  合并——`has_copy_image()` 依赖它们是两个独立指针）。
- **glad 的例外**：`glEGLImageTargetTexture2DOES` 属 ES 扩展 `GL_OES_EGL_image`，桌面 `gl`
  规格下生成器**直接拒绝**（无选项可解，`GL_OES_EGL_image` 会报
  `invalid extensions ...`）。换 `GL_EXT_EGL_image_storage` 能过生成，但这个函数仍然
  生成不出来 → 它是 `GlApi` 里**唯一**一条手工解（`PfnEGLImageTargetTexture2DOES`），
  注释就写在表旁边，让「glad 没覆盖多少」可见。

### `GlApi` 的形态
- 成员 `GladGLContext context_{}` + `const GladGLContext& context()` 访问器。
  **不派生**：① `operator->` 对裸指针不生效（派生写法读起来对、编译不过）；
  ② 本类是导出的，导出类派生自无可见性属性的类会触发 `-Wvisibility`。
- `Load()` 语义**反转**：从「逐个 core 入口点必须非空、报第一个缺失的名字」变成
  「**这里能不能画**」的版本门禁 `is_gles_ ? VERSION_3_0 : VERSION_3_3`。失败只剩两种，
  都指向 context 整体：没有 current context / context 太老（error 是驱动自报的版本串）。
- 能力查询改读 glad 标记：`context_.KHR_debug || context_.ARB_debug_output` 等。

### 顺手修掉 `check_invariants.py` C24 的一个误报

`lists /src/gl.c`。根因在 checker：`CMAKE_SOURCE_RE` 匹配**最长的路径字符游程**，
`${...}` 里的 `}` 不在字符类里，于是整串被切成 `/src/gl.c`；原有的「含 `$`/`{` 就跳过」
拦不住，因为切完的碎片里这两个字符都没了。修法：新增 `cmake_source_paths()`，判据是
**游程起始前一个字符若是 `}`，它必是 `${VAR}/path` 的尾巴**（真字面路径不会紧跟 `}`）。
C24/C25 共用。→ 变量驱动路径有两种形态：整条在变量里 / 只有前缀在变量里。

### 两条教训
1. **「零依赖」≠「零第三方代码」。** vendored 生成物随源码走：消费者不装 glad、不联网、
   不跑生成、不继承额外链接项。「内嵌了 glad」很容易被读成「avbase_gl 依赖 glad」，
   所以 docs/02、docs/BUILDING.md §3.8、docs/13 §5 都补了这句区分。
2. **换装载器的接缝确实在 `GlApi` 内部，但换表会泄漏到调用方。** 上一轮 docs/13 断言
   「所有调用方一行都不用改」——实现了，代价是调用方改了 146 处**名字**（枚举
   `kGLTexture2D` → `GL_TEXTURE_2D`、入口点 `gl.Clear` → `gl.context().Clear`），形状没变。
   只要模块把 GL 的名字直接暴露给调用方，换表就必然泄漏名字；想真透明就得给每个函数留
   转发方法，而那正是本模块刻意不做的（转发买不到东西，还把驱动给的指针伪装成类的方法）。

## GL 渲染性能评估：avbase 能否达到 libobs-gl 的指标

**结论**：libobs-gl 没有单一"性能指标"，按三层拆开——① 单路上传+上屏 **已达且余量很大**；
② 多源/FBO 合成 **缺失**；③ 硬件解码零拷贝 **缺失**（甚至反向）。

### 实测（微基准 /tmp/gl_upload_bench.cc，CGL 离屏 core profile + 内嵌 glad）

本机 Intel Iris Plus 655（**集成显卡 + 统一内存**），I420 三平面：

| 分辨率 | 每帧 | 同步 `glTexSubImage2D`+Finish | 仅提交 | PBO+Finish |
| --- | --- | --- | --- | --- |
| 720p | 1.3 MB | 0.076 ms | 0.075 ms | 0.144 ms |
| 1080p | 3.0 MB | **0.220 ms** | 0.222 ms | 0.539 ms |
| 4K | 11.9 MB | **1.305 ms** | 1.297 ms | 2.653 ms |

- **上传根本不是瓶颈**：1080p 占 60fps 预算 1.3%、4K 占 7.8%。
- **同步 ≈ 仅提交** → 此平台上 `glTexSubImage2D` **不阻塞**（统一内存无 PCIe 拷贝）。
- PBO 反而更慢，是**单缓冲 + 每帧 Finish** 的固定多一次拷贝成本，**不代表 PBO 的流水优势**；
  PBO 的价值在独显/离散显存上。这个数字**不可外推**到独显平台。
- 端到端：1080p60 与 4K30 素材跑 `play_glfw` 均 exit=0、0 ERROR。
- 整帧 CPU 侧只有约 25 个 GL 调用（`Present()` 数得出来），可忽略。

### 三层差距（带证据）

- ① **达标**：`gl_present.cc` 与 libobs 同路径——上传 → 单遍 YUV shader → 1 draw → swap。
- ② **缺失**：GL 层**无 FBO**、无多源、无滤镜链（grep `Framebuffer` 零命中；所谓 "compositor"
  是 `media/filters` 里 Chromium 风格的**帧调度器**，不是合成器）。参考框架 vspo 有 scene+FBO。
- ③ **缺失且反向**：`VideoFrame` 有一套完整零拷贝契约（`StorageType`/`NativeHandle`/
  `WrapNativeBuffer`/`ToI420`），但 `gl_video_sink.cc:129` 对硬件帧**主动 `ToI420()` 回读**成
  CPU I420 再走同步上传；且当前 FFmpeg 构建 `CONFIG_HWACCELS 0` → 硬件帧**从未产生**。
  `EGLImageTargetTexture2DOES` / `has_egl_image()` **零调用方**（手工解了但没用）。

### 两个结构性差异（口径问题）

- **呈现节奏**：`GlVideoSink` 用固定 16.67ms 定时轮询（GLFW 后端**不设 swap interval**，
  SDL2 用 `PRESENTVSYNC`）；`GetDisplayInterval` 注释自认是"估算"。
- **可观测性**：`VideoSinkStats`（presented/dropped/submit_failures）**全仓库无人消费**、
  从不打印；无耗时统计、无基准、`tests/testdata` **无 1080p 素材**。参考框架有
  `RenderPerfStats`（avg_upload_ms / avg_compose_ms / fps）。→ **avbase 当前无法量化验证性能**。

### 若要向 libobs 看齐的优先级

1. 接上性能计数器输出（`VideoSinkStats` + 每帧耗时）——最低成本最高信息量
2. 硬件解码 + EGLImage/IOSurface 导入，消掉 `ToI420` 回读（量级差异在这，不在上传）
3. FBO 合成层（仅当产品需要多源/滤镜）
4. PBO 推迟到有意上独显时再谈

### 改了什么

### 度量立刻抓到两个真 bug（本轮主要收获）

1. **帧率砍半**：1080p60 素材只出 30 fps。`GlVideoSink::PresentOne` 的 `PostDelayedTask(kMaxPresentInterval)`
   是从**调度点**算的完整 16.67ms，而 `SwapBuffers` 已为 vsync 等了 ~13ms → 周期 33ms。
   改成从**帧起点**算预算、只补差值。
2. **swap interval 没显式设**：修完 1 后同样素材一次 60fps 一次 53fps，差异在 `present_ms`
   （15.6ms = 等了 vsync / 1.1ms = 没等）。三个后端都靠平台默认值（GLFW 默认 0；CGL 恰好
   vsync，X11 不是）。现在 `GlfwGLContext`/`SdlGLContext`/`EglGLContext` 的 `MakeCurrent()`
   里显式 `SwapInterval(1)`。这同时让 1 的判据可靠：`GlVideoSink` 按「本帧是否已等过 vsync」
   决定要不要再等定时器。

### 实测（macOS，Intel Iris Plus 655）

```
1080p60   upload 0.8ms  compose 0.06ms  present 15.1ms  → 59.94 fps（修复前 30）
play_sdl2 --gl  同素材  ~53 fps，present 1.2ms（SDL2-GL 未阻塞，定时器驱动）
4K30      upload 1.9ms  → 25 fps（素材 30）← 未查，留作后续
```

### 未做（记录）

- **4K 有帧率损失**（25 vs 30），方向是 L4 的异步上传。
- **SDL_Renderer 2D 路径无耗时统计**（非 GL）。
- L2 FBO 地基 / L3 多源场景 / L4 硬件零拷贝 均未开始。

### 验证

no-ffmpeg **475/475**（+7）、macos-sdl2 **599/599**（+7），双预设 0 告警；
`check_invariants` 398 文件全绿；clang-format 全树 392 文件 0 偏离；真机冒烟 exit=0 / 0 ERROR。

### 长期约定（已同步到 MEMORY.md）

- **`--stats` 是渲染性能的唯一入口**：`play_* --stats` 每秒一行 JSON；`tools/bench_render.sh`
  一条命令出表。**别再用记忆里的性能数字**。
- **判断渲染回归先看三段耗时**：`upload` 慢 = 像素搬运；`compose` 慢 = draw；`present` 慢 ≈
  在等 vsync（正常）。`present_ms ≈ 刷新周期` 是设计意图，不是 bug。
- **平台默认值不是契约**：凡是决定节奏的东西（swap interval、对齐）必须显式设，
  否则症状是「帧率时好时坏」。

## 第五十九轮：L2 FBO 合成地基

### 做了什么

`GlPresenter` 从「直画窗口 back buffer」改成**两段式**：`Compose()` 画进离屏 canvas FBO，
`PresentComposed()` 把 canvas 纹理 blit 上屏；`Present()` = 两者 + swap（签名不变，宿主没改）。

新增原语（`render/gl/`，留在零依赖模块内）：`gl_framebuffer.{h,cc}`（`Ensure` 幂等且同尺寸
保留内容、`Bind` 连 viewport 一起设、`Destroy` 先删 fbo 再放纹理）、`gl_blitter.{h,cc}`
（全屏 quad + 纹理 program）。`render/gl/*.cc` 是 CONFIGURE_DEPENDS glob，**不用动 CMakeLists**。

接线：`PresentTiming` 加 `blit_ms`（独立成字段，不折进 compose）；`RenderPerfStats` 加
`blit` EWMA；`GlSurfaceBinding` 加 `canvas_width/height`（canvas 是**被绘制 surface 的属性**，
所以放 binding 不放 sink setter）；三个后端的 surface 结构各加两个字段。宿主加 `--canvas WxH`
（`play_sdl2` 要求必须配 `--gl`）。

### 两个真 bug / 陷阱

1. **blit 的翻转方向与渲染相反，必须 `flip_vertical=true`**。`GlQuad(flip=false)` 下 NDC y=-1
   对应 v=0（合自上而下 CPU 位图）；但 framebuffer 纹素第 0 行在视口**底部**。搞反的症状是
   「图上下颠倒」，**没有任何返回值或 GL 错误**。参考框架 `CreateFullscreenQuadVAO(flip_v=true)`
   结论一致，但它的 program quad 约定与 avbase 相反，**照抄会翻错** —— 独立推导的，写进
   `gl_blitter.h` 注释与 `docs/13 §4.4`。
2. **`GL_UNPACK_ROW_LENGTH` 单位是 texel 不是字节**（真 bug）。`UploadPlanes()` 从没设过它，
   而 `VideoFrame` 每平面行对齐 **64 字节**。1080p 恰好色度 stride = 可见宽度（960=960）把
   它藏住；64 宽画布上 stride=64、可见 32，每行多读一半 → **周期 8 行的绿色横条**。NV12 用
   `GL_RG`（1 texel = 2 字节）所以传 `stride / 2`，用完还原 0。暴露尺寸 320x240 / 854x480。

### 测试：仓库首个 GL 像素套件

`tests/unit/gl/`（`AVBASE_ENABLE_GLFW` 门控，10 个测试）。**隐藏窗口**（`GLFW_VISIBLE=FALSE`）
→ 不需要显示器、CI 可跑；`glfwSwapInterval(0)` 覆盖 `MakeCurrent()` 里的 1。
断言用**内容不用 GL 名字**（GL 会复用刚 delete 的名字）；读像素用 `Compose`+`PresentComposed`
**不用 `Present`**（swap 后 back buffer 未定义，会读到全黑）。

**两次反证确认测试有牙**：`flip_vertical` 改回 false → 朝向测试变红；`SetUnpackRowLength`
退回 0 → 立刻出现 `(55,188,35)` 绿色条纹。

### 测量（12s 素材，稳态）

```
720p60   59.86 fps   upload 0.292  compose 0.044  blit 0.014  present 16.05
1080p30  29.99 fps   upload 0.743  compose 0.068  blit 0.040  present 11.45
1080p60  59.92 fps   upload 0.710  compose 0.058  blit 0.029  present 15.21   ← 与 L1 一致
2160p30  27.98 fps   upload 1.811  compose 0.053  blit 0.018  present  9.99
```
**`blit_ms ≈ 0.015~0.03 ms` —— 离屏往返几乎免费**，compose 也没因为 FBO 变贵。

### 本轮最大的产出其实是两个「测量谎报」（都不是渲染 bug）

1. **`bench_render.sh` 把 60 fps 报成 53**：取 `median`，而统计约每 4 s 一行、素材只有 3 s，
   启动爬坡（fps=0 / fps=51）被算进中位数。改成「丢掉启动段 + 取尾部 5 采样中位数」，默认
   素材 6s → **12s**，并要求播放超出片尾。同二进制同负载：修前 53、修后 59.92。
2. **脚本从来没在「不带 `--canvas`」时跑过**：`set -u` + bash 3.2 下空数组 `"${arr[@]}"`
   直接中止。L1 记的「4 档素材跑通」是带参数那次。修法 `"${arr[@]+"${arr[@]}"}"`。

顺带**推翻 L1 的一个判断**：L1 说 SDL_Renderer 路径「如实报 0」。报 0 读起来是「全都免费」
不是「没测」—— 现在按 update / clear+copy+overlay / present 三段如实计时（blit 仍为 0，因为
那条路确实没有画布），并注明 SDL 是延迟提交，那里的 compose 读作「命令提交」。

### 关于「present_ms 从 15.1 掉到 0.8」的排查（结论：不存在）

一度以为 L2 破坏了 vsync 节流。实测同二进制连跑 5 次 present_ms 稳定在 **15.2~15.6ms**
（vsync 阻塞态）。又用 **SDL_Renderer**（完全不同的 present 机制）对照，同样报 ~52 fps ——
**两条独立通路给出同一个可疑数 = 环境**。根因是 `clangd --background-index --clang-tidy -j=8`
在 4 核 i5-8279U 上把 load 压到 **12**；而真正的「53 fps」来自上面那个 median 方法学错误。
**教训：两条通路同一个错数是环境，只有一个变才是代码。**

### 验证

no-ffmpeg **476/476**（+1 为 render_perf_stats 单测）、macos-sdl2 **610/610**（+11），
双预设 0 告警；`check_invariants` **407** 文件全绿；clang-format 全树 **401** 文件 0 偏离；
`gl_unittests` **10/10**；强制重编 6 个本轮源文件 0 warning。
`play_glfw --canvas 1280x720` 走缩放 blit 正常。

### 长期约定（已同步 MEMORY.md）

- **每一帧都走 canvas，包括单视频** —— L3 要建在其上的路径必须是被跑过的路径。
- **blit 用 `flip_vertical=true`**（与渲染相反），错了无返回值可抓，只能读像素。
- **`GL_UNPACK_ROW_LENGTH` 是 texel**，NV12 传 stride/2，用完还原 0。
- **GL 像素测试用隐藏窗口**；断言用内容不用 GL 名字；用 `PresentComposed` 不用 `Present`。
- **基准工具要先被基准过**：素材 ≥ 12s、丢启动段、取尾部 5 采样。
- **`max_present_ms` 是自启动累积的**，新进程里总是启动尖峰，不是稳态最差帧。

### 侦察结论：参考框架里哪些是 avbase 该抄的

`framework/render/scene/`（5,464 行）读下来，与 avbase 相关的只有三块：
- `render_scene.{h,cpp}`（267+1320）= 核心：`SourceLayer`/`CgLayer` 两种层，`Compose(Fbo,w,h)`
  按 `layer_index` 升序画，`SetLayerVisible/Opacity/Rect`，转场用 A/B 两个 FBO ping-pong。
- `render_channel.{h,cpp}`（97+210）、`source_transform.{h,cc}`（104+275）= 每层的变换。
- `html_layer_producer`（213+752）与 `render_scene_cg`（522）是 MediaComponent 专有的
  **HTML/OSR** 内容源（`ExecuteJs` / `SendMouseClick` / FreeType 文字栅格），avbase 不需要。

`uRect` 的约定从 `kQuadVertexShaderWithRectBody` 独立推出：
`gl_Position = aPos * uRect.zw + uRect.xy`，`aPos ∈ [-1,1]`
→ **`xy` 是 NDC 中心、`zw` 是 NDC 半幅**，全视口 = `(0,0,1,1)`。
注意它与 `gl::TextOverlay` 的拼法**不同**（那里 x/y 已是 NDC 偏移、w/h 是半幅的比例），
两者只在全幅时一致 —— 所以写了一个 `NormalisedRectToUvRect()` 而不是到处靠注释。

### #131 抽出 `GlVideoLayer`（纯重构，行为不变）

把 `GlPresenter` 里的 `EnsureTextures` / `UploadPlanes` / `UpdateColorUniforms` 搬进
`media/gl/gl_video_layer.{h,cc}`：一层 = 3 张平面纹理 + 格式/色彩空间状态 + `Upload(frame)` +
`Bind(program, opacity)`。**这是「N 层」的前置条件。**

搬的过程里发现原代码有一处**靠巧合工作**的地方：`UploadPlanes` 的
`if (!up.data) continue;` —— NV12 只有 **2 个平面**（`LayoutFor` 返回 `{2, ...}`，
V 平面按设计不存在），那句 `continue` 正是 NV12 能跑的原因。我一度改成 `return false`，
会让 NV12 直接不上传。现在改成显式 `plane_count = nv12 ? 2 : 3`：该在的平面缺失就失败
（截断的 I420 不再静默通过），NV12 的 V 不进入循环。

验证：`-Werror` 下干净编译；`gl_unittests` **10/10**；全门禁绿（不变量 409 / 格式 403 /
no-ffmpeg 476 / macos-sdl2 610）。

### #132 `GlScene`：N 层 + z 序 + rect/opacity/visible

`media/gl/gl_scene.{h,cc}`。设计要点：

- **不持有渲染目标与 context**：`Compose()` 画进「当前已绑定的目标」。切分点是
  「surface 属于调用方」—— 于是同一个 scene 既能合成到要显示的 canvas，也能合成到永不显示
  的离屏目标（导出），而 scene 自己不知道是哪种。
- **句柄不复用**（`LayerId` 单调递增，非向量下标）：跨过 `RemoveLayer()` 的旧句柄指向「没有」
  而不是「另一个层」。测试 `AStaleHandleAddressesNothing` 守着它。
- **排序在 Compose 里做一次**（`stable_sort` by z）：拖动图层会发很多次 `SetLayerZ` 而只呈现
  一次。`stable_sort` 让同 z 的层保持插入序 —— 这是调用方唯一能预测的顺序。
- **opacity 用 uniform 而不是第二个着色器**：`kYuvFragmentShaderBody` 加 `uOpacity`，
  两个着色器只差一个字符是维护陷阱。`SetLayerOpacity` 拒绝非有限值而不是 clamp（NaN 是上游 bug）。
- **整趟开混合**而不逐层判断：alpha=1 走 `SRC_ALPHA/ONE_MINUS_SRC_ALPHA` 与不开混合结果相同，
  分支只会给常见情况多一条路径。
- 新增 `CreateVideoLayerProgram()` 工厂：**单层 presenter 与多层 scene 共用同一个 program**
  （rect 顶点着色器 + YUV 片元）。`GlPresenter` 也改成用它并设 `uRect=(0,0,1,1)` ——
  这是恒等情形，所以 10 个 GL 测试全绿本身就是一次等价性证明。

### 关键结论（别踩）

- **`GlQuad(flip_vertical=false)` 把 `v=0` 放在 NDC 顶部**（`kQuadUpright`: `NDC(-1,-1)↔uv(0,1)`）。
  所以往 framebuffer 里画 → 图像第 0 行落在 framebuffer **最后一行** → **这张纹理的第 0 行是图像的底**。
  读它的人（`GlBlitter`、`GlTransition`）**都要 `flip_vertical=true`**。
  我曾在 `gl_transition.h` 写下「转场不用翻、blit 才要翻」的整段论证，前提就是错的；
  `ScenePresentTest.ATransitionAtZeroIsTheFromSceneUpright` 读回像素把它抓了（上面 1、下面 255）。
  顺带把 PROGRESS 第五十九轮里同样写反的推导一起改了。
- **NV12 只有 2 个平面**，`UploadPlanes` 里 `if (!up.data) continue;` 是 NV12 能跑的原因；
  抽 `GlVideoLayer` 时改成 `return false` 会让 NV12 完全不上传。现为显式 `plane_count = nv12?2:3`。
- **GL 对象归 presenter 所有**（`EnsureScene()`）：`GlPresenter::Shutdown()` 是唯一在宿主线程
  重新 make current 再删对象的地方。`GlSceneDriver` 只持有借用，`Shutdown()` 不碰 GL。
  两个 sink 的销毁顺序固定为「先 driver、后 presenter」。
- `UploadLayer()` 的时间**累加**进 `upload_ms`（赋值会把最后一层报成整帧）。
- 场景每帧作参数传入，**不存成 presenter 状态**。

### 头号结论（会再用的）

- **macOS 导入只接受 `GL_TEXTURE_RECTANGLE`**，2D 全组合回 `kCGLBadValue`（3.3 core 实测）。
  → 必须有 `sampler2DRect` 版 fragment body。
- **`GL_TEXTURE_RECTANGLE` 在 Apple 的 `gl.h` 里不存在**（只有 `glext.h` 的 `_ARB` / `_EXT`；
  `gl3.h` 才有）。后端用系统头，调用方用 glad → 两边各写一遍就是「新版的手写 GL 常量」。
  修法：后端用 `target()` 把它说出来，图层照着建纹理。
- **`CVPixelBufferCreate` + `kCVPixelBufferIOSurfacePropertiesKey = {}`** 就得到
  IOSurface-backed 的 2 平面 NV12 buffer（实测通过），不用手拼 plane 布局。

### 真机 A/B（同机、同 clip、相隔几分钟）

### fps 那个坑（差点记成回归）

60fps 素材 59.9 → 48.98。临时诊断打印 `spent`/`delay`：请求周期正好 16.67 ms、实际 ~18.5 ms。
再临时把 `VideotoolboxHwSpec()` 的 `device_type` 改坏强制软解 A/B → **软解也是 ~53 fps、
`present_ms` ≈ 0.6**。所以与路线无关：上一轮那次 swap 被 vsync 挡住（`present_ms ≈ 15.9`），
vsync 自己节流；这次 swap 直接返回，节流交给 `PostDelayedTask`，唤醒每次超 ~1.8 ms。
**已存在的现象，未修**：修法是按上次的**计划**起始时间累加，而不是按「现在」。

### 依赖：pinned FFmpeg 之前根本没有硬件解码

`CONFIG_VIDEOTOOLBOX 0`（`--disable-autodetect --disable-everything`）→ 整条管线产不出 GPU 帧。
`setup_ffmpeg.sh` 现在按 `uname` 追加 `--enable-videotoolbox --enable-hwaccel=h264_videotoolbox,
hevc_videotoolbox,vp9_videotoolbox`（两个都要：`--disable-everything` 把 hwaccel 也关了）。

**顺带修的脚本坑**：相对 prefix 会被 FFmpeg 按**构建目录**解析 ——
`tools/setup_ffmpeg.sh 7.1.1 tools/build` 装到 `tools/deps/ffmpeg-7.1.1-build-shared/tools/build`，
而 install 是最后一步，脚本打印「Installed:」退出 0，目标 prefix 没变。症状后来才出现且指错地方：
「this FFmpeg build has no 'videotoolbox' hw device type」。现在脚本里就解析成绝对路径。
