# 第三十七轮(承接 10-09 会话,跨零点):4.3b 收尾——计数三例全绿,代价是揪出解码器丢包

用户说「要」= 继续做 4.3b 剩下的那半(双速用例)。上一轮把它留在 DISABLED,理由是
「源侧:需要一个新的 VOD 源形态」。**这个判断对了一半**,而错的那一半比对的更有价值。

## 上一轮判断的修正:VOD 形态本来就存在,不需要新写

对的部分:1x paced 源确实喂不动 2x 消费者。
错的:**VOD 形态不需要新写**,`paced = false` 就是它——直播与 VOD 的区别正是「谁决定什么到期」:
源(墙钟边缘)决定 vs 消费者(时钟)决定。

实验:`spec_.paced = false;` 放在 `BuildPipeline()` 之前(不先设计,先做实验)。结果:
墙钟 2532ms ✅、媒体 5s ✅、**帧数 35/150 ❌**。→ 停止条件和时间都对,只有帧数少。
**关键分叉点**:这长得像「2x 丢帧」(速率处理错了),但**先去看它是不是真在丢帧**,而不是调容差。

## 真缺陷:`DecoderStream::DecodeNextBuffer()` 丢掉被 watermark 掐断的批次尾巴

诊断链(每一步都只加一行日志,不加猜测):
1. `SetMinVLogLevel(2)` 打开合成器丢帧日志 → **零条丢帧**。既然没丢,帧就是没进队列。
2. 给 `PutCurrentFrame()` 加日志 → 帧时间戳跳跃:`600000 → 800000 → 1066666 → 1333333`
   (视频帧 33333µs 一帧,即**每隔 7 帧才来一帧**)。帧在**进合成器之前**就少了,
   而解复用器与合成器之间只有 `DecoderStream`。
3. 读 `DecodeNextBuffer()`:`while (index < size && outputs < watermark)`,循环有**两个**退出条件,
   注释却只认一个("Exhausted the batch")。watermark 先到时 `pending_buffers_.clear()` 照样执行
   → **把已解复用、未解码的尾巴永久丢掉**(解复用器游标已越过,不会重发)。
4. 加计数器定案:`BATCH-DISCARD undecoded=N` → **93 批,89 批剩 7**,即「取 8 帧解 1 帧」。

修法一行判据:批次未消费完则 `return`(尾巴留给下一次 `DecodeNextBuffer()`,由 `MaybeDeliver()` 触发)。

**为什么能活到现在**:`kBuffersPerRead = 8` 一直都在,但**只在解复用器一次真交多个 buffer 时可达**。
paced 合成源按构造一次只给一个(可用量随墙钟逐帧增长);而 `FFmpegDemuxerStream::Read` 是
`PopUpTo(count)`——**真实文件一直是批量的**。所以真实播放里解码器一旦跑到渲染器前面,就会丢
解复用器刚交出来的**压缩包**(对 P/B 帧比丢帧更糟)。这不是「为了测试才修」。

## 断言换了:墙钟 → 设备计数

原 `EXPECT_NEAR(wall_ms, 2500, 1200)` 在 ffmpeg 预设过、**在 ASan 下必挂**:同一个 run 墙钟
4624ms,而**两个计数断言全对**。原因:这个夹具的显示器是**测试线程自己拉的**,一轮墙钟由
**泵自己的开销**决定,不由管线速率决定 → **断言墙钟等于断言构建类型**。

改断言**设备侧计数**:2x 时一个 device period 覆盖两倍源帧 → 「5 秒媒体」离开设备只有 2.5 秒音频
= **120000 输出帧**(1x 是 240000)。容差 5%,理由写在断言旁:循环停在**外推的音频时钟**上
(两次设备回报之间外推),ASan 并行负载下实测差 1184 帧 / 1%;要区分的另一个答案差着一倍。

## 顺带:存量缺陷——`ffmpeg_demuxer_unittest` 的 ASan 释放后使用

asan 预设一度变红,挂 `FFmpegDemuxerTest.Open*`,栈是 `MemoryDataSource::ReadBlocking` 的
**heap-use-after-free**:两个桥测试把文件读进**局部** `vector`,把 `data()` 交给解复用器,而
`MemoryDataSource` **不复制**字节、解复用线程会读到它自己结束 → 测例体一结束就撞。

**先判归属再修**:`git stash` 本轮改动,干净树重复 30 次 → **3 次失败、同一条栈** ⇒ 存量竞态,
非本轮引入。修法:字节改为夹具成员,并**声明在 `demuxer_` 之前**(成员逆序析构 ⇒ 比解复用器活得久)。
修后 40 次 0 失败。

## 教训

- **「症状像什么」不是「病因是什么」**。35/150 长得像 2x 丢帧,实际是解复用器交给解码器的东西被丢了。
  分辨两者只需要一行日志。我先花了几轮猜启发式(`ComputeTargetDelay` 的 diff 该用 `last_timestamp`
  还是 `next_timestamp`)——猜错了,那几轮没进版本库,时间白花。
- **一处自相矛盾的注释就是一处未判定的设计**。`clear()` 上方的 "Exhausted the batch" 与循环的
  两个退出条件矛盾;上一轮 `VideoStream::Read` 的缺锁是同一模式(一处注释说"无锁因单序列",
  另一处说"并发读")。**两轮连续撞到同一模式**,下次读代码可以把它当检查项。
- **一个计数器就能定案**。`BATCH-DISCARD undecoded=N` 把「可能」变成「93 批 / 89 批剩 7」。
  与上轮 `sample <pid>` 抓栈同理:最便宜的测量往往就是决定性的那个。
- **门禁红了先判归属**。`git stash` + 重复 30 次,把「本轮引入」与「存量」分开,既不修错地方,
  也不把存量的锅记在本轮账上。
- **不要把「测不到的东西」做成断言**。墙钟在这个夹具里测的是机器,不是管线;换成设备计数后
  同一个用例在 ASan 下从「必挂」变成「稳定绿」。**先问这个量由谁决定,再决定要不要断言它。**

# 第三十八轮:FFmpeg 不是平台 —— 64 文件搬进 media/ffmpeg/,三条门禁落地

## 起因:用户一句反对推翻了我给的方向

上一节(第三十八轮前半,见 PROGRESS)评审目录结构时,我给的第 3 步是

# 续:目录再分层评估(media/base 与 media/ffmpeg 要不要开子目录)

用户问能否按功能(transcode/encode/decode/io)再开子目录。**只做分析,未改任何文件。**

判据仍是 docs/06 §7.6:目录划分决定的是"能不能 glob",不是好看不好看;本仓铁律是**目录 = 构建目标**。

- **media/base/ 保持扁平。** 27 个 .cc 是接口层:被 143 个外部文件、333 条 include 引用(覆盖 12 个
  模块组:ffmpeg/filters/renderers/player/platform/examples/tools/tests)。按 audio/video 切会切开
  `decoder_buffer`/`decoder_config`/`media_types` 这几个 a/v/text 共享的"货币"类型 → 跨子目录 include,
  结构反而更乱。**根 `base/` 按设施分层(memory/task/time/threading/functional/types)是另一回事**——
  那些组各自是叶子,且它用显式列举(platform_thread_posix.cc 按平台挑)。
- **media/ffmpeg/ 也保持扁平,但有且只有一个可切点。** 33 个 .cc,docs/02 §4.4 已分五类,与按文件名
  算出的分组吻合:①版本与初始化 4 / ②解复用 5 / ③解码 6 / ④编码·转码 10 / ⑤像素与辅助 8。
  但**① 和 ⑤ 是横切共享层**:`av_includes.h` 被全部 5 类引用(它就是本目录 PCH)、`compat.h` 被 4 类
  引用 → 照 5 类开 5 个子目录,只会得到两个"人人 include 的 common/",路径变长结构不变。
- **唯一值得动的:④ 编码/转码 → `media/transcode/` + 独立 target。** 硬证据:这 10 个 .cc 在 media/ffmpeg
  之外共 **13 条 include,全部来自测试**(encode_muxer / remuxer / audio_encoder / concat_job /
  transcode_job / video_encoder_factory 六个 unittest),**生产侧 0 引用**。唯一看着像生产消费者的
  player 截图走的是 ⑤ 里的 `ffmpeg_image_snapshot.*`,不属于这一类(它只依赖 video_convert + compat)。
  落点是 `media/transcode/` 而非 `media/ffmpeg/transcode/`:同 target 的子目录收益≈0,独立 target 才让
  Phase 5 离线转码不必进播放器/CI 的默认链接集。

代价(两条都适用):

1. **`file(GLOB)` 不递归**(docs/06 §7.6 明文)。加一层子目录后 `base/*.cc`、`ffmpeg/*.cc` 立刻漏文件,
   必须补 `*/*.cc` 或每子目录一行。漏了不静默——C25 会报"某 .cc 无归属"。
2. include 是**仓根全路径**(`media/base/pipeline.h`),移动即改路径;上限 media/base 333 条 /
   media/ffmpeg 57 条(只改真正移动的那部分)。
3. 门禁用**前缀**匹配(`rel.startswith("media/ffmpeg/")`),同前缀下开子目录不影响 C4/C16/C27;
   但新开 `media/transcode/` **必须扩 C4 的 allowlist**,否则转码文件里的 libav 头会被判
   "FFmpeg 头跑出隔离区"——这是最容易漏的一条。
4. `tests/unit/media_filters/` 是显式列举(4 进 media_unittests、其余进 media_ffmpeg_unittests),
   源文件搬了测试目录跟不跟是第二个决定。

  在 `avbase::media::ffmpeg`)。查了全目录:本仓命名空间跟的是**层**(`avbase::media` =
  media/base 接口的 FFmpeg 实现;`avbase::media::ffmpeg` = vendor 胶水),不是目录。
  按目录改命名空间会破坏既有约定,收益为零。
- **不给 `avbase_transcode` 加 PCH。** `avbase_ffmpeg` 的 PCH 是 av_includes.h,理由是
  "本目录每个 TU 都需要它";transcode 的判据不是 libav 而是产品线,且
  `ffmpeg_transcode_job_async.cc` 是纯线程 shim、不含 libav。实测不加 PCH 编译通过。
- **不进 `avbase::avbase` 聚合。** 转码是 opt-in,调用方显式链 `avbase::transcode`。
- **不重写 PROGRESS 里第 28 轮的历史路径记录**(`media/filters/ffmpeg_concat_job.*`、
  `platform/ffmpeg/video_encoder_factory.*`)。那是当时的事实,历史台账不动。
